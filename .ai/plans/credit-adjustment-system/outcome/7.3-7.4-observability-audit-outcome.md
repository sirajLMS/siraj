## 7.3 — Structured success logging

`runAdjustment` (the shared post-commit wrapper around the adjustment
transaction) already logged once per successful adjustment; the task was to
make the payload conform to the required field set. Changes:

- `runAdjustment(params, logMessage)` now builds the log context from
  `AdjustmentTxParams` — the third `logContext` argument is removed and the
  three wrappers (`addCredit`/`subtractCredit`/`subtractWithCarryover`) pass
  only their distinct log message. This both satisfies the required field set
  and keeps the three call sites from duplicating the context literal.
- Log context is now exactly:
  `{ actorUserId, studentId, adjustmentType, changeAmount, carryoverTeacherId }`
  (`changeAmount` is the signed ledger delta `params.signedHours` — positive for
  Add, negative for Subtract flows; `carryoverTeacherId` is `undefined` outside
  carryover so the key simply carries the optional).
- **Logger placement decision**: logged once in `runAdjustment` — i.e. at the
  wrapper that awaits the committed transaction — not inside
  `executeAdjustmentTransaction` and not per private flow. A rolled-back
  transaction therefore produces **no** success log; a committed one produces
  exactly one.
- Failure logging unchanged: the service throws domain errors and does not
  `logger.error` adjustment failures (callers/`logger.logDomainError`
  conventions own those surfaces) — no double-logging introduced.

## 7.4 — Audit-log integration: EXISTS (not N/A)

Evidence of an existing audit subsystem (grep `AuditService|logAudit|audit\.log`):

- `backend/services/system/audit.service.ts` — `AuditService.createManyAuditLogs`,
  `createManyAdminAuditLogs`, etc.
- `backend/db/repo/audit/audit.repository.ts` — bulk insert behind
  `runInTransaction` (owns its own transaction when no `tx` is passed).
- `backend/types/audit/audit.types.ts` — `CreateAuditLogInput` with typed
  `ActorType` / `AuditEntityType` / `AuditAction` unions.
- Established call-site pattern (followed exactly): `CreateAuditLogInput` →
  `await AuditService.createManyAuditLogs([input])` wrapped in a best-effort
  `try/catch` with `logger.error` — seen in
  `backend/services/whatsapp/whatsapp-account.service.ts` and
  `backend/services/appearance/appearance-settings.service.ts`.

Implementation in `credit.service.ts`:

- New private `emitAdjustmentAudit(params, created)` invoked from
  `runAdjustment` **after** the adjustment transaction commits (no `tx` passed —
  the repo wraps the insert in its own transaction, so an audit write is never
  rolled into the adjustment tx and a committed adjustment is never rolled back
  by an audit failure).
- Audit entry: `actorType: "USER"`, `actorUserId: params.actorUserId`,
  `entityType: "STUDENT"`, `entityId: studentId` (no CREDIT-like entity type
  exists in `AuditEntityType` — a dedicated type is a follow-up candidate),
  `action: "UPDATE"`, `description: \`Credit adjustment ${adjustmentType}\``,
  `newState: { creditTransactionId, adjustmentType, changeAmount,
  carryoverTeacherId }` (null when absent).
- Best-effort: any audit failure is swallowed with a `logger.error` carrying
  `{ actorUserId, studentId, adjustmentType, error }` — identical shape to the
  whatsapp call site.
- Import follows the established call-site specifier
  `@/backend/services/system/audit.service` (same as whatsapp/appearance/profile).

Behavioral notes:

- Idempotent re-submits (in-tx existing-row return) also log + audit — the
  returned row is a successful adjustment record; matching the pre-existing
  log behavior (kept deliberately, no return-shape change).
- The 23505 recovery path (winner row returned from the catch branch) emits no
  success log/audit — identical to pre-change behavior.
- No notes/PII beyond the required fields are logged or written.

## Test isolation change (why)

`credit-adjustment.service.test.ts` mocks every seam `credit.service.ts`
imports. The new `AuditService` import would otherwise flow through the mocked
`db.transaction` into a bare `{}` tx (`t.insert` missing → TypeError swallowed
by the best-effort catch — nondeterministic noise), or against a configured DB
would write real audit rows. Added:

```ts
await mock.module("@/backend/services/system/audit.service", () => ({
  AuditService: { createManyAuditLogs: async () => [] },
}));
```

No test bodies changed; no new assertions added (7.3/7.4 are side-effect
observability, existing contract tests unchanged).
