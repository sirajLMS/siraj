## Enum/transaction split — how it was handled (no custom restructure needed)

The plan's `(a) enum adds outside a transaction / (b) column adds transactional`
requirement is already implemented natively by the repo's migration runner
(`backend/db/scripts/migrate.ts` → `runDrizzleMigrations`):

1. `ensureIdempotentMigrations()` rewrites generated SQL into idempotent form
   (DO-block guards for `CREATE TYPE` / `ALTER TYPE ADD VALUE` /
   `ADD CONSTRAINT`; `IF NOT EXISTS` for columns/indexes). The migration file was
   already in this form — a second run reported "no changes needed".
2. `ensureEnumValuesCommitted()` + `preCommitEnumStatementsForMigrationFile()`
   extract every `ALTER TYPE ... ADD VALUE` from each migration file and execute
   them **outside any transaction** before any folder is applied.
3. Each folder then runs in its **own** transaction (not one global transaction),
   and the in-transaction DO-guards no-op because the enum values are already
   committed — this is exactly what avoids PG 55P04.

Therefore the Task 0.3 custom-migration mechanism
(`backend/db/migration/35-…sql` + auto-bundled folder) was **not** extended for
Task 0.5: the generated folder covers both halves correctly. Custom SQL is
reserved for data/seed/grant changes, per the settled convention.
