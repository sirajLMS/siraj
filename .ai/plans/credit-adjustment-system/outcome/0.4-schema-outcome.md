## Deviations from `implementation.md` §2.4 (deliberate, documented)

1. **Carryover date columns are TEXT, not PG `date`.** The repo has no dialect-aware
   `date` helper in `backend/db/schema/__shared__/dialectAwareBuilder.ts`, and that
   file was outside this task's scope. The settled precedent is degradation to TEXT
   with ISO `YYYY-MM-DD` strings: `teachers.dateOfBirth: textColumn("date_of_birth")`
   ("PG-only: `date` column has no dialect-aware helper — degraded to TEXT") and
   `invoices.issue_date`/`due_date`/`paid_date` in `billing/billing.ts` ("date -> text
   (ISO string)"). Followed that exact convention. If Task 0.5 or later wants a true
   PG `date` column, a new `dateColumn` helper must be added to
   `dialectAwareBuilder.ts` first (cross-file, flagged to orchestrator).
2. **`adjustmentType` is `NOT NULL DEFAULT 'ADD'`, not nullable.** The task brief's
   parenthetical said "nullable per plan", but both the §2.4 code sketch and the §1
   architecture diagram say `NOT NULL DEFAULT 'ADD'` (safe additive migration; every
   pre-existing row means "plain ledger entry, not an adjustment"). Followed the
   design. `.$type<CreditAdjustmentType>()` is required (kept from the sketch) because
   plain string-literal unions are not assignable to TS string enums — without it the
   inferred select type would not satisfy `CreditAdjustmentReturnType.adjustmentType`.
3. **One-sided relation only.** `carryoverTeacher` lives on `creditTransactions`; no
   mirrored `creditTransactions`/`carryoverCreditTransactions` relation was added to
   `teachers` — consistent with the existing one-sided `creditedBy`/`sourcePayment`
   relations.
