## Exact contract (Tasks 1.5–1.8 depend on this)

**File**: `backend/services/billing/credit-adjustment.idempotency.ts`

```ts
export interface CreditAdjustmentIdempotencyInput {
  studentId: string;
  adjustmentType: CreditAdjustmentType; // from "@/backend/enum"
  hours: number;
  carryoverTeacherId?: string | null;
  carryoverFromDate?: string | null;
  carryoverToDate?: string | null;
  carryoverPaymentDate?: string | null;
}

export function deriveAdjustmentIdempotencyKey(input: CreditAdjustmentIdempotencyInput): string;
```

### Hashed fields (fixed positional order, colon-joined)

```
["credit-adjustment", studentId, adjustmentType, String(hours),
 carryoverTeacherId ?? "", carryoverFromDate ?? "",
 carryoverToDate ?? "", carryoverPaymentDate ?? ""].join(":")
→ createHash("sha256").update(...).digest("hex")  // 64-char lowercase hex
```

- The leading literal `"credit-adjustment"` namespaces the key so it can never
  collide with ledger keys derived by other flows (purchase/deduction).
- `null` and `undefined` missing carryover fields normalize to the empty segment —
  both produce the identical key.
- **`notes` (the rich-text reason) is deliberately NOT hashed** (design decision in
  `implementation.md` §3.3): two operators submitting the same numeric adjustment with
  different reasons must NOT be collapsed. The test suite encodes this behavior.
- Deviation from the plan sketch: none in hashing semantics. The only difference is
  the parameter type name — the plan's `CreditAdjustmentInput` lives in
  `backend/types/` and did not exist yet (Task 1.1 pending at dispatch time), so a
  structural subset interface `CreditAdjustmentIdempotencyInput` is defined inline in
  the helper (service-layer `.types.ts` files are prohibited). It is a strict subset
  of the planned `CreditAdjustmentInput` minus `notes`, so once 1.1 lands, callers in
  1.5–1.8 can pass `CreditAdjustmentInput` directly — structural typing accepts it
  (verified via the "notes excluded" test, which passes an object carrying `notes`).
