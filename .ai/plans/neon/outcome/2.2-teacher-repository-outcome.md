## Changes Made

### 1. Added 2 Module-Level Prepared Statements

Defined at module scope (outside the namespace, before it) so they are compiled once at module load time:

| Prepared Statement | Drizzle Name | Query Pattern |
|---|---|---|
| `findByUserIdPrepared` | `find_teacher_by_user_id` | `select().from(teachers).where(...).limit(1)` |
| `findByIdPrepared` | `find_teacher_by_id` | `select().from(teachers).where(...).limit(1)` |

### 2. Updated `findByUserId()` to Use Prepared Statement

```typescript
export const findByUserId = async (userId: string, tx?: DBTransaction) => {
    if (!tx) {
      const result = await findByUserIdPrepared.execute({ userId });
      return result[0] ?? null;
    }
    // Fall back to regular query for transactions
    const [teacher] = await tx.select().from(teachers).where(eq(teachers.userId, userId)).limit(1);
    return teacher ?? null;
  };
```

### 3. Updated `findById()` to Use Prepared Statement

```typescript
export const findById = async (id: string, tx?: DBTransaction) => {
    if (!tx) {
      const result = await findByIdPrepared.execute({ id });
      return result[0] ?? null;
    }
    // Fall back to regular query for transactions
    const [teacher] = await tx.select().from(teachers).where(eq(teachers.id, id)).limit(1);
    return teacher ?? null;
  };
```

## What Was NOT Changed (and Why)

The following methods were **intentionally left unchanged** because they use complex join conditions and/or dynamic queries that are difficult or impossible to parameterize with `sql.placeholder(...)`:

| Method | Reason Skipped |
|---|---|
| `create()` | Performs multiple queries (check existence, insert, fetch user) — write operation |
| `searchTeachers()` | Has a dynamic `searchQuery` that can be empty (uses conditional `undefined` in `and()`) — cannot prepare with optional condition |
| `getTeacherDirectory()` | Has dynamic optional search + `innerJoin` + `$dynamic()` + `queryWithPagination()` — complex pipeline |
| `getTeacherDirectoryMetrics()` | Uses aggregated `sum(case ...)` with `innerJoin` — no simple placeholder pattern |
| `getTeacherProfileForEdit()` | Has `innerJoin` + sub-selects (`totalClasses`, `avgEngagementScore`) — complex select |
| `updateTeacherProfile()` | Dynamic `setInput` built from filtered `Object.entries` — write operation |
| `upsertByUserId()` | Complex `onConflictDoUpdate` — write operation |

These methods are either write operations (not suitable for prepared statements), have dynamic WHERE conditions, or include complex joins that exceed the simple `eq(table.column, placeholder)` pattern.

## Pattern Followed

Exactly matching the pilot pattern from `backend/db/repo/users/user.repository.ts`:
1. Prepared statements defined at **module level** (before the namespace)
2. `sql.placeholder("paramName")` for dynamic values
3. `.prepare("descriptive_name")` with clear, unique names
4. `.execute({ paramName: value })` to run
5. Transaction fallback: when `tx` is provided, skip the prepared statement and use a regular query builder
