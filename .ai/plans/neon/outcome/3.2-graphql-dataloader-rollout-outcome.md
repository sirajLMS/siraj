## Carry-Over Knowledge

### Pattern: Pre-compute in Service Layer
The most effective approach for eliminating N+1 in Pothos is to pre-compute related data in the service layer before returning results. This avoids the complexity of `t.loadable()` for fields that need parent data beyond just an ID (e.g., `displayAmount` needs `amount` + `currency` + `displayCurrency`).

### Pattern: Batch Repository Methods
For fields that only need an ID (e.g., `provider` on meeting configs), adding a batch repository method (`getByIds(ids)`) and using it in the service layer is clean and efficient.

### Pattern: `t.loadable()` for Cross-Type Relations
For fields that reference another loadable type (e.g., `targetUser` → `UserPothosObject`), `t.loadable()` with `getDataloader(ctx).loadMany(ids)` is the cleanest approach and reuses the existing DataLoader.

### Limitations
- `t.loadable()` doesn't support list-typed returns — use `t.expose()` with pre-computed arrays
- `t.loadable()` only receives IDs, not full parent objects — pre-compute in service layer when parent data is needed
- Pre-computing in the service layer is simpler and more maintainable than complex DataLoader setups for fields needing parent data
