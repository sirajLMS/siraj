# Frontend Architectural Review: `profile` Views

## Executive Summary

The `profile` domain is predominantly compliant: switchers correctly use `ResponsiveViewSwitch` + `createLazyView` (`ProfileShell`, `ProfileTabNav`, `ParentProfileContainer`, `StaffProfileView`, `TeacherProfileContainer`, `AssignedStudentsTab`, `PaymentMethodsTab`, `MeetingConfigsTab`, `NotificationPreferencesTab`), ViewModels are viewport-agnostic, and section views broadly reuse `SectionPanel`, `StatusBadge`, `ProfileFieldRow`, `PhoneFormField`, `CurrencySelect`, `TimezoneSelect`, `CountrySelect`, `GenderSelector`, and `DateOfBirthControllerField`. However, several bespoke reimplementations persist — most notably two separate duplicative `MeetingGenerationStatusIndicator` implementations, a hand-rolled error state inside `ProfileShellShared`, a custom raw-`Chip` mobile tab nav despite an existing `MobileTabPill` primitive, raw `Select` in billing, and un-paginated / redundantly paginated lists.

## Non-Negotiable Execution Protocol

Every modified file MUST pass per-file verification immediately after the edit:

```bash
bun run scripts/health/sub-loop.ts <file-path> --lifecycle codescene
```

Exit code 0 is mandatory after **each** touched file (not batched). The strict chain runs `tsgo → oxlint → biome:check → lint:type-aware → check:duplicates → codescene --file` and short-circuits at first failure.
