## Security Audit

- Data-access only: no permission checks, no business rules, no error
  strings in the repo additions (repo/AGENTS.md separation of concerns).
- Row locking is confined to caller transactions: `getById(id, tx,
  { forUpdate: true })` locks inside the passed `tx`; `updatePayrollCalculation`
  takes `tx` as its REQUIRED first parameter — a payroll write cannot be
  issued outside a transaction executor through this method.
- No injection surface: all values are bound parameters via drizzle; the
  search term is wildcard-escaped (`escapeLikeWildcards`) before being
  wrapped in `%…%`; the idempotency hash is compared as a bound parameter.
- Soft-deleted instances are excluded from the report (E9 visibility rule).
- No secrets, tokens, or credentials handled; no network/filesystem access;
  no module-level mutable state.

### Dialect-handling decisions (apply to later cross-dialect work)

1. **Row locking**: use `withForUpdate(query)` from `@/backend/db` (from
   `backend/db/dialect.ts`) — emits `FOR UPDATE` on PG, no-ops on SQLite.
   Precedent: `quota.repository.ts selectQuotaForBookingFIFO`.
2. **Case-insensitive search**: `caseInsensitiveLike(column, pattern)` from
   `@/backend/db` (PG `ILIKE` / SQLite `LIKE`) + `escapeLikeWildcards` from
   `@/backend/utils`. Precedent: `daily-schedule.utils.ts`.
3. **Time windows / date filters**: compute bounds as JS `Date`s and bind
   them (`gte(col, date)`) — never PG `interval` arithmetic or `::date`
   casts. `scheduledStartAt` is timestamptz on PG / epoch-millis on SQLite;
   drizzle maps both. Precedent: `ratelimit.repository.ts`,
   `getTeacherProgressFeed`.
4. **JSONB text extraction**: `sql`${col}->>${key}`` works on BOTH dialects
   (PG jsonb `->>`, SQLite/libsql JSON1 `->>`); the key and the compared
   value are bound params. Precedent:
   `permission-management.repository.ts` localizedOrderExpr.
5. **Boolean SQL expressions**: `sql<boolean>`…`.mapWith(Boolean)` (PG native
   boolean, SQLite 0/1).
6. **`ClassOutcome` / `ClassExecutionState` import path**: they are NOT in
   `@/backend/enum` (the classes barrel lacks them) — import from
   `@/shared/constants/class-instance-detail.enum` (entity-setup.ts
   precedent). `CalculationStatus` IS in `@/backend/enum`.

### Report read-model decisions (for Tasks 1.8 / 2.x / 4.x)

- `teacherName` = `users.name` via `teachers.userId`; `studentName` =
  `students.name` directly (repo-wide convention —
  `recurringScheduleBaseQuery`, `daily-schedule.utils.ts`, parent/teacher
  repositories). The plan text's "students (via users)" parenthetical was
  resolved to the repo convention.
- `filters.teacherId` / `row.teacherId` are `teachers.id`; `filters.studentId`
  / `row.studentId` are `students.id`. GraphQL (task 2.x) must map any
  user-id-based teacher picker accordingly.
- `dateFrom`/`dateTo` are inclusive `YYYY-MM-DD` bounds on
  `scheduledStartAt`, evaluated in **UTC** day boundaries
  (`00:00:00.000Z`/`23:59:59.999Z`); display-timezone concerns belong to the
  UI/service layer.
- Rows are ordered `scheduledStartAt DESC, id ASC` (newest first,
  deterministic tiebreak); soft-deleted rows are excluded (E9).
- `isStudentAbsence` = `outcome = 'ABSENT' AND actual_start_at IS NOT NULL`;
  `isTeacherAbsence` = `actual_start_at IS NULL AND outcome <> 'ABSENT'` —
  a faithful SQL mirror of implementation.md §3.3's calculator branches.
  **LEAVE rows fall outside both flags** (they take the grace/pro-rate
  branch in §3.3; E13's "paid in full" for LEAVE emerges via the grace
  branch, not the student-absence flag). Task 1.6 must keep its TS branch
  conditions aligned with these SQL predicates or the report column will
  disagree with the pay outcome.
- `findPayrollReportRows` returns raw rows + `totalCount` only — aggregates
  (`totalPaidAmount`, `rowCountByStatus`, dominant currency) are task 1.8's
  service-side job per §3.6. Note for 1.8: the §3.6 snippet reduces over the
  returned PAGE; if full-filtered-set aggregates are wanted, either query
  with a large limit or extend the repo later.
- Empty `calculationStatuses: []` is treated as "no status filter"
  (documented + tested); blank/whitespace `search` likewise.
