## Enum-value-use rule (why 3 units)

PostgreSQL forbids using a new enum value in the same transaction that added it (and PG < 12
forbids `ALTER TYPE ... ADD VALUE` in a transaction at all). Unit 1 adds the value, unit 3
(the only unit that USES `'payroll'` in an INSERT) runs in a later folder/transaction.
Additionally, the repo's runner (`backend/db/scripts/runDrizzleMigrations.ts`) pre-commits
every `ALTER TYPE ... ADD VALUE` it finds in a folder **outside** that folder's transaction
(`preCommitEnumStatementsForMigrationFile`), so even unit 1's in-transaction copy is a
guarded no-op on re-run. Migration 36's `app_permission` values get the same treatment.

## Carry-Forward Knowledge

1. **Migration pipeline (repo-specific)**: `bun run db generate` = `drizzle-kit generate
   --ignore-conflicts --config drizzle.config.ts` (offline diff vs the newest
   `backend/drizzle/*/snapshot.json`; there is NO `meta/_journal.json` — drizzle-orm
   1.0.0-rc.4 errors if it finds one). `bun run db migrate` = bundle custom SQL
   (`applyCustomMigrations`) → make everything idempotent (`ensureIdempotentMigrations`)
   → apply per-folder transactions with enum pre-commit
   (`runDrizzleMigrations`). Applied-state tracking is **name-based**
   (`drizzle.__drizzle_migrations.name`) — renaming an existing folder makes it re-run.
2. **New custom migration recipe**: write `backend/db/migration/NN-*.sql` (idempotent,
   `--> statement-breakpoint` NOT needed — the bundler adds them) → run `bun run db
   migrate` → the bundler creates `backend/drizzle/<ts>_custom_<name>/migration.sql` and
   updates `.custom-migrations.json`. Standalone pre-generation (no DB) via a temp script
   calling `applyCustomMigrations()` is also possible (task 2-b precedent).
3. **Splitting a generated migration**: rename the generated folder to keep its
   snapshot.json as the LAST unit; give earlier units snapshot-less folders with
   timestamp-prefixed names sorting before it; remove statements owned by other
   migrations (here: the two `app_permission` values owned by migration 36). The next
   `db generate` must print "No schema changes" — that is the correctness check.
4. **Enum type names now live in the DB**: `calculation_status` (6 values above) and
   `system_setting_category` gained `payroll`. `app_permission` gained
   `accounting.payroll_view` / `accounting.payroll_manage` (via migration 36, applied
   here). Phase 1/2 code can rely on all of them existing on dev + test DBs.
5. **Backfill state**: all 658 existing `class_instances` rows sit at `NOT_CALCULATED`
   (default backfill). The §2.6 one-shot paid-amount backfill for COMPLETED rows is
   Phase 6 territory (script `scripts/payroll-backfill.ts`, SCREAMING_SNAKE_CASE literals).
6. **PG 18 quirk**: NOT NULL columns get auto-named `<table>_<col>_not_null` constraints —
   do not "clean them up" and do not assert them in tests.
