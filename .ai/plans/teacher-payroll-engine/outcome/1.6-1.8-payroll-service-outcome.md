## Summary

Created `backend/services/teacher/payroll-calculation.service.ts` — the
`PayrollCalculationService` namespace with the three Phase-1 core methods:

1. **`calculateForInstance(input, tErrors, tx?)`** — computes the payroll
   snapshot for one class instance through the four payable-duration branches
   (student-absent → full scheduled pay; teacher-absent → zero; on-time within
   grace → full scheduled pay; late beyond grace → pro-rated, capped at
   `scheduledEndAt`, overtime never credited). Rate comes from the PURE
   `resolveClassRate` (pricing module) after fetching the recurring schedule /
   subject / teacher rows; an unusable rate degrades the snapshot to
   `NOT_CALCULATED` with an `"Auto-calc failed: <reason>"` payroll note instead
   of throwing (AC-2.5's no-rollback contract). Guards: PAID always rejects
   (`PAYROLL_ALREADY_PAID`), PARTIALLY/REFUND/WAITING_PAID are sticky without
   `forceRecalc`, non-terminal execution states reject
   (`PAYROLL_NOT_TERMINAL`). Every write is inside one transaction:
   teacher-scoped `pg_advisory_xact_lock` → `FOR UPDATE` row read →
   `updatePayrollCalculation` → `PAYROLL_STATUS_TRANSITION` event via
   `createMany`. Identical re-runs within 30 s collapse onto the first result
   via `findRecentByInstanceAndHash` + a content-derived sha256 key.
2. **`applyOverride(input, tErrors)`** — the four-mode override matrix
   (Refund / Calculated / Not Calculated / Partially) with `computeOverridePatch`
   equivalent (`buildOverridePatch`), state guards
   (`PAYROLL_ALREADY_PAID` on PAID; `PAYROLL_AWAITING_SETTLEMENT` on
   WAITING_PAID without `force`), the 30-second duplicate collapse via
   `deriveOverrideIdempotencyKey` (RAW note hashed, sanitized note persisted),
   and a `PAYROLL_OVERRIDE` audit event carrying `actorUserId`. Refund writes
   the exact string `"0"` (CHECK text-equality contract). Calculated re-runs
   the calculator inline; Partially prorates the row's calculated amount (or a
   fresh calculation when the row has none) by the validated integer
   percentage.
3. **`getReport(actorUserId, filters, pagination, tErrors)`** — the read model:
   one page via `findPayrollReportRows` plus service-side aggregates over the
   **full filtered set** (a second capped scan of 10 000 rows — the CSV-export
   ceiling — skipped when the whole set already sits on the requested page):
   precision-safe decimal-string `totalPaidAmount` (BigInt minor units, no
   floating point anywhere), dominant `totalPaidCurrency`, and a zero-filled
   `rowCountByStatus` with every `CalculationStatus` key present.

All money math is exact integer arithmetic: decimal strings parse into BigInt
minor units (hundredths), hour proration and percentage math use
round-half-up integer division, and the report sum accumulates minor units —
never `Number` arithmetic.

## Semantic Review (item by item)

- **Race conditions — all read-then-write sequences inside ONE tx**:
  - `calculateForInstance`: `requirePermission` (read-only, pool-level) →
    `db.transaction` (or the caller's tx) → unlocked PK read (lock key only) →
    `acquireAdvisoryLock(tx, "payroll_teacher_<id>")` → `getById(…, {forUpdate})`
    → status guards → compute → idempotency lookup →
    `updatePayrollCalculation` → event insert → commit. Every status decision
    and write happens on the FOR UPDATE-locked row; the advisory lock is taken
    before those status reads and serializes per-teacher batch runs
    (0.4–0.5 outcome requirement; `student_${id}` credit-service precedent).
    Lock ordering is uniform (advisory → row), so two payroll transactions can
    never deadlock against each other.
  - `applyOverride`: same `lockInstanceForPayroll` prologue, then state
    guards → idempotency lookup (`findRecentByInstanceAndHash`) → write →
    event, all inside one `db.transaction`. The idempotency check and the
    event insert share the transaction (TOCTOU-free; E11's two-operator race
    resolves as last-writer-wins with both events preserved, per the row lock
    serialization).
  - `getReport`: read-only; two independent repo reads.
- **No module-level mutable state / no unbounded caches**: all module-level
  values are `const` literals or immutable `Set`s built from literals; no
  caches (grace settings are re-read per calculation by design — NFR-12).
- **No dead branches; every throw reachable**: PAID/NOT_TERMINAL/ALREADY_PAID/
  AWAITING_SETTLEMENT throws are all reachable from public inputs;
  `requirePartialPercentage`'s throws are reached via `validateOverrideInput`;
  the switch `default` handles WAITING_PAID/PAID targets; the three defensive
  invariant throws (`CLASS_INSTANCE_NOT_FOUND` on the locked re-read,
  `PAYROLL_UPDATE_FAILED`, `PAYROLL_EVENT_INSERT_FAILED`) mirror
  implementation.md §3.3/§3.4's own guards and are forced by the repo
  signatures' null returns — unreachable only because the same-tx row lock
  makes the invariants hold, which is their purpose.
- **No cross-layer imports**: services → repo (`@/backend/db/repo/…`), enum
  (`@/backend/enum`, `@/shared/constants/…`, `@/shared/lib/enum`), lib
  (`@/backend/lib`), types (`@/backend/types`), sibling services
  (`billing/permission-utils`, `pricing/rate-resolver.service`,
  `teacher/payroll-grace-settings`, `teacher/payroll-override.idempotency`),
  `@/shared/locale` (type-only). All allowed directions; no frontend imports.
- **No manual `ReturnType` construction**: all returns are plain object
  literals typed by the task-1.1 interfaces; mappers are hand-written field
  copies (they also normalize `undefined`→`null`, so no `ReturnType` helper
  would be correct anyway).
- **Clean comments**: `rg -in "REQ-|task [0-9]|phase [0-9]|\.ai/plans|specs\.md|tasks\.md|trackable|implementation\.md"`
  over the service → **0 matches**. All JSDoc describes domain behavior

## Spec deviations from implementation.md (all deliberate, semantics-first)

1. **REFUND `"0"` instead of `"0.00"`** (§3.5 snippet) — the DB CHECK does
   text equality; `"0.00"` would be rejected (0.4–0.5 outcome carry-forward).
2. **`TeacherRepository.findById` instead of `findByUserId`** (§3.3 snippet) —
   `class_instances.teacherId` is `teachers.id`, not a users id; the snippet's
   call could never resolve a teacher. (Row-shape verified against
   `teacher-due.service.ts`.)
3. **Float money math replaced with BigInt minor units** (§3.3/§3.5/§3.6
   snippets use `Number`/`toFixed`) — semantic-review mandate "never float
   arithmetic"; results identical for 2-decimal inputs, exact for 3+-decimal
   rates where float rounding could drift a cent.
4. **PAID blocks `calculateForInstance` even with `forceRecalc`** (§3.3's
   sticky list would let force overwrite PAID) — task 1.9's matrix mandates
   "Force-recalc blocked on PAID"; settled money is immutable.
5. **Rate-resolution failure handled in-branch instead of throwing**
   (§3.3 throws `NotFoundError("TEACHER")` for a missing teacher) — folded
   into the `NOT_CALCULATED` + note branch so AC-2.5's "shall not roll back
   the state transition" holds for every rate-tier failure; a missing teacher
   row (FK-guarded anyway) degrades rather than aborts the session completion.
6. **Calculation idempotency via a content-derived key** — `PayrollCalculationInput`
   carries no `clientRequestId` (task-1.1 contract), so the 30-second collapse
   (task 1.9 matrix) keys on the computed snapshot content
   (instanceId + status + duration + amount): identical re-runs collapse,
   edited rows produce new keys and recalculate.
7. **Aggregates over the full filtered set, not the page** (§3.6 snippet
   reduces the returned page) — the task-1.1 `PayrollReportPage` contract says
   "Sum of paid amounts across the filtered set"; implemented via the 1.2
   outcome's sanctioned "query with a large limit" approach, capped at 10 000
   rows (E17's export ceiling) with a page-reuse shortcut when the whole set
   is on the requested page.
8. **`PAYROLL_STATUS_TRANSITION` event on every calculation write** — US-9's
   auditability (NFR-6 "every calculation reconstructible") + the dispatch
   instruction; the event's `toState` carries the idempotencyKey so the
   collapse lookup works for calculations too.
9. **`calculateForInstance` gained an optional `tx?` third parameter** —
   AC-2.1 requires the auto-trigger (task 1.11) to run the calculation inside
   the state-transition transaction; the two-arg call shape is unchanged
   (`createDueEntry`'s optional-tx precedent).
10. **Validation errors use localized labels, not hardcoded strings** —
    §3.5's `throw new DomainError("PAYROLL_PARTIAL_REQUIRES_PERCENTAGE",
    "partialPercentage required")` becomes
    `ValidationError(tErrors.payroll.partialRequiresPercentage)` etc.
    (clean-comments/i18n rule); error codes for the two validation families:
    `VALIDATION` (GraphQL extension code via the `ValidationError` base).

### Branch behavior table (for 1.9's test matrix)

| Row state | Branch | calculatedDuration | Status |
|---|---|---|---|
| `outcome=ABSENT` + `actualStartAt` set | student-absent | full scheduled | CALCULATED |
| `actualStartAt` null + `outcome≠ABSENT` (incl. ON_DEMAND_NO_CREDITS_ABSENT) | teacher-absent | 0 | CALCULATED (zero pay) |
| `outcome=ABSENT` + `actualStartAt` null | on-time (falls through) | full scheduled | CALCULATED |
| ran, `lateness ≤ grace` (short ≤30-min sessions, long above) | on-time | full scheduled | CALCULATED |
| ran, `lateness > grace` | pro-rated | `max(0, min(actualEndAt ?? scheduledEndAt, scheduledEndAt) − actualStartAt)` | CALCULATED |
| rate unusable / teacher row missing | failure | null, amount null | NOT_CALCULATED + note `"Auto-calc failed: …"` |
| status PARTIALLY/REFUND/WAITING_PAID, no `forceRecalc` | sticky return | row's values | unchanged |
| status PAID (any input) | blocked | — | throws `PAYROLL_ALREADY_PAID` |
| non-terminal executionState | blocked | — | throws `PAYROLL_NOT_TERMINAL` |
