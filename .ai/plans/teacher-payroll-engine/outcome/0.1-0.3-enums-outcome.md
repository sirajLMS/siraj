## Summary

Task 0.1 introduced `CalculationStatus` (`NOT_CALCULATED | CALCULATED | PARTIALLY |
REFUND | WAITING_PAID | PAID`, SCREAMING_SNAKE_CASE per every other PG enum) using the
repo's settled cross-layer enum convention: the canonical `export enum` lives in
`shared/constants/teachers/payroll-calculation.enum.ts` and
`backend/enum/teachers/payroll-calculation.enum.ts` is a value re-export shim
(identical to the `CreditAdjustmentType` / `CreditReason` pattern).
`CalculationStatusPothosEnum` is registered once in
`backend/graphql/pothos/shared/enum.pothos.ts` (enum-object form, per
`backend/graphql/pothos/AGENTS.md`).

Task 0.3 added `Payroll = "payroll"` to `SystemSettingCategory` (additive, lowercase
value). Verification confirmed `backend/db/schema/enums.ts`
(`systemSettingCategoryEnum = createPgEnumFromEnum("system_setting_category",
SystemSettingCategory)`, line 139) derives its values from the TS enum — **no
`enums.ts` change required**.

Adding the `Payroll` category value surfaced an **unplanned cross-layer ripple**
(the plan's file list under-scoped 0.3): the frontend exhaustively maps
`SystemSettingCategory` → generated GraphQL enum (`useGeneralSettingsViewModel.ts`)
and the locale layer types `categories: Record<SystemSettingCategoryKey, string>`.
The new value broke tsgo in 4 places (baseline was 0). The fix — required to restore
the 0-error gate — was: regenerate the GraphQL schema + codegen (adding `Payroll` to
the generated `SystemSettingCategory` enum), add the `Payroll` switch case, extend the
`SystemSettingCategoryKey` union, and add `payroll` labels to the ar/en
`dashboard.settings.general` locales (+ locale snapshots).

## Carry-Forward Knowledge (for later subagents)

1. **Cross-layer enum convention**: canonical `export enum` in `shared/constants/`,
   backend `backend/enum/` file is a value re-export shim. Never redefine the enum in
   backend (two distinct TS enum identities are not mutually assignable).
2. **`CalculationStatusPothosEnum` is registered** in
   `backend/graphql/pothos/shared/enum.pothos.ts` (line 250). Phase 2/4 tasks
   (`implementation.md` §4.1 shows `payroll.pothos.ts` re-registering it) MUST import
   it from `@/backend/graphql/pothos/shared/enum.pothos` instead — re-registration
   triggers Pothos "'CalculationStatus' has already been declared" (pothos AGENTS rule).
   Logged as D6.
3. **Pothos prints registered-but-unreferenced enums** into `schema.graphql`
   (`CalculationStatus` and `CreditAdjustmentType` both appear with no field
   referencing them yet). But `graphql.ts` (typescript-operations codegen) only emits
   types used by documents — `CalculationStatus` is in the schema but NOT yet in
   `graphql.ts`. First document/field usage will bring it into `graphql.ts`
   automatically on the next regen.
4. **Adding a `SystemSettingCategory` value requires a 5-point ripple** (future
   categories beware): shared enum value → `SystemSettingCategoryKey` union
   (`shared/locale/types/dashboard/settings/general.ts`) → ar/en locale
   `categories` labels → GraphQL schema+codegen regen → `toGraphQLCategory` switch
   case in `useGeneralSettingsViewModel.ts`. Locale snapshots regenerate at prebuild.
5. **Task 0.4**: import `CalculationStatus` from `@/backend/enum` (or deep
   `@/backend/enum/teachers/payroll-calculation.enum`) for
