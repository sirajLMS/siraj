# Outcome — Task 1.11: Wire auto-trigger into the session state machine

- **Status**: ✅ Done

## Summary

The class-session state machine (`backend/services/session/class-session.service.ts`
— the service that owns execution-state transitions; it imports the state-change
validation from `backend/services/scheduling/state-change-validation.service.ts`)
now invokes `PayrollCalculationService.calculateForInstance(input, tErrors, tx)`
**inside the same database transaction** as every transition into a terminal
execution state (`COMPLETED` or any of the four `ON_DEMAND_*` terminal states).

Wired transition paths (all with the caller's `tErrors` and the transitioning
user's id as `actorUserId`):

| Path | Transition | Trigger location |
|---|---|---|
| `ClassSessionService.stop` | RUNNING → COMPLETED (outcome TAKEN) | `db.transaction` wrapper around `stopClassInstance`; trigger after the updated row returns |
| `ClassSessionService.updateStatusAbsent` | ACTIVATED/RUNNING → COMPLETED (outcome ABSENT) | `db.transaction` wrapper around `markClassAbsent` |
| `ClassSessionService.updateStatusLeave` | original → COMPLETED (outcome LEAVE) | inside the existing leave tx, after `processClassLeave`, re-reading the completed original (`getById(processed.originalId, tx)`) |
| `ClassSessionService.markNoCreditsBatch` | batch → any `ON_DEMAND_*` terminal execution state | inside the caller-supplied tx; per-instance re-read + state verification, then trigger with `isOnDemand: true` |

Non-terminal transitions (`start` → RUNNING, `activate`/`activateOverride` →
ACTIVATED, `reset` → NOT_ACTIVATED, `reschedule` successor insert,
`deleteInstance` soft-delete) intentionally do **not** trigger.

Key design decisions (all documented in code comments, domain language only):

1. **Failure isolation (AC-2.5)** — the trigger helper
   (`triggerTerminalPayrollCalculation`) wraps the calculator call in a
   try/catch and logs + swallows every rejection. No calculator failure —
   permission guard, settled/sticky row, non-terminal re-read, or unexpected
   error — can roll back the session state transition. Rate-resolution
   failures never reach this boundary at all (the calculator degrades them
   in-branch to `NOT_CALCULATED` + payroll note, per the 1.6–1.8 contract).
2. **`isOnDemand` flag (AC-2.2)** — derived from the post-transition row via
   `ON_DEMAND_TERMINAL_EXECUTION_STATES` (a `Set<string>` of the four
   `ON_DEMAND_*` enum values), which matches the calculator's own
   `TERMINAL_EXECUTION_STATES` one-for-one. `COMPLETED` rows trigger with
   `isOnDemand: false`.
3. **Actor policy** — actor-carrying paths attribute the calculation to the
   transitioning user. `markNoCreditsBatch` gained an optional
   `options.actorUserId`; actor-less system flows (the on-demand no-credits
   resolver cron currently omits it) **defer** the calculation with a warning
   log rather than inventing a system actor — no system-actor precedent
   exists in the repo, and the calculator's `requirePermission` gate
   (ACCOUNTING_PAYROLL_MANAGE) would reject a synthetic actor anyway.
   Deferred rows stay at the schema default `NOT_CALCULATED`, reconcilable
   via the US-6 override dialog.
4. **Same-tx mechanics** — the repo's `runStateChange`/`processClassLeave`
   already accept `tx?` and only open their own transaction when it is
   undefined, so wrapping the call in `db.transaction` and passing the tx
   joins the transition + status event + payroll snapshot into one commit.

Trigger-suite coverage matrix:

- **Fires on terminal transitions**: stop (asserts repo call AND calculator
  both receive the same `fakeTx` sentinel → same-tx proof); mark-absent;
  leave (completed original re-read in-tx); on-demand batch → CANCELLED with
  `isOnDemand: true`; on-demand batch → NO_CREDITS_ABSENT with
  `isOnDemand: true`; batch fan-out calculates once per flipped instance.
- **Does NOT fire on non-terminal transitions**: start (RUNNING); activate
  (ACTIVATED); reset (NOT_ACTIVATED); soft-delete cancel; non-terminal batch
  execution state (no re-read either); batch that flipped zero rows (no
  re-read).
- **Guard semantics**: actor-less system batch → skip + warn (asserted
  message); rows the batch did not actually flip (concurrent claim /
  already-terminal) → skipped; calculator rejection → state change preserved
  + single `logger.error` (AC-2.5).
- Input shape asserted exactly (`{ instanceId, actorUserId, isOnDemand }`)
  plus `tErrors` pass-through on the actor-carrying service paths.

## Security Audit

- **No new permission surface**: the trigger adds no permission checks of its
  own; the session-action gates (`SESSION_OVERRIDE_ACTIONS`,
  `SESSION_UPDATE_STATUS_ABSENT`, `SESSION_UPDATE_STATUS_LEAVE`,
  `SESSION_ACTIVATE_CLASS`) are unchanged and still run before any state
  change. The payroll write itself remains behind the calculator's internal
  `requirePermission(ACCOUNTING_PAYROLL_MANAGE)` — a transitioning user can
  never widen their own payroll authority through the auto-trigger.
- **actorUserId provenance**: always the authenticated transitioning user
  (GraphQL context user), never a client-supplied field; persisted by the
  calculator on the snapshot and event rows (NFR-5).
- **No injection / no secrets**: no new free-text inputs; the trigger passes
  only ids, enum-derived flags, existing `tErrors`, and the tx. No network,
  filesystem, or module-level mutable state added (`ON_DEMAND_TERMINAL_EXECUTION_STATES`
  is an immutable module constant).
- **Error-channel hygiene**: all failure logging goes through `logger`
  (error/warn) with structured context; nothing sensitive in the payloads
  (ids + message strings only).

## Semantic Review (item by item)

- **Race conditions — trigger inside the SAME tx**: verified structurally for
  all four paths. `stop`/`updateStatusAbsent` wrap the repo call in
  `db.transaction` and trigger inside the callback; `updateStatusLeave`
  triggers inside its pre-existing tx; `markNoCreditsBatch` triggers inside
  the caller-supplied tx (repo `runStateChange` joins a passed tx instead of
  opening its own — verified in `state-changes.ts:122`). The suite asserts
  the calculator receives the exact tx object the transition ran in
  (`fakeTx` sentinel), so transition + payroll snapshot commit or roll back
  together (AC-2.1). The batch re-read uses the same tx, so it observes the
  just-flipped state under the batch UPDATE's row locks.
- **No unawaited promise leaking**: every trigger call site awaits; the batch
  fan-out awaits `Promise.all` of per-instance triggers before
  `markNoCreditsBatch` returns.
- **No dead branches; trigger fires ONLY on terminal transitions**: the
  `updatedCount > 0` gate, the `ON_DEMAND_TERMINAL_EXECUTION_STATES.has(...)`
  gate, the null-actor gate, the per-instance state-verification skip, and
  the catch branch are each exercised by a dedicated test (fired side + not
  fired side). Non-terminal paths (start/activate/reset/reschedule/delete)
  contain no trigger code at all.
- **No cross-layer imports**: added imports are sibling service
  (`@/backend/services/teacher/payroll-calculation.service` — deep path per
  the file's established sibling-import pattern, avoiding the
  `@/backend/services` barrel self-cycle), shared enum value
  (`@/shared/constants/class-instance-detail.enum`), shared lib
  (`@/shared/lib/enum`), existing `@/backend/types` types. No repo-bypass, no
  frontend, no GraphQL-context reliance.
- **Clean comments — zero plan-artifact references**: greps over the added
  lines of both modified files and the whole new test file for
  `REQ-|task N|phase N|\.ai/plans|specs\.md|trackable|implementation\.md|AC-n|US-n`
  → **0 matches**. All new JSDoc describes domain behavior (terminal states,
  same-tx atomicity, best-effort semantics, deferral policy).
- **Enum VALUE imports**: `ClassExecutionState` is a value import and every
  runtime position uses enum members; the raw drizzle `executionState` string

- **Failure isolation per AC-2.5**: catch-all around the calculator call —

### Semantics for Phase 2 / TB.1 (E2E journeys)

1. **AC-2.1 same-tx proof**: the trigger suite asserts tx identity with a
   sentinel — TB.1 journeys that complete a session should additionally
   observe `class_instances` payroll columns populated immediately after the
   stop/absent/leave mutation returns (no eventual-consistency window).
2. **Actor policy**: journeys driven by a payroll-manage-capable operator
   (super_admin / academy_admin per migration-36 grants) will see
   `CALCULATED` snapshots; journeys driven by teachers/parents will see the
   trigger invoked but rejected at the calculator's permission gate (logged,
   row stays `NOT_CALCULATED`) — see D14 before encoding journey assertions.
3. **System cron flows** (on-demand no-credits resolver; session expiry
   missed-by-system) produce NO auto-snapshot today — TB.1 should treat
   `NOT_CALCULATED` after those flows as the expected baseline (D14).
4. **Leave flow**: only the ORIGINAL instance auto-calculates (successor is
   NOT_ACTIVATED); the calculator sees `outcome = LEAVE` + `actualStartAt`
   set → payable branch per its documented matrix.
5. **Calculator error surface is fully swallowed at the trigger boundary** —
   Phase-2 GraphQL resolvers will never see payroll errors surfacing from
   session-state mutations.
