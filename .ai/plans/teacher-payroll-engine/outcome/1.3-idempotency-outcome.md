- **Status**: ✅ Done

## Summary

Created `deriveOverrideIdempotencyKey(input)` — the deterministic SHA-256 key that
lets `applyOverride` (task 1.7) collapse duplicate submissions within the 30-second
lookup window (spec US-6 AC-6.10 / edge case E1 / NFR-4). The key hashes a fixed
serialization of the five identifying fields — **(instanceId, targetStatus,
partialPercentage, note, force)** — prefixed with the `"payroll-override"` domain
tag, exactly the field list mandated by the task definition. The actor user id and
the client-generated request id are deliberately **not** hashed: a double-clicked
submission and a second operator repeating the identical override must collapse onto
the same key.

The implementation follows the established sibling precedent
`backend/services/billing/credit-adjustment.idempotency.ts` line-for-line in
structure: a narrow `PayrollOverrideIdempotencyInput` interface (structural subset of
`PayrollOverrideInput` from task 1.1), a `parts` array serialized in fixed order with
absent optional fields normalized to empty segments, joined by `":"` and hashed with
`createHash("sha256")` → lowercase hex digest.

**Path adaptation (documented deviation from the plan text)**: trackable-tasks.md
says `backend/services/teachers/payroll-override.idempotency.ts`, but the actual
domain directory is `backend/services/teacher/` (**singular** — verified:
`backend/services/teachers/` does not exist). The file was created in the singular
dir. The same adaptation applies to every remaining Phase 1 task (1.4–1.13) which
also names the plural dir.

The teacher services barrel (`backend/services/teacher/index.ts`) follows the billing
barrel precedent (which exports `./credit-adjustment.idempotency`), so the new helper
was added there via an atomic edit as the alphabetically-first export.

Task-mandated coverage:
- ✅ same input → same key (`determinism > same input produces the same key`)
- ✅ percentage change → different key (`field sensitivity > changing partialPercentage changes the key`, 50 → 75)

4-Tier depth:
- **Tier 1 (all branches)** — the helper's only branches are the three nullish
  normalizations (`partialPercentage ?? ""`, `note ?? ""`, `force ?? false`); every
  side of each is exercised: present values (sensitivity block), absent/null values
  (normalization block), plus the always-taken hash/serialization path (determinism
  block). No other branches exist.
- **Tier 2 (boundaries)** — null vs undefined `partialPercentage` normalize
  identically; null vs undefined vs **empty-string** note normalize identically
  (empty note is falsy, and `applyOverride` will persist it as `null`, so the key
  treats it as absent — consistent with the service contract);
  `partialPercentage: 0` is DISTINCT from an absent percentage (0 is a meaningful
  refund-equivalent value, spec E2); 0 / 50 / 100 hash pairwise distinctly (E2/E3);
  `force: true` vs `false` vs absent — true differs from both, absent ≡ false.
- **Tier 3 (chaos)** — Arabic + emoji notes hash distinctly from Latin equivalents
  and each other; a 3,400-char note (beyond the 2,000-char `payroll_note` column
  cap — hashing happens on the raw note, sanitization is the service's job) hashes
  stably and distinctly from its own prefix; a colon-bearing note cannot impersonate
  a different `force` flag (serialization-safety: `note: "approved:true", force:
  false` ≠ `note: "approved", force: true`).
- **Tier 4 (N/A — documented)** — real-world integration/mocking/failure-injection
  is not applicable: `deriveOverrideIdempotencyKey` is a pure, synchronous,
  side-effect-free function over its arguments with zero external dependencies
  beyond `node:crypto`'s deterministic sha256. No I/O to mock, no failure modes to
  inject, no DB/GraphQL surface (the 30-second window lookup and event write belong
  to task 1.7's `applyOverride` and task 1.2's repository method).

Additional coverage beyond the tiers: 100-input seeded fuzz (mulberry32, seed 42)
asserting per-input stability and global key uniqueness; 25-input single-field
mutation sweep asserting each of the five fields alone always changes the key;
explicit exclusion test proving `clientRequestId` / `actorUserId` do NOT affect the
key (two different request ids + actors with identical override content → same key,
matching AC-6.10's "same instanceId + target status + percentage + note" wording);
key-insertion-order stability; lowercase-64-hex format check.
