## Step 3 — Forward-migration rehearsal

**Mechanism (adaptation, no repo files touched):** `bun run db migrate` bootstraps env
via `applyEnvFile()` which **overwrites** `process.env.DATABASE_URL` from the selected
env file — a shell `DATABASE_URL` export cannot survive it, and a temp `.env` swap is
forbidden. The db CLI's migrate action ultimately spawns
`bun --no-env-file run backend/db/scripts/migrate.ts` (the exact pipeline:
`applyCustomMigrations → ensureIdempotentMigrations → runDrizzleMigrations`), so the
rehearsal invoked that entrypoint directly with: all 45 `KEY=VALUE` pairs from `.env`
parsed line-by-line (plain `source .env` is unsafe — line 114 is a non-assignment) +
`DATABASE_URL` overridden to the staging URL (value never printed; bun `--no-env-file`
so the repo `.env` cannot clobber the override).

**Result:** `MIGRATE_EXIT=0`, whole command 30,574 ms (bun boot + env validation +
scanning 104 folders; the 3 pending folders applied 17:42:32.980 → 17:42:33.237 ≈
**257 ms**; log lines: `Applied migration:` ×3 + `Migrations completed successfully!`).
Runner pre-commits verified the payroll enum additions as guarded no-ops
(`Pre-executing 1 enum addition(s) from ...payroll_calculation_types`).

## Deviations & adaptations (all documented, none faked)

1. **Direct `migrate.ts` invocation with env override** instead of `bun run db migrate`:
   the CLI's `applyEnvFile()` overwrites `process.env` from the env file, so the
   documented env-var mechanism only works at the spawned-runner level (the identical
   pipeline the CLI action runs). No `.env` swap, no repo file modified.
2. **`.env` line-parser instead of `source`** — `.env` line 114 is not a `KEY=VALUE`
   assignment (breaks POSIX sourcing); vars exported without shell evaluation.
3. **`--actor-user-id` added to the task's backfill commands** — the 6.1 script
   contract mandates it (fail-fast `requirePermission(ACCOUNTING_PAYROLL_MANAGE)`);
   the task text omitted it. Actor = staging super_admin (bypass path).
4. **4 backfill runs instead of 2** — 1,196 candidates > 500/run cap; the loop-to-
   exhaustion is the script's documented contract and run 4 (0 candidates, 0 processed,
   exit 0) is the idempotency proof the task asked for.
5. **Enum rollback asymmetry** — PG cannot `ALTER TYPE ... DROP VALUE`, so
   `system_setting_category.'payroll'` stayed through the rollback; the types unit's
   re-run is a guarded no-op for it (verified applied cleanly). Everything else was
   fully recreated.
6. **Rollback data-loss note (by design)** — dropping `calculation_status` reset the 6
   dev `WAITING_PAID` rows to the schema default; a real prod forward-only migration
   never drops columns, so this is rehearsal-only and the rows were recalculated by
   the backfill (now `CALCULATED`).

## Environment findings (predecessor anomaly + new)

- **Non-atomic snapshot FK orphans (predecessor's `credit_transactions` finding,
  generalized):** the staging build used two separate `pg_dump` phases (data, then
  post-data) with `session_replication_role=replica` on restore; 20 post-data FK
  constraint statements across 14 tables failed validation on staging
  (`credit_transactions`×3, `leave_requests`×3, `impersonation_sessions`×2,
  `invoices`×2, `recurring_schedules`×2, and 1 each for `dst_migration_runs`,
  `learning_resources`, `leave_quota_usage`, `notification_deliveries`,
  `session_metadata`, `student_status_history`, `teacher_assignments`,
  `user_meeting_configs`, `user_permission_groups`). Mechanism: concurrent dev writes
  between the two dump phases → child rows whose parents postdate the data dump.
  **Staging-only artifact; zero impact on payroll objects** (all class_instances /
  users FKs + all payroll constraints restored); documented as a snapshot-methodology
  caveat for any future rehearsal (use a single-transaction `pg_dump --snapshot`).
- **Dev DB carries no live payroll snapshots** (all 2,645 rows were NOT_CALCULATED /
  NULL timestamps except the 6 WAITING_PAID oddities) — the backfill's 1,196-row
  patch count is therefore the true historical backlog for terminal COMPLETED sessions.

## Carry-forward knowledge

1. The migrate pipeline tolerates `DATABASE_URL` env override at the
   `backend/db/scripts/migrate.ts` level (the CLI wrapper does NOT — it clobbers
   process.env from the env file); this is the safe pattern for any future
   point-a-tooling-at-another-DB task (e.g. prod-like rehearsal, DR restore drill).
2. Lock observation recipe that worked: background psql session sampling
   `pg_locks` (~10 ms cadence) + `NOT granted` count for waiters; 3,000 samples is
   enough for a sub-second migration; gives both hold-window and waiter counts.
3. Backfill throughput on staging (dev-grade hardware): ~60-65 rows/s
   (500 rows ≈ 8.2-8.5 s); a 100k-row prod backlog would need ~26 min of looped runs —
   schedule accordingly (operator actor + sequential advisory locks are by design).
4. `class_status_events` grows one `PAYROLL_STATUS_TRANSITION` row per patched
   instance — prod backfill sizing should budget that table's growth.
5. Teardown pattern `DROP DATABASE ... WITH (FORCE)` + `pg_database` count + scratch
   removal verified clean; dev read-only invariants (ci=2645, journal=104, 8 cols)
   held before and after every phase.
