## Security audit

- **Permission enforcement — BOTH fields, BEFORE any service call**:
  - Query: `authScopes: { permission: AppPermission.ACCOUNTING_PAYROLL_VIEW }`.
  - Mutation: `authScopes: { permission: AppPermission.ACCOUNTING_PAYROLL_MANAGE }`.
  - Mechanics verified in `gqlSchemaBuilder.ts`: the `permission` scope is
    evaluated by the ScopeAuthPlugin before `resolve` runs; failure short-circuits
    into `unauthorizedError` → localized `tErrors.insufficientPermissions`
    GraphQLError, `extensions.code: "FORBIDDEN"` (UNAUTHENTICATED when not
    logged in). The service is never invoked on a denied request — AC-7.3's
    "shall not execute the underlying query" and AC-7.4's "shall not touch any
    row" hold.
  - Defense in depth: `PayrollCalculationService.getReport` /
    `applyOverride` re-check via `requirePermission` (their first statement,
    per the 1.6–1.8 outcome), protecting non-GraphQL callers (e.g. the 2-d
    CSV route) independently.
- **actorUserId provenance — authenticated context only**: both resolvers take
  the actor from `requireAuth(ctx)` → `ctx.user.id`. The GraphQL input type
  `PayrollOverrideInputPothos` has no `actorUserId` field at all (2.1's
  design), so a client cannot even attempt to spoof it; the resolver injects
  it after spreading `args.input` (key order guarantees injection wins). The
  PAYROLL_OVERRIDE audit event therefore always records the authenticated
  user's id (AC-7.5).
- **Input surface bounding**: `limit` constrained to `min: 1, max: 200` via
  the GraphQL constraint directive (validated before the resolver — mirrors
  the `users` query precedent and bounds the repo's `.limit()` since neither
  service nor repo clamps); `filter.search` capped at 200 chars by the 2.1
  input directives. Free-text `note` is sanitized downstream in the service
  (`sanitizePlainText`, ≤ 2000).
- **No impersonation gate (deliberate, follows convention)**: the mutation
  does NOT add `notImpersonating: true`. The plan's §4.3 snippet and the
  closest teachers-domain financial sibling (`markTeacherDuesPaid`) use
  permission-only authScopes; `notImpersonating` is reserved for
  billing-management/cron-style flows per the AGENTS.md scope-auth note.
  While impersonating, the override is attributed to the impersonated
  operator (ctx.user) — identical to every other teachers/billing mutation.
  Surfaced to the review gate as D16 (no action requested).
- No secrets, tokens, credentials, I/O, or network access; no module-level
  mutable state (pure field registrations); no `console.*`, no dynamic
  imports, no `oxlint-disable`.

## Deliberate deviations from implementation.md §4.3 snippets

1. **File placement `teachers/` instead of `billing/`** — the plan's §4.3
   snippet wrote `query/billing/payroll.query.ts`, but the authoritative
   trackable-tasks.md 2.3/2.4 entries (and this dispatch) specify
   `query/teachers/` + `mutation/teachers/`, matching the pothos types'
   `pothos/teachers/` placement and the teachers-domain service. Sibling
   convention followed.
2. **`limit` gained `constraint: { min: 1, max: 200 }` + description** — the
   snippet had a bare `defaultValue: 50`; neither service nor repo clamps the
   page size, so the directive bounds the surface pre-resolve (auth `users`
   query precedent: identical defaults + min 1 / max 200).
3. **Query description extended** with the aggregate-scope note (full filtered
   set, 10 000-row cap) — the 1.6–1.8 outcome's explicit carry-forward
   instruction ("document in the query description").
4. **Mutation description extended** with the actor-provenance sentence —
   matches the 2.1 input type's own description.
5. **`force: args.input.force ?? undefined` normalization** — the snippet's
   bare `{ ...args.input, actorUserId }` spread does not satisfy the
   `PayrollOverrideInput` contract, whose `force?: boolean` member excludes
   `null` while Pothos infers `boolean | null | undefined` for optional input
   fields. Null → absent is semantically identical for the service's
   `!input.force` guard.
6. **No `notImpersonating: true`** — kept the snippet's permission-only
   authScope (see security audit; D16).
7. **No try/catch error envelope** — the snippet had none either; confirmed
   against the credit-adjustment sibling that service DomainErrors propagate
   as-is (their `extensions.code`s are the contract).
