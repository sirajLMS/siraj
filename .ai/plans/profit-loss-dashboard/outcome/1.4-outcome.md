## Deviations from the Plan SQL (intentional, codebase-driven)

- **`deleted_at` lives on `invoices`, not `payments`**: the `payments` table has no `deleted_at`
  column (`backend/db/schema/billing/billing.ts`); soft-delete exclusion is applied as
  `isNull(invoices.deletedAt)` on the inner-joined invoices — same visibility intent as the plan's
  `p.deleted_at IS NULL`. Invoices RLS auto-filters soft-deleted rows for real users, but tests run
  as admin (RLS bypass), so the explicit predicate is required.
- **`payment_catalogs` → `packagePlans`**: `packageName` comes from `packagePlans.displayName`
  joined via `payments.packagePlanId` (this codebase has no `payment_catalogs` table).
- **`students.parent_id` + `parents.user_id` joins**: student name from `students.name` (repo
  idiom — the plan's `students ⋈ users` hop is unnecessary here); parent name from `users.name`
  joined via `parents.userId = users.id` (the plan's `u_p.display_name`).
- **Return type**: `Omit<ProfitLossIncomePage, "aggregate">` rather than the full page — the
  aggregate requires FX conversion (service-side, Task 1.6), so the repo cannot compose it.
- **Inner join on students** (per plan SQL `JOIN students`): payments whose invoice has no student
  are excluded; parent/package/invoice joins stay `LEFT JOIN` so `parentName`/`packageName` resolve
  nullable (covered by a dedicated test).
