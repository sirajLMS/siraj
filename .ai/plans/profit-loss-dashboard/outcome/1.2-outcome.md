## Deviations from the Plan (intentional, rule-driven)

- **Month filter as JS Date bounds instead of `to_char(...)`**: the plan SQL says
  `to_char(ci.scheduled_start_at, 'YYYY-MM') = $1`; implemented as
  `scheduled_start_at >= <first instant of month, UTC>` AND
  `scheduled_start_at < <first instant of next month, UTC>` (exclusive upper bound).
  This follows the file's established dialect-aware idiom (bound timestamps as JS
  Dates so the same SQL runs on PostgreSQL timestamptz and SQLite epoch-millis —
  see `startOfUtcDay`/`buildPayrollReportConditions`) and is index-friendly
  (`class_instances_scheduled_start_at_idx`). Filter semantics identical for the
  filters used.
- **Names join shape**: teacher name from `users.name` (via `teachers.userId`) and
  student name from `students.name`, matching the sibling `payrollReportBaseQuery`
  in the same file (the plan's `display_name` / second `users` join does not exist
  in this schema).
- **Subject join as INNER JOIN on `subject_id`**: the plan says `LEFT JOIN
  class_subjects` on `ci.class_subject_id`; the actual column is `subject_id` from
  `coreScheduleColumns` (NOT NULL, enforced FK), and the non-null
  `subjectName: string` type + sibling idiom use an inner join.
- **Count query without joins**: `totalCount` is a single-table `count(*)` over
  `class_instances` with the same filters — the conditions reference only
  `class_instances` columns and the report joins are inner joins over enforced
  NOT NULL FKs, so the unjoined count equals the joined row count. (A joined count
  would be a byte-identical 13-line clone of `findPayrollReportRows`'s count query,
  flagged by intra-file jscpd.)
- **`calculation_status IN (...)` values as the `CalculationStatus` enum**: the
  plan SQL's string literals map to `CalculationStatus.CALCULATED / PARTIALLY /
  REFUND / WAITING_PAID / PAID` (rule: no string literals where enum types expected).
