## Summary

Created the two P&L grid chips. No pre-existing importable chip matched either need, so
both are local variants that **delegate rendering/color to existing shared primitives**:

- **Reuse search findings**:
  - CalculationStatus: no standalone payroll chip exists — Plan 3's payroll grid
    (`PayrollReportsDataGrid.tsx`) renders inline `<StatusBadge category="payrollCalculation">`
    with a `buildStatusLabels` bridge from the `dashboard.billing.payroll` locale. There IS
    a `SessionAuditStatusChip`, but it keys on `SessionAuditStatus` (a different enum) — not reusable.
  - PaymentMethod: `PaymentMethodDisplay` is a full card display (multiple slots, phone/country/
    currency displays) — not a small chip. `PaymentsLedgerView` renders method as a title-cased
    raw string, not a chip. No chip to reuse.
- **`CalculationStatusChip.tsx`**: thin wrapper over the shared
  `StatusBadge` (`category="payrollCalculation"`) — identical colors to the payroll grid
  (REFUND error, CALCULATED info, PARTIALLY warning, WAITING_PAID secondary, PAID success),
  resolved via `theme.palette.status` inside `statusBadgeShared.utils`. Bridges the payroll
  locale's literal keys (`NOT_CALCULATED` … `PAID`) onto the generated enum, same as
  `usePayrollReportsViewModel.ts`'s `buildStatusLabels`.
- **`PaymentMethodChip.tsx`**: small MUI v9 `Chip` with per-type semantic
  `theme.palette.status.*Container` / `on*Container` pairs (active/confirmed/pending/completed),
  colors via a `Record<PaymentMethodType, (theme) => colors>` table (no string-keyed palette
  indexing — a template-literal palette key failed tsgo TS7053 on the theme's intersection type).

## Enum import deviation (important carry-forward)

The task text says "value imports from `@/backend/enum`", but `backend/enum/index.ts` is
**backend-only** — its own header comment says frontend MUST use the GraphQL codegen enums
from `@/frontend/common/graphql/generated/gql/graphql` instead. Both chips import value
enums from there (`CalculationStatus`, `PaymentMethodType` — same string values as the
backend enums, PascalCase member names, e.g. `CalculationStatus.Paid`, `PaymentMethodType.Cash`).
This matches every other frontend consumer (payroll grid, `payment-method.ts` lib).

## Label sources (i18n)

- `CalculationStatusChip` reuses `dashboard.billing.payroll` status labels via
  `useAppTranslation(DashboardBillingPayroll)` — no new keys needed and the labels stay
  consistent with the payroll grid. The `dashboard.accounting.profitLoss` namespace has NO
  per-status keys in its `ProfitLossLabels` schema, and Phase 7's i18n task is only a
  *confirmation* pass — the plan never specified new status keys.
- `PaymentMethodChip` reuses the shared `ui.paymentMethod` type catalog via
  `useAppTranslation(Translation.Ui.PaymentMethod)` (`.type.mobileWallet` … `.type.proofUpload`),
  so method names stay consistent with the rest of the billing UI. Note: the
  `dashboard.accounting.profitLoss` namespace's `column.paymentMethod` is a *column header*,
  not per-value labels.

## Accessibility

- `CalculationStatusChip` — visible text IS the full localized status; `StatusBadge` renders
  it inside an accessible Box/Typography (no `aria-label` prop is accepted by
  `StatusBadge`/`StatusBadgeShared` — same accessibility as the payroll grid, which is the
  established pattern).
- `PaymentMethodChip` — MUI `Chip` with explicit `aria-label={label}` carrying the full
  localized method text, satisfying the plan's Phase 7 "status chips have aria-label with
  full text" requirement.
