## FX Service Integration (carry-forward for 1.7)

The plan's `FxService.getLatestRate(from, to)` does not exist. The actual soft-read path
used by the sibling services (`carryover-balance.service.ts`, `fx-display.service.ts`) is:

- `BillingRepository.getLatestExchangeRateForDisplay(from, to)` from
  `@/backend/db/repo/billing` (`backend/db/repo/billing/billing.repository.ts:189`) →
  `Promise<{ rate: string | null; stale: boolean }>`.

`convertCurrency` treats **missing OR stale** as "FX rate missing" (returns `null`), the
same policy as `FxDisplayService.convertForDisplay` for UI/display conversion; financial
insert paths (`getLatestExchangeRate`) throw instead and were not used — the dashboard is
read-only. Per-row conversion multiplies decimal strings (`Number.parseFloat(amount) *
Number.parseFloat(rate)`, `.toFixed(2)`), matching `fx-display.service.ts`'s
`multiplyAmountByRate`; unparseable values render as `"0"` (same sibling precedent).
Same-currency amounts normalize to two decimals without a rate lookup, mirroring
`convertForDisplay`'s identity branch.

## Deviations from the Plan (intentional, rule-driven)

- **`tErrors` type is `ProfitLossLabels`, not `ErrorsLabels`** — the plan's §3.2 typed the
  bundle as `ErrorsLabels`, but the month-invalid message lives in the
  `dashboard.accounting.profitLoss` namespace (`ProfitLossLabels.error.monthInvalid`,
  created by Task 3.3), which `ErrorsLabels` does not carry. Following the sibling
  helpers' convention (`expense-helpers.ts`: passed-in typed bundle, message picked from
  it), `validateMonth` takes `ProfitLossLabels` and throws
  `DomainError("MONTH_INVALID", tErrors.error.monthInvalid)`.
  **Carry-forward for 1.7**: `getReport` must supply the profitLoss labels bundle — e.g.
  `getServerTranslations(locale).dashboardTranslations.accountingProfitLoss` — not the
  `ErrorsTranslations` bundle, when calling `validateMonth`.
- **Net Profit formula**: the orchestrator brief in this task described
  "income + payments − expenses", but implementation.md §3.6 and specs.md (AC-6.1, E6, and
  the summary-table definition) all define **Net Profit = Total Payments − Total
  Expenses**; implemented per the plan's exact formula (income appears in the summary as
  its own row, not inside net profit).
- **`aggregateWithFx` sum is a two-decimal string** — the plan's §3.3 assigns `sum`
  directly into the string-typed `aggregate.totalPayments`/`totalExpenses`/
  `totalIncomePayments` fields, so the helper returns `sum` already formatted.
- **Dominant currency**: most frequent source currency among *included* rows (excluded
  rows do not vote); ties resolve to the currency that reached the leading count first;
  empty included set falls back to `CurrencyCode.SAR` (mirrors the
  `carryover-aggregate.ts` / `expense-helpers.ts` fallback).
- **`collectFxWarnings` signature**: takes one group of projected rows per tab (the plan's
  §3.2 call passes the three `rows` arrays); the projection
  `{ originalCurrency, convertedAmount }` is needed because the three tabs name their
  currency fields differently (`studentPaidCurrency` / `expenseCurrency` / `currency`).
  Grouping by original currency equals grouping by currency pair since `targetCurrency`
  is constant per call.
- **`aggregateWithFx` runs conversions via `Promise.all`** (not the sequential walk in
  implementation.md §3.7) — the repo's `no-await-in-loop` oxlint rule requires parallel
  conversion; matches §3.3's own `Promise.all(rows.map(...))` precedent. Results are
  order-preserved so the sum and counts are unaffected.
