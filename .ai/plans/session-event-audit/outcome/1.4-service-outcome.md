## Public contract (for the GraphQL query + CSV export route agents)

```ts
import { SessionAuditService } from "@/backend/services"; // or "@/backend/services/accounting"
import type { SessionAuditReportFilters, SessionAuditReportPage, SessionAuditReportSort } from "@/backend/types";
import type { ErrorsLabels } from "@/shared/locale";

SessionAuditService.getReport(
  actorUserId: string,                                  // authenticated actor (service re-checks the permission)
  filters: SessionAuditReportFilters,                 // pass `{}` for unfiltered
  sort: SessionAuditReportSort | null | undefined,    // null/undefined → { field: "scheduledStartAt", direction: "desc" }
  pagination: { limit: number; offset: number },      // repo clamps limit ≥ 1, offset ≥ 0
  tErrors: ErrorsLabels,                              // resolver: ctx.t().errorsTranslations; route: getServerTranslations(locale).errorsTranslations
): Promise<SessionAuditReportPage>
```

### Error classes thrown (exact)

| Condition | Class | `extensions.code` | Message |
|---|---|---|---|
| Actor lacks `ACCOUNTING_REPORTS_VIEW` | `ForbiddenError` (`@/backend/lib`), thrown by the shared `requirePermission` (`@/backend/services/billing/permission-utils`) | `"FORBIDDEN"` | `tErrors.insufficientPermissions` |
| `dateFrom > dateTo` (both bounds present, ISO-string compare) | `ValidationError` (`@/backend/lib`) | `"INVALID_DATE_RANGE"` | `tErrors.invalidInput` |

**Naming note:** the trackable-tasks bullet says permission denial throws
`InsufficientPermissions`. No such error class exists in the codebase — the
canonical class for an authenticated caller missing a permission is
`ForbiddenError` (code `FORBIDDEN`), which is exactly what the shared
`requirePermission` throws and what Pothos `authScopes: { permission }`
produces for the same denial. Tests assert `instanceof ForbiddenError` +
`code === "FORBIDDEN"`. Downstream deviates-from-plan documentation lives
only here; consumers must match on `FORBIDDEN`.

**Localized-message note:** `ErrorsLabels` has no date-range-specific key
(only the unrelated `scheduling.dateRangeExceedsMax` and generic
`invalidInput` / `scheduling.startTimeBeforeEndTime`). The validation error
therefore carries the generic `tErrors.invalidInput` message with the precise
`INVALID_DATE_RANGE` code; the user-facing picker-level copy comes from the
`dashboard.reports.sessionAudit` namespace (`error.dateRangeInvalid`,
unchanged, frontend-owned). No shared-locale file was touched — adding a
dedicated errors key would have been a cross-layer edit outside this slice.

## Behavior notes downstream agents must know

- **Sort defaulting**: the service owns the default (`scheduledStartAt` desc);
  the repository contract (1.3) requires a sort, so pass the caller's value
  through — never build one at the resolver and never drop the sort arg.
- **Last-page clamp lives here**: when `offset >= totalCount` (and
  `totalCount > 0`), the service re-issues the read at
  `floor((totalCount - 1) / limit) * limit` and returns that page with the
  original `totalCount`. Tests assert the second call's exact offset.
- **Aggregates are page-level** (over the returned rows, not the full filtered
  set — `totalCount` carries the full size): `rowCountByStatus` always exposes
  all four keys; `rowCountByPaid` splits on
  `calculationStatus === CalculationStatus.PAID`; `totalPaidAmount` sums every
  non-null `teacherPaidAmount` via exact hundredth-unit bigint math (no
  floats) back to a two-decimal string; `totalPaidCurrency` is the currency
  carried by the most rows (ties → first-seen; no currencies/empty page →
  `CurrencyCode.SAR`) per the mixed-currency risk rule in the implementation
  doc. Malformed decimal strings are excluded from the sum rather than zeroed.
- **Graceful degradation**: null payroll columns pass through untouched; the
  aggregates treat them as unpaid with zero amount.
- **NFR-11 structured logging**: `logger.info("Session audit report query", {
  actorUserId, filters, limit, offset, rowCount })` fires on every successful
  query (after clamping). This pre-fulfills trackable-tasks 6.1 — that task
  only needs to confirm, not edit. (The export route should add its own
  logger.info with the export context; the service log already covers the
  actual report read the export performs.)

## Deliberate deviations / notes

1. **`ForbiddenError`, not `InsufficientPermissions`** — see table above.
2. **Money helpers re-implemented locally** (differently-shaped minor-unit
   parse/format) instead of extracting the payroll service's private
   `parseAmountToMinorUnits`/`formatMinorUnits`/`pickDominantCurrency`:
   extraction would edit `backend/services/teacher/payroll-calculation.service.ts`,
   which is outside this slice's scope. If the cross-file jscpd gate flags the
   pair later, the sanctioned fix is a shared money-math module (e.g.
   `backend/services/billing/__shared__/decimalAmount.ts`) consumed by both —
   flagged here as a follow-up, not done unilaterally.
3. **Validation order**: permission check runs before date validation (denied
   callers learn nothing about filter validity).
4. The service does **not** normalize/clamp `limit`/`offset` itself (the
   repository already does that per 1.3); the clamp math re-derives the
   normalized limit locally to compute the last-page offset.
5. No batch/DataLoader method added: this is a top-level report query, not a
   per-parent field resolver, so the batch-method rule does not apply.
