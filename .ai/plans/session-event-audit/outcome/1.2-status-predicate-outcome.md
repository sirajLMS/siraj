## Exported API (contract for the repository agent, task 1.3)

```ts
// Barrel path: @/backend/services  (or deep: @/backend/services/accounting)
import { expandStatusesToSql } from "@/backend/services";

export function expandStatusesToSql(statuses: readonly string[]): SQL;
```

Returns a Drizzle `SQL` fragment (from `drizzle-orm`) that references the
`classInstances` columns (`executionState`, `outcome`, `actualStartAt`) and can
be embedded directly inside `.where(and(...))`. Repository agent combines it
with the other filters via drizzle combinators, e.g.:

```ts
const where = and(
  isNull(classInstances.deletedAt),
  // …other filters…
  expandStatusesToSql(filters.currentStatuses ?? []),
);
```

**Verified composition behavior:** drizzle's `and()` parenthesizes each operand,
so the returned multi-status fragment (`(a) OR (b)`) nests safely inside an
AND-chain — checked live via `PgDialect.sqlToQuery`.

### Semantics per status value

| Status | Rendered predicate |
|---|---|
| `open` | `NOT (execution_state = 'COMPLETED' AND outcome IN ('TAKEN','ABSENT','LEAVE'))` — complement of the terminal set, matching `mapToSessionAuditStatus`'s catch-all (covers NOT_ACTIVATED, RUNNING, ACTIVATED, ON_DEMAND_*, and unmatched combos) |
| `end` | `execution_state = 'COMPLETED' AND outcome = 'TAKEN'` |
| `Absent` | `execution_state = 'COMPLETED' AND outcome = 'ABSENT' AND actual_start_at IS NULL` |
| `absent_student` | `execution_state = 'COMPLETED' AND (outcome = 'LEAVE' OR (outcome = 'ABSENT' AND actual_start_at IS NOT NULL))` |

### Edge behaviors (all tested)

- `[]` (empty list) → literal `true` fragment (no filtering). Note: drizzle-orm
  1.0.0-rc.4 has **no** `sql.true` helper, so the literal is `sql`true`` — same
  semantic the task description names.
- Duplicates collapse (`["end","end"]` ≡ `["end"]`).
- Each expanded status is wrapped in parentheses and joined with ` OR `.
- Enum values are parameterized (`$1, $2, …`), never inlined — no injection
  surface.
- All `IN` lists use drizzle's array expansion inside an `sql` template.

### Deliberate deviation from the implementation.md sketch — input is `readonly string[]`, consumed via `STATUS_TO_PREDICATE_KEY`

`implementation.md` §3.4 (and the 0.2 outcome) sketch this helper as
`statuses: readonly SessionAuditStatus[]`. The parameter is typed as
`readonly string[]` instead, for two reasons:

1. The values arrive from untrusted boundaries (GraphQL filter input, URL
   query params for the CSV export route). Signature-level narrow typing does
   not exist at runtime; a defensive path was required either way.
2. The project's oxlint `no-unsafe-type-assertion` rule (see
   `docs/quality/linting-rules.md` — stricter than ESLint; `as unknown as`
   does not bypass it, and the repo contains zero `as-unknown-as` and zero
   `@ts-expect-error` occurrences) makes it impossible for a test to construct
   an out-of-union input through a `readonly SessionAuditStatus[]` parameter
   without a banned narrowing assertion. The `string[]` boundary + literal
   comparison (`STATUS_TO_PREDICATE_KEY[status] === candidate`) exercises the
   fallback with zero casts.

Unknown strings (e.g. legacy `CANCELLED`/`RESCHEDULED` concepts from specs
AC-2.8, which do not exist as `ClassOutcome` enum values) resolve to the
**open** predicate — mirroring `mapToSessionAuditStatus`'s catch-all, exactly
as the 0.2 outcome prescribed.

`STATUS_TO_PREDICATE_KEY` (from `@/shared/constants/classes/session-audit-status`)
is genuinely consumed: it is the membership/identity registry `toPredicateKey`
uses to validate raw strings before they reach the fragment table.
