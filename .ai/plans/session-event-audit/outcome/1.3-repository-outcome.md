## Contract for the service agent (Task 1.4)

```ts
import { SessionAuditRepository } from "@/backend/db/repo/scheduling"; // or "@/backend/db/repo"

await SessionAuditRepository.findReportRows(
  filters,    // SessionAuditReportFilters (from @/backend/types)
  sort,       // SessionAuditReportSort — REQUIRED, the service supplies the default
  pagination, // { limit: number; offset: number }
  tx?,        // optional DBTransaction
): Promise<{ rows: SessionAuditReportRow[]; totalCount: number }>
```

- **Accepted sort fields** (`SessionAuditReportSortField`, all tested asc + desc):
  `scheduledStartAt`, `scheduledEndAt`, `actualStartAt`, `actualEndAt`,
  `durationMinutes`, `calculatedDuration`, `teacherPaidAmount`,
  `calculationStatus`, `teacherName`, `studentName`.
- `teacherPaidAmount` sorts numerically (the column is decimal-as-text — the
  ORDER BY goes through `CAST(... AS NUMERIC)`) with `NULLS FIRST` for `asc`
  and `NULLS LAST` for `desc`, then `class_instances.id` as a stable
  tiebreaker for every sort.
- **Pagination**: `limit` is clamped to ≥ 1 and `offset` to ≥ 0. The
  repository does **not** clamp the offset to the last page — an offset past
  the end returns `[]` with the full `totalCount`, and the service layer owns
  the last-page clamp (trackable-tasks 1.4).
- **Filters**: `teacherId`, `studentId`, inclusive `dateFrom`/`dateTo` on
  `scheduled_start_at` (UTC day bounds, same helper shape as the payroll
  report), `currentStatuses` (OR-expanded via `expandStatusesToSql`; `[]` /
  `null` = no filtering), `search`, `includeDeleted` (soft-deleted rows are
  excluded unless `=== true`).
- **Search semantics**: the term is split on whitespace; every token must
  match (AND across tokens) either the teacher's `users.name` or the
  student's `students.name` (OR within a token), case-insensitive, with LIKE
  wildcards escaped via `escapeLikeWildcards`. This makes multi-word phrases
  like "smith algebra" match a teacher named Smith teaching a student named
  Algebra.
- `currentStatus` on each row is computed in TypeScript via
  `mapToSessionAuditStatus` (never in SQL), so the row value and the
  `currentStatuses` filter predicate share the same rule by construction
  (verified live: `["Absent"]` returns exactly the COMPLETED+ABSENT+no-join
  row, etc.).
- `teacherDuePaymentDate` = `teacher_payments.payment_date` via LEFT JOINs
  `teacher_dues` → `teacher_payments`, populated **only** when
  `calculation_status = 'PAID'` (gated in the row mapper, not the SQL — a due
  linked to a payment on a non-PAID row still yields `null`; tested).
  `teacher_dues.class_instance_id` is unique, so the LEFT JOINs never fan out.
- Exactly **2 statements per call**: one joined SELECT and one COUNT (the
  COUNT keeps the inner joins because the search filter references the joined
  name columns; it drops the LEFT JOINs). Asserted by a `Proxy`-based
  select-counter test — there was no pre-existing query-count helper in
  `backend/db/test`, so the test carries its own 10-line wrapper.

## Deliberate deviations from the plan docs

1. **Student name source**: the wave instructions and implementation.md §3.4
   sketch show `students + users` INNER JOINs for the student name, but the
   landed schema keeps the student display name on `students.name`
   (NOT NULL), and the already-landed payroll report
   (`findPayrollReportRows` in `class-instances.ts`) joins `students` only.
   The repository follows the payroll report exactly (teacher name via
   `teachers → users`, student name via `students.name`) so both accounting
   grids render the same names and search semantics.
2. **`expandStatusesToSql` import path**: imported from the deep module
   `@/backend/services/accounting/session-audit-status-predicate` rather than
   the `@/backend/services` barrel, to eliminate any barrel-level import
   cycle once Task 1.4's service (which imports this repository) joins the
   accounting barrel. Deep service-module imports from this directory are an
   established pattern (`class-instances.ts` imports
   `@/backend/services/scheduling/availability.service`).
3. **Enum columns**: `execution_state` / `outcome` columns infer as plain
   `string` (the dialect-aware enum builder is untyped); the row mapper
   normalizes them through the canonical `parseClassExecutionState` /
   `parseClassOutcome` helpers from `@/shared/lib/enum` instead of asserting
   (zero `as` casts, per the `no-unsafe-type-assertion` rule).
