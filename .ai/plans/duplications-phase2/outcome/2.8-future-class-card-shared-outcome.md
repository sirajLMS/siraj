## Key Design Decisions

### Render Function for ClassProfileLink (vs ComponentType)
Used a render function `(props: { href, name, avatarUrl }) => React.ReactNode` instead of `React.ComponentType<P>` for the `ClassProfileLink` slot. This avoids TypeScript contravariance issues:
- Desktop's `DesktopClassProfileLinkProps.typographyVariant` is `UiTypographyVariant` (narrow, strict MUI variants)
- Mobile's `MobileClassProfileLinkProps.typographyVariant` is `UiTypographyVariantLoose` (wide, admits custom strings)
- A shared `ComponentType<{ typographyVariant: string }>` can't accept both because `string` is not assignable to `UiTypographyVariant`
- The render function approach lets each tier's wrapper hardcode its own `typographyVariant` and `fontWeight` values, with the scaffold only passing `href`, `name`, and `avatarUrl`

### Scaffold Location: `common/views/` (not `common/components/ui/`)
These are view-level composed cards (not UI primitives), so the scaffold belongs in `frontend/common/views/dashboard/teachers/futureSchedule/` following the pattern established by `adminInvoiceCardShared.tsx`.

### Direct Module Path Imports
All imports use direct file paths (no barrel `index.ts` re-exports) to prevent circular dependency TDZ errors identified in Phase 1.
