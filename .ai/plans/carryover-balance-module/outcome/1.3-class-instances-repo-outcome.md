# Task 1.3 Outcome — Class-Instance Repo Carryover Extensions

- **Date**: 2026-09-05
- **Status**: ✅ Complete

## What was implemented

Four new data-access methods appended to `backend/db/repo/scheduling/class-instances.ts`
in a new "Carryover linking" section (after `updatePayrollCalculation`, before the
payroll-report helpers). No existing methods were changed.

- `getByIdsForUpdate(ids: readonly string[], tx: DBTransaction)` — batch
  `SELECT ... FOR UPDATE` via the existing dialect-aware `withForUpdate` helper
  (no-op on SQLite). `tx` is a **required** parameter: the row lock only exists
  inside the caller's transaction, so a bare read would feign mutual exclusion
  (same rationale as `getById(..., { forUpdate: true })`'s runtime guard, here
  enforced by the type system). Unknown ids are omitted; callers compare counts.
  Empty input returns `[]` without issuing a query.
- `findByCarryoverId(carryoverId: string, tx?)` — returns all instances whose
  `carryoverBalanceId` matches, via `queryDb(tx)` for non-transactional read
  support per the repo-layer Neon HTTP rule.
- `linkToCarryover(instanceIds, carryoverId, tx)` — batch update setting
  `carryoverBalanceId` + refreshing `updatedAt`, `.returning()` the rows.
  Validation (audited state, not already linked) stays in the service layer.
- `unlinkFromCarryover(instanceIds, tx)` — batch update nulling
  `carryoverBalanceId` (+ `updatedAt`), `.returning()` the rows. Restoring the
  pre-link `calculationStatus` from item snapshots stays with the service.

All four surface automatically through `SchedulingRepository`
(`backend/db/repo/scheduling/index.ts` already spreads `* as ClassInstances` —
no barrel change needed).

## Adaptations / decisions

- **Plan name `ClassInstanceRepository` → `SchedulingRepository`**: no
  `ClassInstanceRepository` export exists; the codebase's canonical consumer
  surface for this file is `SchedulingRepository` (namespace spread). Service
  pseudocode in implementation.md §3 should call
  `SchedulingRepository.getByIdsForUpdate(...)` / `findByCarryoverId(...)`.
- **Test placement**: new focused file rather than appending to
  `payroll-report.repository.test.ts` — carryover linking is a distinct surface
  from payroll reads, and the existing layout favors one file per concern.
- **Sequential fixture inserts**: `Promise.all` against a single rollback-tx
  connection works but trips node-postgres' deprecated queued-query path
  (deprecation warning observed in the first green run); the setup helper uses
  sequential unrolled inserts instead (`instanceCount: 1 | 2 | 3`).

## Carry-forward knowledge

- Consumers use `SchedulingRepository.getByIdsForUpdate`, not the plan's
  fictional `ClassInstanceRepository` namespace.
- `linkToCarryover`/`unlinkFromCarryover` deliberately do NOT touch
  `calculationStatus` — status transitions + `ClassStatusEventRepository`
  events are service-layer (implementation.md §3.2 writes `WAITING_PAID`
  inline; §3.5 restores from `carryover_balance_items.originalStatus`).
- `getByIdsForUpdate` returns rows unordered; services grouping by teacher
  must not rely on input order (aggregate helpers already handle grouping).
- Rollback transactions pin one connection: avoid `Promise.all` over repo
  calls sharing one `tx` (pg queued-query deprecation; keep sequential).
