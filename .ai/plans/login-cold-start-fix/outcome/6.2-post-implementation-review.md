### [MEDIUM] `SHORT_CACHE_TTL_MS` was dead code — transient DB failure throttling not applied
**File:** `backend/services/system/environment-config.service.ts`
**Issue:** The `SHORT_CACHE_TTL_MS = 30_000` and `resolveTtl()` were introduced to throttle re-queries during transient DB outages. However, transient DB failures wrote `source: "env"` cache entries, and both `resolveEnvConfig` and `serveFromCache` only short-circuited on `source === "db"` — `"env"` entries always fell through to a fresh DB lookup. The 30s TTL had zero effect.

**Fix applied:**
1. Added `transientError: boolean` flag to `CacheEntry` interface
2. Updated `commitDbResolvedValue()` to accept and pass `transientError` parameter
3. Updated single-key cache hit check: short-circuit on `source === "db"` OR (`source === "env"` AND `transientError`)
4. Updated batch `serveFromCache()` with the same condition
5. Updated `recordResolvedKey()` to accept `transientError` parameter
6. All call sites pass `dbError ? wasTransient : false`

**Result:** Transient DB failures now throttle re-queries for 30s (short TTL), preventing thundering-herd against a failing DB. Non-transient `"env"` entries (pre-warmed, permanent failures) still always fall through to re-query DB. After the short TTL expires, the DB is re-queried — if it has recovered, the DB override is picked up.
