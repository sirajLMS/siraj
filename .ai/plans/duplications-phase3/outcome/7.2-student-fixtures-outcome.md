## Design Decisions

### Factory functions instead of static exports
Static exported fixture objects would need cloning. Factory functions (`createProfileMockData`, `createTwoSessionHistoryMockData`, `createSingleSessionHistoryMockData`) allow per-test customization via `overrides`:
- **Profile test** uses `createProfileMockData(studentId, { dateOfBirth: "...", gender: "MALE", ... })` to override default nulls
- **History container/sessions** use `createTwoSessionHistoryMockData()` (defaults)
- **History mobile** uses `createSingleSessionHistoryMockData()` (defaults — includes session-1 only, with `totalClasses: 2, hoursStudied: 2`)

### Per-test `studentId` differences
Each test uses a different template student ID:
- `studentHistoryContainer`: `"student-history-1"`
- `studentHistoryMobile`: `"student-history-mobile-1"`
- `studentSessionsContainer`: `"student-sessions-1"`
- `studentProfileContainer`: `"student-profile-1"`

The fixture is parametrized on `studentId`, so all tests pass a local value.

### Two history variants
The history container/sessions tests share metrics `totalClasses: 3, hoursStudied: 4.5` with 2 sessions. The mobile test uses `totalClasses: 2, hoursStudied: 2` with 1 session. Rather than use an overrides-heavy single factory, I created two purpose-built factories: `createTwoSessionHistoryMockData()` and `createSingleSessionHistoryMockData()`. This makes each test's intent clear and avoids accidental override mismatches.

### Session-1 field variation
The history container and sessions tests' session-1 has two extra fields populated compared to the mobile test: `notes: "Strong progress"` and `meetingJoinUrl: "https://meet.example.com/session-1"`. The mobile version uses `notes: null, meetingJoinUrl: null`. The two-session factory encapsulates this variation so callers don't need to repeat it.
