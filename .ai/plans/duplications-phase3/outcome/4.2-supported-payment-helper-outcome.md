## Approach

### Helper Design (`supportedPaymentMethodBase.ts`)

**Design §8.2 Adaptation:** The design specified a single `supportedPaymentMethodBase(tableName)` function returning `{ id, paymentMethodId, region, active, createdAt, updatedAt }`. However, the actual 3 supported-* tables (`supported_mobile_wallets`, `supported_payment_links`, `supported_online_accounts`) share a different and larger column set — and critically, each table inserts **domain-specific columns in the middle** of the shared envelope (between `instructions` and `supportedDirections`). A single spread object would either:
1. Force all domain-specific columns to the end (changing column order → reordering migration), or
2. Require splitting the base into two parts.

**Chosen approach: head/tail split** — preserves exact column order with domain-specific columns in the middle:

```ts
pgTable("my_table", {
  ...supportedPaymentMethodBaseHead(),   // id, slug, name, description, instructions
  // domain-specific columns
  ...supportedPaymentMethodBaseTail(),  // supportedDirections, logoUrl, isActive, createdAt, updatedAt
}, (t) => [ ...indexes... ]);
```

This mirrors the Task 4.1 pattern of adapting the design to actual schema reality while preserving the elimination goal.

## Design Deviations

The design §8.2 specified:
```typescript
function supportedPaymentMethodBase(tableName: string) {
  return {
    id: uuid("id").defaultRandom().primaryKey(),
    paymentMethodId: uuid("payment_method_id").notNull(),
    region: text("region").notNull(),
    active: boolean("active").default(true).notNull(),
    createdAt: timestamp("created_at").defaultNow().notNull(),
    updatedAt: timestamp("updated_at").$onUpdate(() => new Date()).notNull(),
  };
}
```

**Actual schema does NOT match this simplified form:**
1. The 3 real tables are `supported_mobile_wallets`, `supported_payment_links`, `supported_online_accounts` — not `supported-payment-method.ts`, `supported-payment-method-file.ts`, `supported-payout-method.ts` (those files don't exist)
2. There is no `paymentMethodId` or `region` column — instead there's `slug`, `name`, `description`, `instructions`, `supportedDirections`, `logoUrl`, `isActive`
3. `active` is actually `isActive: boolean("is_active")` with `{ withTimezone: true, precision: 3 }` timestamps
4. `updatedAt` does NOT use `.$onUpdate()` — it's a plain `.notNull()` timestamp
5. Domain-specific columns go in the **middle** of the shared envelope, requiring head/tail split (not a single function)

**Adapted implementation:** Two-function head/tail pattern that preserves the design intent (eliminate duplication) while matching the actual schema structure exactly. No `tableName` parameter needed (no unique constraint names use the table name as a prefix).
