## Design Decisions

### Two-tier export pattern

The shared file exports **both**:
1. **`ProfilePageServer`** — the full flow (auth → resolve → render). Used by 3 of 4 route files where no intermediate logic is needed.
2. **`renderProfilePageClient`** — the render-only helper. Used by `profile/edit/page.tsx` which must inspect the resolution between resolve and render (for the teacher forceComplete redirect logic).

This avoids forcing the self-edit page to duplicate the enum-bridge conversion and ProfilePageClient rendering, while still allowing it to branch on `resolution.scope` and `resolution.audience` before rendering.

### `generateMetadata` stays in route files

Each route file retains its own `generateMetadata` function because:
- Self-view uses `t.pageTitle`; self-edit uses `t.editTitle`
- `[id]`-view uses `${userName} — ${t.pageTitle}`; `[id]`-edit uses `${userName} — ${t.editTitle}`
- `[id]` routes call `getUserPageTitle(id)` which requires the `params` prop
- These differences make metadata generation route-specific and not suitable for sharing

### Return value consistency

The shared `ProfilePageServer` returns `null` on auth failure (matching the original self-view) and `undefined` on redirect (matching all other routes). This preserves the original behavior of each route file exactly:
- Self-view originally returned `null` on auth failure → `ProfilePageServer` returns `null`
- All other routes returned `undefined` on auth failure → they still do (the shared component returns `null` which is equivalent for rendering purposes)
