## Helper API

```typescript
// backend/graphql/utils/pagination-utils.ts

/**
 * Parse a GraphQL pagination input into a runtime PaginationArgs.
 * Returns null when input is null/undefined.
 * Wraps PaginationArgs.fromArgs() from @/backend/types.
 */
export function parsePaginationArgs(
  input: PaginationInput | null | undefined
): PaginationArgs | null;

/**
 * Build the GraphQL PageInfo response from a result page.
 * Wraps PaginationUtils.buildPageInfoFromArgs() from @/backend/utils.
 */
export function buildPageInfo(
  args: PaginationArgs | null | undefined,
  count: number,
  total: number
): PageInfo;
```

## Design Deviations

1. **`toPaginationArgs` not exported separately**: The design mentioned `toPaginationArgs` as a separate export, but since it does exactly the same thing as `parsePaginationArgs` (both wrap `PaginationArgs.fromArgs()`), only `parsePaginationArgs` is exported. The `schedule.query.ts` local `toPaginationArgs` was replaced with `parsePaginationArgs` directly.

2. **`buildPageInfo` included but unused by consumers**: The helper exports `buildPageInfo()` for completeness, but no current consumer files use it yet. Existing resolvers that build page info do so via service-layer methods that already use `PaginationUtils.buildPageInfoFromArgs()`.

3. **`quota.query.ts` was an unplanned consumer**: This file used `PaginationArgs.fromArgs()` directly (not an inline block or local function), but was updated for consistency with the canonical helper pattern.

4. **`lesson-report.query.ts` keeps `PaginationArgs` value import**: Legitimately needs `new PaginationArgs()` as a fallback when `parsePaginationArgs()` returns null (service methods require non-null `PaginationArgs`).
