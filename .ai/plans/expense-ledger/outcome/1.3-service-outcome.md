### `expense.service.ts` — `ExpenseService` namespace

Extract signature surface (all return `Promise<ExpenseRow>` unless noted):

```ts
create(input: CreateExpenseInput, actorUserId: string, tErrors: ErrorsLabels)
createInternal(input: CreateExpenseInput, tx: DBTransaction, tErrors: ErrorsLabels)
update(input: UpdateExpenseInput, tErrors: ErrorsLabels)
softDelete(input: SoftDeleteExpenseInput, tErrors: ErrorsLabels) // { id, actorUserId, reason?, tx? }
bulkDelete(input: BulkDeleteExpensesInput, tErrors): Promise<BulkDeleteExpensesResult> // { deleted, auditLogIds }
getById(actorUserId: string, id: string, tErrors)
getReport(actorUserId: string, filters: ExpenseFilters, pagination: { limit; offset }, tErrors): Promise<ExpensePage>
```

Design decisions relative to implementation.md (red ones are deviations, all intentional):

- **Repository delegation.** The plan's snippets write raw drizzle in the service; the
  implementation uses `ExpenseRepository.create/getById/getByIdForUpdate/update/softDelete/
  findFiltered` from Task 1.2 — write paths never leave data access in the service.
- **`create` creator attribution.** `createdByUserId` in the persisted row is forced to the
  `actorUserId` argument (`createInternal({ ...input, createdByUserId: actorUserId }, …)`) —
  server-derived, never client-supplied. The public `create` also rejects
  `ExpenseType.SALARIES` with `EXPENSE_SALARIES_VIA_CARRYOVER_ONLY` (correct spelling per §4.1
  note; the task-list's `CARRYVER` is a typo) **before** validation/writes, throwing the
  localized `expenses.salariesViaCarryoverOnly` message.
- **Permission model.** `create`/`update`/`bulkDelete` require `ACCOUNTING_EXPENSES_MANAGE`;
  `getById`/`getReport` require `ACCOUNTING_EXPENSES_VIEW` (via `requirePermission`).
  `createInternal` never checks permissions (caller owns it). `softDelete` checks the
  permission only when no caller `tx` is provided — the caller-tx path is the
  settlement/Plan-5 seam where the caller already owns permission and the transaction.
- **Soft-delete idempotency (AC-6.2).** Re-deleting an already-deleted row returns the current
  row without a second write or audit entry. Settlement guard (AC-3.5): a row with
  `sourceEntity = 'carryover_balances'` + `sourceEntityId` whose carryover (locked via
  `CarryoverBalanceRepository.getByIdsForUpdate` in the same tx) is still paid rejects with
  `EXPENSE_DELETE_VIA_UNPAY`; unpaid carryovers delete normally.
- **`bulkDelete` atomicity.** Opens one tx, applies `softDeleteInTx` per id sequentially
  (reduce-chain, lint-clean), any rejection rolls the whole batch back. Returns
  `{ deleted, auditLogIds }` (`BulkDeleteExpensesResult` added to
  `backend/types/billing/expense.types.ts`).
- **Audit.** One `audit_logs` row per mutation via `AuditService.createManyAuditLogs` —
  `EXPENSE_CREATE` (metadata: idempotencyKey + type/value/currency/sourceEntity/sourceEntityId),
  `EXPENSE_UPDATE` (metadata: `previousValues` via `pickChanged` + applied patch as
  `newValues`), `EXPENSE_DELETE` (metadata: sanitized reason). Entity type `EXPENSE`. Both were
  added (additive-only) to `backend/types/audit/audit.types.ts` (`AuditAction`,
  `AuditEntityType`, and both value const arrays) — same precedent as the carryover wave.
- **Structured logging** (`logger.info`) on create / update / softDelete / bulkDelete;
  `logger.error` before `EXPENSE_CREATE_FAILED`; `logger.info` on idempotent replay.
- **Validation errors.** `ValidationError` for title/value/currency (per plan-review R2);
  `DomainError` codes for the rest: `PAYMENT_DATE_INVALID`, `EXPENSE_DATE_INVALID`,
  `EXPENSE_NOT_FOUND` (unknown AND malformed ids — a canonical-uuid shape check precedes the
  store read so malformed ids surface as not-found instead of driver errors),
  `EXPENSE_ALREADY_DELETED`, `TEACHER_NOT_FOUND` (dangling `teacherId`), plus the
  salaries/carryover guards above. All messages from `tErrors.expenses.*` / `teacher.*`.
- **`getReport` aggregates** are page-derived (per plan §3.3/3.6): `totalValue` sums the page's
  amounts as integer minor units (no float drift), `dominantCurrency` is the page's
  mode (fallback `SAR` on empty pages), `rowCountByType` reports all four types
  (zero-initialized). `totalCount` still covers the entire filtered set.

### `expense-idempotency.ts` — `deriveCreateIdempotencyKey`

sha256 of the scope + actor (`createdByUserId`) + `clientRequestId` + the identifying payload
(title, type, value, currency, paymentDate, expenseDate, teacherId, sourceEntity,
sourceEntityId); `null`/`undefined` collapse to an empty segment; note is excluded
(non-identifying, mirrors the carryover key convention). **Deviation from plan §3.7:**
`clientRequestId` participates in the hash — with the plan's field list, two different requests
with identical content would collapse and eat legitimate repeat submissions (e.g. two identical
utility bills); keying on the client request id makes double-clicks replay while deliberate
repeats persist. Same convention as Plan 5's `deriveCrudIdempotencyKey`.

**Idempotency replay** (`findReplayExpense`): only when `clientRequestId` is set. The replay
lookup scans `AuditRepository.queryAuditLogs` (`action = EXPENSE_CREATE`, actor-scoped, 60 s
window, recursive pages of 500 capped at 10 pages) matching `metadata.idempotencyKey` (the
plan's fictional `AuditLogRepository.findRecentByActorAndHash` — same substitution Plan 5
documented), picks the newest match deterministically, and re-reads the live expense row by the
audit row's `entityId` (`ExpenseRepository.getById`) so a replay returns current state, never a
stale snapshot. Missing audit/row ⇒ falls through to a normal insert. No advisory lock
(plan-review R2 finding 9: single-table write doesn't need one); the window race of two
simultaneous first-writes remains possible in theory but both would create separate rows only
on truly concurrent first submission — acceptable per plan.

## Contract for the Plan-5 stub swap (unchanged call shape)

```ts
// bulkCarryoverToExpense, inside its tx:
const row = await ExpenseService.createInternal(
  {
    teacherId, teacherName, title,
    type: ExpenseType.SALARIES,          // replaces local EXPENSE_TYPE_SALARIES constant
    expenseValue: carryover.payable, expenseCurrency: carryover.teacherCurrency,
    paymentDate, expenseDate, note,
    sourceEntity: "carryover_balances", sourceEntityId: carryover.id,
    createdByUserId: actorUserId,
  },
  tx, tErrors,
);
carryoverBalances.expenseId = row.id;

// unpayCarryoverBalance, inside its tx (idempotent on already-deleted):
await ExpenseService.softDelete({ id: carryover.expenseId, actorUserId, reason: note, tx }, tErrors);
```

Only the two stub functions (`createExpenseRecord`/`softDeleteExpenseRecord`) need the swap;
result types and audit trail in the carryover service are unaffected. Note: `createInternal`
emits its own `EXPENSE_CREATE` audit row into the caller tx, in addition to Plan 5's
`CARRYOVER_TO_EXPENSE` row.
