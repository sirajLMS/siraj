## Document names vs plan shorthand

The plan lists SCREAMING_SNAKE names (`EXPENSES_QUERY`, …) but the
sharedDocuments layer convention mandates `{camelCase}QueryDocument` /
`{camelCase}MutationDocument` typed as
`TypedDocumentNode<{Op}Query, {Op}QueryVariables>`. Mapping:

| Plan shorthand | Exported constant | GraphQL operation |
|---|---|---|
| `EXPENSES_QUERY` | `expensesQueryDocument` | `query Expenses($filter: ExpenseFilter, $limit: Int, $offset: Int)` |
| `EXPENSE_QUERY` | `expenseQueryDocument` | `query Expense($id: ID!)` |
| `CREATE_EXPENSE_MUTATION` | `createExpenseMutationDocument` | `mutation CreateExpense($input: CreateExpenseInput!)` |
| `UPDATE_EXPENSE_MUTATION` | `updateExpenseMutationDocument` | `mutation UpdateExpense($input: UpdateExpenseInput!)` |
| `DELETE_EXPENSE_MUTATION` | `deleteExpenseMutationDocument` | `mutation DeleteExpense($input: DeleteExpenseInput!)` |
| `BULK_DELETE_EXPENSES_MUTATION` | `bulkDeleteExpensesMutationDocument` | `mutation BulkDeleteExpenses($input: BulkDeleteExpensesInput!)` |

`expenses` selects the flattened page aggregates directly (`totalValue`,
`dominantCurrency`, `rowCountByType`) — the Pothos layer already flattens the
nested backend `aggregates` shape (outcome 2.1), so no client-side unwrapping.
