# Task 9.10 — Zod Validation Schema & Safe Fallback Parsers

## Summary

Created the canonical Zod validation schema for `AppearanceFields`
(`shared/schemas/appearance.zod.ts`) and wired it into
`AppearanceSettingsService.saveDraft` as defense-in-depth on the JSONB
boundary. The schema is the TypeScript-native runtime validation source of
truth (decision §22 — "Single-Source Zod Validation & Schema Type
Inference"); the JSON Schema from Task 9.1 remains the IDE/file-validation
source of truth. The two are structurally identical and MUST be kept in
sync (Task 9.1 carry-forward).

This satisfies **AC-38** — `NEXT_PUBLIC_APP_BRANDING` env strings and user
inputs SHALL be validated against a Zod schema, strictly rejecting invalid
hex formats, oversized strings, and non-safe URLs while safely falling back
to defaults on corrupt ENV strings.

## Requirements Coverage

- **AC-38** — Zod validation for `AppearanceFields`:
  - **Strict hex regex**: `APPEARANCE_HEX_PATTERN = /^#[0-9a-fA-F]{6}$/`
    applied to all 4 nested color fields (`colors.{light,dark}.{primaryMain,
    secondaryMain}`). Matches the JSON Schema pattern (Task 9.1) and the
    `HEX_PATTERN` in `shared/lib/color-contrast.utils.ts` (Task 9.6) — a
    single canonical shape across validation, persistence, and contrast math.
  - **String length limits**: `siteName` 1–80, `siteTitle` 1–120,
    `siteDescription` 0–300 (mirrors the JSON Schema `minLength`/`maxLength`).
  - **Safe URL refinement**: `logoUrl` is `z.string().nullable().refine(...)`
    using `URL.canParse(value)` (Node 18.17+ / Bun built-in). Empty string
    and `null` short-circuit to valid (unset logo).
  - **`defaultColorScheme`**: `z.enum(["light", "dark"])`.
  - **`.strict()`**: rejects unknown top-level keys (mirrors the JSON
    Schema's `additionalProperties: false`) — prevents typo'd keys like
    `primaryColor` from silently round-tripping.
- **Safe fallback parsing**:
  - `zAppearanceFieldsSafe(data, fallback)` — never throws; returns parsed
    value on success or `fallback` on failure. Used in `saveDraft` for
    JSONB-boundary defense-in-depth.
  - `parseAppearanceEnvBranding(envValue, fallback)` — JSON-parses the
    `NEXT_PUBLIC_APP_BRANDING` env string and validates the result; returns
    `fallback` on unset / empty / malformed-JSON / schema-failure (decision
    §22: "Invalid JSON in `NEXT_PUBLIC_APP_BRANDING` logs a domain error and
    gracefully falls back to `DEFAULT_APPEARANCE_FIELDS` without throwing or
    stalling server boot"). Ready for Task 9.2 to wire into the SSR
    resolution path.

## Design Decisions

### Why a strict 6-digit hex regex (not the 3-or-6 form in decision §22)?

Decision §22 mentions `/^#([0-9a-fA-F]{6}|[0-9a-fA-F]{3})$/` (3-or-6-digit),
but:
- The locked JSON Schema (Task 9.1) uses `^#[0-9a-fA-F]{6}$` (6-digit only).
- The contrast utils (Task 9.6) `HEX_PATTERN` uses the strict 6-digit form.
- MUI's `nativeColor` input always emits 6-digit hex (`#RRGGBB`).
- `primaryMain` / `secondaryMain` are persisted as `#RRGGBB` in the DB.

Accepting 3-digit hex at the validation boundary would create a discrepancy:
the validator accepts `#abc`, but the persistence layer expects `#aabbcc`
(and the contrast math assumes 6-digit). The strict form keeps validation,
persistence, and contrast math aligned on a single input shape. If a future
operator workflow ever needs to accept 3-digit hex, it should be normalized
to 6-digit BEFORE validation (Task 9.8's hex normalization helper carries
this concern forward).

### Why `.strict()` (rejects unknown keys)?

Defensive: prevents typo'd keys in mutation inputs (e.g. `primaryColor`
instead of `primaryMain`) from silently round-tripping through the system.
The `AppearanceFields` type is a closed interface; the Zod schema mirrors
that closure. Matches the JSON Schema's `additionalProperties: false`.

### Why `URL.canParse(value)` for `logoUrl` (not a regex)?

URI validation via regex is brittle (RFC 3986 is complex). The runtime
validator delegates to the platform `URL.canParse()` built-in (Node 18.17+ /
Bun), which is correct and zero-dependency. Empty strings short-circuit to
valid (an unset logo is represented as `null`, not `""`, but `""` is
tolerated defensively — matches the JSON Schema validator's behavior in
Task 9.1).

### Why log+fallback in `saveDraft` (not throw)?

- The GraphQL layer should already reject invalid inputs (the GraphQL input
  type enforces shape). The Zod re-check is defense-in-depth for the JSONB
  boundary.
- Throwing here would create an inconsistent UX: a mutation that passed
  GraphQL validation would fail at the service layer with a different
  error message.
- Falling back to `DEFAULT_APPEARANCE_FIELDS` is the safest behavior — it
  prevents bad data from being persisted, and the `logger.warn` ensures the
  domain error is observable (matching decision §22's "logs a domain error
  and gracefully falls back" pattern for ENV strings).

### Why no `satisfies z.ZodType<AppearanceFields>`?

The existing `backend/lib/payment-method.validation.ts` and
`backend/lib/meeting-provider.validation.ts` use
`satisfies z.ZodType<CanonicalType>` for type-safety. That pattern works
because those files live in `backend/lib/` and can import from
`@/backend/types`. This file lives in `shared/schemas/`, which MUST NOT
import from `@/backend/types` (layer isolation rule). Instead, the
canonical type is inferred from the Zod schema itself
(`export type AppearanceFieldsZod = z.infer<typeof zAppearanceFields>`).
The inferred type is structurally identical to `AppearanceFields`, so
callers in `backend/` can pass `AppearanceFields`-typed values where
`AppearanceFieldsZod` is expected (and vice-versa) without casts. This is
the "Zod is the source of truth" pattern (decision §22 option A).

### Why no `parseAppearanceEnvBranding` caller yet?

The ENV-var resolution path (`process.env.NEXT_PUBLIC_APP_BRANDING` → typed
`AppearanceFields`) is the Task 9.2 carry-forward. Task 9.2 will wire
`parseAppearanceEnvBranding(process.env.NEXT_PUBLIC_APP_BRANDING,
DEFAULT_APPEARANCE_FIELDS)` into `getResolvedAppearance()` (the tiered
SSR resolution function from decision #14). The helper is ready and
fully tested at the schema level (sub-loop passes); only the call-site
wiring remains.
