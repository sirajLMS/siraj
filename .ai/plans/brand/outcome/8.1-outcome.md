# Task 8.1 — Override `server-theme-css.ts` fallback tokens

## Summary

Overrode the SSR critical-theme CSS builder
(`frontend/common/lib/server-theme-css.ts`) so that a published
`appearance_settings` row paints the published brand `primaryMain` into the
`--mui-palette-primary-main` CSS variable on the very first server render,
before client hydration and Emotion cache mount (AC-21). The published
`defaultColorScheme` now also drives the initial SSR theme mode when no theme
cookie is set ("use published value as default mode"), and the cached read is
tagged `"appearance"` so `revalidateTag` on `publish` invalidates it (AC-22).

When no published row exists — or the cached DB read throws — the function
falls back to the pre-task behavior exactly (static `darkPalette` /
`lightPalette` + `DARK_FALLBACKS` / `LIGHT_FALLBACKS`, default mode `"dark"`),
so the change is backward-compatible and resilient.

## Requirements Coverage

- **AC-21** — Published appearance overrides SSR theme CSS tokens.
  - `--mui-palette-primary-main` is overridden with the published per-mode
    `primaryMain` for **both** emitted modes (`light` and `dark`), so the
    published brand color paints on first render regardless of which mode the
    visitor lands in.
  - The published `defaultColorScheme` is the default SSR theme mode when no
    `theme-mode` cookie is set (first visit / cookie expired). The cookie
    still takes precedence so the user's explicit mode choice is respected.
- **AC-22** — Cache invalidation: the published read goes through
  `AppearanceSettingsService.getFirstAppearancePublished()`, which is
  `unstable_cache`d with tag `"appearance"`. `publish` calls
  `revalidateTag("appearance", "max")` (Task 2.3), so the next SSR render
  picks up the new published `primaryMain` / `defaultColorScheme` without a
  redeploy.

## Design Adherence

### Why override `primaryMain` for BOTH modes (not just the default mode)

`buildServerThemeCss` emits CSS rules for **both** `light` and `dark` modes
on every SSR render (the initial server mode first, then the other mode) so
that a client-side theme toggle immediately finds a matching
`html[data-theme="…"]` rule with the correct variable values. If we overrode
`primaryMain` only for the published `defaultColorScheme`, the other mode's
rule would carry the static palette `primaryMain` — and a first-time visitor
who toggles modes before hydration would see the old brand color flash in
the toggled mode.

`getFirstAppearancePublished()` returns the full `AppearanceFields` with
both `colors.light` and `colors.dark` populated (the active mode from the
published single-mode columns, the inactive mode from the `draft_fields`
JSONB — see `toPublishedAppearanceFields` in the service). So overriding
both modes' `primaryMain` is a single-source read with no extra DB cost.

### Why `publishedPrimary ??` and not `appearance ? … : …`

The pre-task resolution chain for `primaryMain` was:
`hasMain(primary) ? primary.main : fallbacks.primaryMain`. Inserting the
published value as the **first** choice (`publishedPrimary ?? …`) means:
- When `appearance` is `null` (no row / read threw): `publishedPrimary` is
  `undefined`, the `??` falls through, and the pre-task chain runs
  unchanged — byte-identical CSS output.
- When `appearance` is present: the published `primaryMain` wins over both
  the static palette and the constant fallback.

This mirrors the unified `?.` + `??` resolve-and-return pattern used in
Task 8's `generateMetadata` (single expression, no duplicated object
literal, low cyclomatic complexity).

### Why `resolveServerThemeMode` is a separate exported helper (not inlined)

The layout needs the resolved mode for **two** consumers:
1. The HTML attributes (`data-mui-color-scheme`, `data-theme`,
   `data-${initialTheme}`, `style={{ colorScheme }}`,
   `<InitColorSchemeScript defaultMode={initialTheme} />`,
   `<MuiProvider initialTheme={initialTheme} />`).
2. `buildServerThemeCss(initialTheme)` — the CSS rule order.

If `buildServerThemeCss` resolved the mode internally (e.g. accepted the raw
cookie value), the layout would still need a separate mode read for the HTML
attributes, doubling the cached appearance fetch (or requiring a
`{ css, mode }` return tuple that breaks the existing call shape). Keeping
`resolveServerThemeMode` as a sibling export lets the layout read once and
pass the resolved mode to both consumers, and `buildServerThemeCss` stays
focused on CSS generation.

### Resilient read (try/catch → static fallback)

`fetchPublishedAppearance()` wraps `getFirstAppearancePublished()` in
try/catch and logs via `logger.error`, returning `null` on failure. The SSR
theme CSS is non-critical (the page body renders independently), and a
cold-cache DB hiccup would otherwise 500 every route render — the same
resilience pattern used in Task 8's `generateMetadata` and in the service's
`emitPublishAudit` best-effort audit.

### Why the layout change is in-scope

The task spec says "Modify `server-theme-css.ts`", but making
`buildServerThemeCss` async (required because `getFirstAppearancePublished`
is an `unstable_cache`d async function) necessitates `await` at the call
site. The "use published value as default mode" requirement also requires
the layout to use the published `defaultColorScheme` for the HTML
attributes (otherwise the CSS mode and the `data-mui-color-scheme`
attribute would disagree, causing a first-paint mode mismatch). Both
layout changes are minimal (1 import swap, 2 `await` additions) and
necessary corollaries of the `server-theme-css.ts` change.

## Decisions

- **Override `primaryMain` for both emitted modes, not just the default
  mode.** `buildServerThemeCss` emits rules for both `light` and `dark` on
  every SSR render so a client toggle immediately finds a matching rule.
  Overriding only the default mode would leave the other mode's
  `--mui-palette-primary-main` at the static palette value, causing a
  brand-color flash on first toggle. `getFirstAppearancePublished()`
  returns both modes' colors (active from published columns, inactive from
  `draft_fields` JSONB), so overriding both is a single-source read.

- **`publishedPrimary ??` prepended to the existing resolution chain.**
  Chose to prepend the published value as the first-choice in the `??` chain
  (`publishedPrimary ?? (hasMain(primary) ? primary.main :
  fallbacks.primaryMain)`) rather than an `if (appearance)` branch. When
  `appearance` is `null`, `publishedPrimary` is `undefined` and the `??`
  falls through to the pre-task chain — byte-identical CSS output. This
  mirrors the unified `?.` + `??` pattern from Task 8's `generateMetadata`
  and keeps cyclomatic complexity at 1 (no new branch).

- **`resolveServerThemeMode` as a sibling export, not inlined in
  `buildServerThemeCss`.** The layout needs the resolved mode for both the
  HTML attributes and the CSS. Inlining mode resolution in
  `buildServerThemeCss` (e.g. accepting the raw cookie value) would either
  double the cached read or require a `{ css, mode }` return tuple that
  breaks the existing call shape. A sibling export lets the layout read
  once and pass the resolved mode to both consumers.

- **try/catch around the cached read.** Same rationale as Task 8: the SSR
  theme CSS is non-critical, and a cold-cache DB failure would otherwise
  500 every route render. The try/catch logs and falls back to `null`,
  which the `??` chain turns into the pre-task static tokens.

- **Layout change is a necessary corollary, not scope creep.** Making
  `buildServerThemeCss` async requires `await` at the call site. The "use
  published value as default mode" requirement also requires the layout to
  use the published `defaultColorScheme` for the HTML attributes (CSS mode
  + `data-mui-color-scheme` must agree). Both layout edits are minimal (1
  import swap, 2 `await` additions).

## Carry-Forward / Deferred

- **`secondaryMain` CSS variable.** The `ServerThemeTokens` interface does
  not include a `secondaryMain` token (only `primaryMain` /
  `primaryContainer`). MUI's CSS variable system (`cssVariables: true`)
  generates `--mui-palette-secondary-main` automatically from the runtime
  palette, so the SSR critical CSS does not need to override it — the
  client-side `useAppearanceCssVars` hook (Task 4.1) writes the published
  `secondaryMain` to `--mui-palette-secondary-main` on hydration. If a
  future task wants the published `secondaryMain` in the SSR critical CSS
  too (to prevent a secondary-color flash on first paint), it would add a
  `secondaryMain` field to `ServerThemeTokens` and a
  `--mui-palette-secondary-main` line to `buildModeRule`. Out of scope for
  AC-21 (which says "primary/secondary fallback tokens" — the secondary
  fallback is the in-memory `lightPalette.secondary.main`, which the
  `useAppearanceCssVars` hook overrides on the client).

- **`primaryContainer` override.** The published appearance only stores
  `primaryMain` / `secondaryMain` (decision #2 — brand primitives only;
  MUI derives `primaryContainer` via `color-mix()`). Overriding
  `primaryContainer` in the SSR CSS would require either a derived value
  or a new published field. Deferred — the client-side hook handles it.

- **ENV hydration (Task 9.2).** When `NEXT_PUBLIC_APP_BRANDING` is
  implemented, `fetchPublishedAppearance` could fall back to the ENV JSON
  before the static palette. Out of scope for 8.1.
