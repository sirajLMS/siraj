## Design adherence

### Per-mode color reconciliation (decisions #2, #7, #12)

The design explicitly reconciles the three locked decisions:

- **Published columns** (`primaryMain`, `secondaryMain`, `logoUrl`, `siteName`,
  `siteTitle`, `siteDescription`, `defaultColorScheme`) are **single-mode** values
  applied to the selected `defaultColorScheme` mode (decision #2 + #7).
- **Draft** (`draftFields`) is **per-mode** — `{ light: {primaryMain, secondaryMain},
  dark: {...} }` — so the admin can edit each mode independently in the
  `?customize=1` overlay (decision #12).
- **On publish**, the draft's active-mode colors
  (`draftFields.colors[draftFields.defaultColorScheme]`) are copied into the single
  published `primaryMain`/`secondaryMain` columns (decision #7).

This is captured by:
- `AppearanceFields.colors: PerModeColors` (per-mode, for draft).
- `AppearanceSettingsRow.primaryMain: string` (single-mode, for published).
- `AppearanceSettingsRow.draftFields: AppearanceFields` (typed JSONB).

### `PaletteMode` import

`defaultColorScheme: PaletteMode` is imported from `@mui/material/styles`,
matching the existing pattern in `frontend/common/lib/server-theme-css.ts`
(server-side file that already imports `PaletteMode` the same way). Makes the
type compatible with MUI's theme pipeline (decision #2 — MUI `nativeColor`
derives light/dark/contrastText in-browser).

### Why `AppearanceSettingsRow` is an explicit object literal (not `$inferSelect`)

The AGENTS.md positive pattern suggests `{Entity}SelectType = typeof table.$inferSelect`.
This file deliberately deviates because:

1. **Task 2 (Drizzle schema) is running in parallel** — the schema file
   `backend/db/schema/appearance/appearance-settings.schema.ts` does not exist
   yet, so `$inferSelect` cannot be referenced.
2. **Typed JSONB enforcement** — Drizzle's `$inferSelect` types `draftFields` as
   `unknown` (jsonb column). The explicit `draftFields: AppearanceFields`
   enforces the typed JSONB shape at the type boundary. The repo layer (Task 2.2)
   can use `as AppearanceSettingsRow` after `JSON.parse` to satisfy this.
3. **ISO string timestamps** — `$inferSelect` would type `updatedAt`/`createdAt`
   as `Date`. The design calls for ISO strings (serialized by the repo before
   returning), matching `AppearanceSettingsRow.updatedAt: string`.

The repo layer (Task 2.2) is expected to define its own `toReturnType` mapper
that converts the raw Drizzle row (with `Date` timestamps and `unknown` jsonb)
into `AppearanceSettingsRow` (with ISO strings and typed `draftFields`).

## Lint adaptation: `Omit<AppearanceSettingsRow, never>`

The design specifies:
```ts
export type AppearanceSettingsReturnType = AppearanceSettingsRow;
```

However, `sonarjs/redundant-type-aliases` (run by `lint:type-aware`) flags bare
`Type = OtherAlias` declarations when the referenced symbol is itself a
`TSTypeAliasDeclaration`. The rule fires for `AppearanceSettingsRow` (a type
alias) but NOT for `AppearanceFields` (an interface, which the rule
classifies as `TSInterfaceDeclaration` and skips).

Adapted to:
```ts
export type AppearanceSettingsReturnType = Omit<AppearanceSettingsRow, never>;
```

This is **structurally identical** to `AppearanceSettingsRow` — `Omit<X, never>`
removes zero keys. The same pattern is used in the codebase by
`ImpersonationSessionReturnType` in `backend/types/auth/impersonation.types.ts`.

The two other aliases (`AppearanceSettingsSubmitInput = AppearanceFields` and
`AppearanceDraftInput = AppearanceFields`) were NOT flagged because
`AppearanceFields` is an interface, not a type alias, so `isTypeAlias()` returns
`false` (see `node_modules/eslint-plugin-sonarjs/cjs/helpers/type.js:437`).

## Carry-Forward Knowledge for Phase 2

1. **`AppearanceSettingsRow` is an explicit object literal, NOT `$inferSelect`.**
   Task 2.2 (repository) must define a `toReturnType` mapper that converts the
   raw Drizzle row (typed by `$inferSelect` with `Date` timestamps and `unknown`
   jsonb) into `AppearanceSettingsRow` (with ISO string timestamps and typed
   `draftFields: AppearanceFields`).

2. **`draftFields` JSONB typing.** The Drizzle schema (Task 2) should declare
   `draftFields: jsonb().$type<AppearanceFields>()` so Drizzle's `$inferSelect`
   is `AppearanceFields` rather than `unknown`. This will make the repo mapper
   trivial. The repo should still `JSON.parse` defensively at runtime.

3. **`defaultColorScheme: PaletteMode`** — `PaletteMode` is imported from
   `@mui/material/styles`. Task 2's schema should use `text("default_color_scheme")`
   with a TS-side `$type<PaletteMode>()` cast (or a Drizzle enum). The Drizzle
   column itself is `text` (per decision #2: `'light'` or `'dark'`).

4. **Published columns are single-mode.** Task 2.3's `publish` service method
   must read `draftFields.colors[draftFields.defaultColorScheme].primaryMain`
   and copy it into the published `primary_main` column (same for `secondaryMain`).
   Other scalar fields (`logoUrl`, `siteName`, `siteTitle`, `siteDescription`,
   `defaultColorScheme`) are copied 1:1 from `draftFields`.

5. **`DEFAULT_APPEARANCE_FIELDS`** (defined in Task 2.3) must conform to
   `AppearanceFields`. The design §4 specifies the seed values:
   ```ts
   {
     colors: {
       light: { primaryMain: "#0D9488", secondaryMain: "#4F46E5" },
       dark:  { primaryMain: "#2DD4BF", secondaryMain: "#818CF8" },
     },
     logoUrl: null,
     siteName: "Siraj",
     siteTitle: "Siraj",
     siteDescription: "Siraj education management",
     defaultColorScheme: "dark",
   }
   ```

6. **`sonarjs/redundant-type-aliases` rule gotcha**: bare `Type = OtherAlias;`
   is flagged ONLY when `OtherAlias` is itself a `type` alias. References to
   `interface`s are NOT flagged. Future type files can use either:
   - `Omit<Alias, never>` (preserves the alias indirection), or
   - Convert `OtherAlias` to an `interface` where structural typing allows.
   The `Omit<X, never>` pattern is the established codebase convention.

7. **CodeScene CLI PATH issue** (cross-cutting, not just this task): on
   siraj-station, the `cs` binary is at `/home/ahmed/.local/bin/cs` but SSH
   sessions don't include `~/.local/bin` in `$PATH`. Workaround: prefix
   sub-loop commands with `CODESCENE_BIN=/home/ahmed/.local/bin/cs` (or
   `PATH=/home/ahmed/.local/bin:$PATH`). The orchestrator / future subagents
   should bake this into their sub-loop invocations. A permanent fix would be
   to either (a) symlink `/usr/local/bin/cs -> /home/ahmed/.local/bin/cs`, or
   (b) patch `scripts/health/codescene/installer.ts` to also try
   `~/.local/bin/cs` as a fallback in `resolveCodesceneBin()`.

8. **File placement** (`backend/types/appearance.types.ts`, root-level): per
   the explicit `implementation.md` §2 spec. Sibling entities live in
   subdirectories (`backend/types/audit/`, `backend/types/storage/`, etc.)
   with their own sub-barrels. The root-level placement was chosen by the
   design author — likely because appearance is a single-file entity with no
   sub-types warranting a directory. Future tasks should NOT migrate this to
