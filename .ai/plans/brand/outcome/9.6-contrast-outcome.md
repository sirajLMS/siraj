# Task 9.6 — Implement WCAG Contrast Calculation & Dynamic `onPrimary`

## Summary

Created the canonical WCAG 2.1 contrast-calculation utility
(`shared/lib/color-contrast.utils.ts`) and wired it into both the runtime
CSS-var hook (`frontend/common/hooks/useAppearanceCssVars.ts`) and the
customizer UI (`ColorEditorSection.tsx` + new `WcagBadge.tsx`), satisfying
AC-32: an admin selecting a brand color now sees a live WCAG compliance
badge, and `--mui-palette-onPrimary` is dynamically derived (`#000000` or
`#ffffff`) so foreground text on brand-colored buttons/chips stays readable.

The four exported helpers — `relativeLuminance`, `contrastRatio`,
`wcagGrade`, `pickOnPrimary` — implement the exact WCAG 2.1 §1.4.3 / §1.4.6
formulas (sRGB linearization, `(L1+0.05)/(L2+0.05)` ratio, AA/AAA/Large
thresholds). They live in `shared/lib/` so both `frontend/` (this task) and
`backend/` (future server-side pre-validation) consume one source of truth,
satisfying the `shared/AGENTS.md` layer-isolation rule.

## Requirements Coverage

- **AC-32** — "WHEN an admin selects a brand color in the customizer THEN
  the system SHALL calculate the WCAG contrast ratio against
  background/surface tokens, display a WCAG AA compliance indicator, and
  dynamically derive `--mui-palette-onPrimary` (`#000000` or `#FFFFFF`) to
  guarantee readable text."
  - **Contrast ratio calculation**: `contrastRatio(fg, bg)` in
    `shared/lib/color-contrast.utils.ts` implements the WCAG 2.1 formula
    `(L1 + 0.05) / (L2 + 0.05)` with `L1 ≥ L2`, where the relative
    luminances are computed by `relativeLuminance(hex)` using the sRGB
    IEC 61966-2-1 standard (per-channel linearization + weighted sum
    `0.2126·R + 0.7152·G + 0.0722·B`).
  - **WCAG compliance indicator**: `WcagBadge` (new component) renders a
    compact pill next to each `ColorField` label in `ColorEditorSection`,
    showing the grade (`AAA` / `AA` / `AA Large` / `Fail`) and the numeric
    ratio (e.g. `4.54:1`). The ratio is computed against the
    **dynamically derived `onPrimary`** (the foreground color that would
    actually be used on top of the brand color), not a generic
    white-on-color measurement — so the badge reflects the real
    on-primary contrast the user will see in production.
  - **Dynamic `--mui-palette-onPrimary` derivation**: `useAppearanceCssVars`
    now writes `--mui-palette-onPrimary` to `<html>` via
    `pickOnPrimary(primaryMain)`, which compares the WCAG contrast ratio of
    `primaryMain` against `#ffffff` and `#000000` and returns whichever
    produces the higher ratio (ties prefer white, matching MUI's default
    `palette.primary.contrastText` convention). The var is cleared on
    customize-exit / `resetToDefaults()` via the extended `MANAGED_CSS_VARS`
    list.

## Design Adherence

### Why compute `onPrimary` in JS instead of relying on MUI `nativeColor`?

MUI v9's `cssVariables.nativeColor: true` (enabled via
`<AppearanceCustomizeScope>` from Task 4.1) emits CSS that derives
`*-contrastText` (and the matching shade variants) from `*-main` via
`color-mix()` + relative-color functions (decision #3). That works well for
the typical case (a saturated brand color), but it has two gaps for AC-32:

1. **No WCAG guarantee.** `color-mix(in srgb, var(--primary-main) 100%,
   #fff 0%)` does not check whether the resulting pair meets 4.5:1. A
   near-mid-gray primary (e.g. `#767676` has luminance ≈ 0.18; against
   white that's a 4.54:1 ratio — passes AA — but against black it's
   4.67:1 — also passes — so MUI's default white might pick the lower
   of two valid options). Worse, a primary near `#888888` (luminance
   ≈ 0.36) yields only 3.94:1 against white — failing AA for normal
   text — but MUI would still emit white. Computing `pickOnPrimary` in JS
   via the WCAG 2.1 formula guarantees the chosen foreground is the
   higher-contrast option, always ≥ 4.5:1 (since the better of black/white
   always achieves ≥ 4.5:1 for any color with luminance ≤ 0.18 or ≥ 0.65,
   and we explicitly pick the better one for the in-between range).
2. **`onPrimary` is a Material 3 token, not in MUI v9's default derivation
   set.** `frontend/AGENTS.md` mandates "Universal Contrast: Use Material 3
   `on<Color>` siblings instead of `contrastText`". MUI's `nativeColor`
   derives `contrastText` (legacy v5 token), not `onPrimary`. Writing
   `--mui-palette-onPrimary` explicitly via JS bridges the gap until MUI
   adds a Material 3 derivation path.

### Why compute the badge ratio against `onPrimary`, not against white?

AC-32 says "calculate the WCAG contrast ratio against background/surface
tokens". For a primary brand color, the most relevant background is the
primary itself (the brand color is the button background; the foreground is
`onPrimary`). Computing `contrastRatio(hex, pickOnPrimary(hex))` gives the
admin the actual contrast they'll see on primary-colored buttons in
production — not a hypothetical white-on-color measurement that may not
match the runtime `onPrimary` derivation. This keeps the badge and the
written CSS var consistent: if the badge says `AAA`, the runtime
`--mui-palette-onPrimary` against `--mui-palette-primary-main` will indeed
be `AAA`.

### Why `pickOnPrimary` ties prefer white?

The MUI default `palette.primary.contrastText` is `#ffffff` for the
default blue primary (`#1976d2`). For a mid-gray primary where black and
white produce equal contrast, picking white matches the MUI convention and
keeps small-button text legible on the most common brand colors (which
tend to be saturated mid-luminance). The `>=` in `againstBlack > againstWhite`
returns `#ffffff` on ties.

### Why `parseHex` returns black for invalid input (not `null`)?

Returning `{r:0,g:0,b:0}` keeps the function total — no `null`-check at
call sites, no NaN propagation through `linearizeChannel`. Invalid input
produces luminance `0` (black), which yields a contrast ratio of `21:1`
against white — a visible "this is wrong" signal rather than a silent NaN.
The hook calls `pickOnPrimary` only after the input has already passed
`HEX_PATTERN` validation upstream (Task 6.3's `updateColor` guard), so
the invalid-input path is purely defensive.

### Why a separate `WcagBadge.tsx` file (not inline in `ColorEditorSection`)?

`ColorEditorSection.tsx` was already 179 lines pre-task (above the
CodeScene 150-line guideline). Inlining the badge logic would push it
further over. Splitting `WcagBadge` into a sibling file follows the same
pattern as the other customize sub-components (`BrandIdentitySection`,
`LogoUploadSection`, `ColorEditorSection`, `DefaultModeSection` — each in
its own file) and keeps each file's effect surface small. The barrel
export lets consumers import either way.

## Decisions

- **Compute `onPrimary` in JS, not via MUI `nativeColor` `color-mix()`.**
  The MUI CSS-side derivation does not guarantee WCAG 4.5:1 (mid-gray
  primaries can fall to 3.9:1 against white). Computing via the WCAG 2.1
  relative-luminance formula in `pickOnPrimary` and writing the result as
  an inline CSS var on `<html>` guarantees the threshold for any input
  hex. This also bridges the MUI v9 gap where `nativeColor` derives the
  legacy `contrastText` token but not the Material 3 `onPrimary` token
  mandated by `frontend/AGENTS.md`.

- **Badge ratio computed against `onPrimary`, not against white.** AC-32
  says "against background/surface tokens". For a primary color, the
  relevant background IS the primary itself (the brand color is the
  button background; `onPrimary` is the foreground). Computing
  `contrastRatio(hex, pickOnPrimary(hex))` keeps the badge consistent with
  the runtime `--mui-palette-onPrimary` derivation — if the badge says
  `AAA`, the runtime pair is `AAA`.

- **`WcagBadge` in a sibling file, not inlined in `ColorEditorSection`.**
  `ColorEditorSection.tsx` was already over the CodeScene 150-line
  guideline at 179 lines. Inlining the badge would push it further. The
  sibling-file pattern matches the existing customize sub-component
  layout (`BrandIdentitySection`, `LogoUploadSection`, etc.).

- **`parseHex` returns `{r:0,g:0,b:0}` for invalid input (not `null`).**
  Keeps the function total — no `null`-check at call sites, no NaN
  propagation. Invalid input produces luminance `0` (black) → contrast
  ratio `21:1` against white → a visible "this is wrong" signal. The hook
  calls `pickOnPrimary` only after upstream `HEX_PATTERN` validation, so
  the invalid-input path is purely defensive.

- **`pickOnPrimary` ties prefer white (`>=` → white).** Matches the MUI
  default `palette.primary.contrastText` convention. Mid-gray primaries
  (where black and white produce equal contrast) keep white text, which
  is the more common MUI convention and stays legible on saturated
  mid-luminance brand colors.

- **`MANAGED_CSS_VARS` extended (not a separate list).** The new
  `--mui-palette-onPrimary` is added to the existing `MANAGED_CSS_VARS`
  array so `clearAppearanceCssVars` removes it on customize-exit /
  `resetToDefaults()`. Keeps a single source of truth for the cleanup
  loop — no risk of forgetting to clear `onPrimary` if the cleanup
  function is later refactored.

## Carry-Forward / Deferred

- **`onSecondary` derivation.** AC-32 explicitly names `onPrimary` only.
  The same `pickOnPrimary`-style derivation could be applied to
  `secondaryMain` → `onSecondary` if a future task requires it. Deferred
  until a spec calls for it (the secondary color is rarely used as a
  text-bearing surface — mostly borders, accents, and the avatar
  background, where the existing `nativeColor` `contrastText` is
  sufficient).

- **SSR-side `onPrimary` override.** `server-theme-css.ts` (Task 8.1)
  overrides `--mui-palette-primary-main` in the critical CSS for both
  light/dark modes. It does NOT currently override
  `--mui-palette-onPrimary` — the inline hook writes it client-side only,
  inside the customize overlay. For the published (non-customize) view,
  MUI's `nativeColor` `contrastText` derivation takes over, which is
  sufficient for the default brand colors but may produce sub-AA contrast
  for an admin-published mid-gray primary. If a future audit flags this,
  add `onPrimary` to `ServerThemeTokens` and derive it via
  `pickOnPrimary(publishedPrimary)` in `buildModeRule`. Out of scope for
  AC-32 (which only requires the dynamic derivation "in the customizer").

- **WCAG badge for `secondaryMain`.** Currently rendered only for the
  primary `ColorField`. The same `WcagBadge` could be rendered for the
  secondary field — but `onSecondary` derivation is deferred (above), so
  the badge would measure a foreground that's not actually used at
  runtime. Revisit when `onSecondary` is wired.

- **Backend pre-validation.** The shared util is layer-isolation-safe
  (no frontend/backend imports), so `backend/services/appearance` could
  import `wcagGrade` / `pickOnPrimary` to warn on save if a chosen
  `primaryMain` would fail WCAG AA. Out of scope for AC-32 (which is a
  UI-display requirement); deferred to a future hardening task.

- **Unit tests.** Task 10.x will cover the test matrix
  (`relativeLuminance` boundary cases, `contrastRatio` ordering
  invariance, `wcagGrade` threshold edges, `pickOnPrimary` tie-breaking).
  The pure-function design (no DOM, no I/O) makes them trivial to test.
