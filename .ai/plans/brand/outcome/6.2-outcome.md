# Task 6.2 — `CustomizeToolbar` component

## Summary

Replaced the Task 6.1 placeholder body of `CustomizeToolbar.tsx` with the
real action surface for the site-appearance customizer overlay — matching
section 1 of `.ai/plans/brand/prototype/customize-overlay.html`.

The toolbar now renders, left-to-right:
1. **Amber "Customize" chip** (`PaletteOutlined` icon + `color="warning"`,
   matching the header `CustomizeButton` and the appearance-tab draft chip).
2. **Undo / Redo** icon buttons (`UndoOutlined` / `RedoOutlined`), wired to
   `useAppearancePreviewStore.undo()` / `redo()`, disabled when the
   corresponding history stack is empty.
3. **Save Draft** button → `saveAppearanceDraft` GraphQL mutation, passing
   the store's `draft` (`AppearanceDraftInput`) directly as the `input`
   variable — no mapping, per `frontend/common/stores/AGENTS.md`.
4. **Publish** button → `publishAppearance` mutation (contained `warning`
   color — amber, matching the prototype's accent button).
5. **Reset** button → opens a confirmation `Dialog`; on confirm, calls the
   `resetAppearanceDraft` mutation.
6. **Live-preview hint** caption (hidden on mobile `xs`, visible `sm+`).
7. **Exit** button (outlined `error` color) → strips `?customize=1` from
   the URL via `router.replace`, preserving all other query params.

All actions fire toast notifications via `@toolpad/core/useNotifications`
on success/failure, matching the existing `AppearanceSettingsTab.tsx`
convention. Errors are also logged via `frontend/common/utils/logger`.

## Design Adherence

### Reactive store slices (not method calls)

The `appearancePreviewStore` exposes `canUndo()` / `canRedo()` methods,
but calling them inside a `useAppearancePreviewStore(s => s.canUndo())`
selector would return a fresh boolean each render without Zustand
knowing to re-render when the underlying `past` / `future` arrays change.
Instead, the toolbar selects the primitive array lengths:

```ts
const pastLength = useAppearancePreviewStore(s => s.past.length);
const futureLength = useAppearancePreviewStore(s => s.future.length);
const canUndo = pastLength > 0;
const canRedo = futureLength > 0;
```

This gives referentially-stable primitives that re-render the toolbar
exactly when history changes (no extra renders, no stale disabled state).

### Direct mutation input — NO MAPPING

Per `frontend/common/stores/AGENTS.md` ("NO MAPPING, NO SCHEMA TYPES"),
the store's `draft: AppearanceDraftInput` is the codegen mutation input
type. The Save Draft handler passes it directly:

```ts
await saveDraft({ variables: { input: draft } });
```

No field-by-field mapping, no `as` cast, no nullable-coalescing. The
resolver (Task 2.4) normalizes `logoUrl: undefined → null` and coerces
`defaultColorScheme: string → PaletteMode`.

### Exit button preserves query params

```ts
const params = new URLSearchParams(searchParams?.toString() ?? "");
params.delete("customize");
const qs = params.toString();
router.replace(qs ? `${pathname}?${qs}` : pathname);
```

This preserves `?tab=appearance`, `?classId=123`, etc. — important
because the user might have entered customize mode from any dashboard
page (the header `CustomizeButton` from Task 6 builds its href from
`usePathname()` + the existing search params).

### Publish uses `color="warning"` (amber)

The prototype's Publish button is `.btn-accent` (amber `#F59E0B`). MUI's
`warning` palette is the amber family (per `lightPalette.ts` comments and
the Task 6 outcome). The Publish button uses
`sx={theme => ({ color: theme.palette.onWarning })}` to override
`contrastText` per AGENTS.md "M3 on<Color> siblings" rule — matching the
header `CustomizeButton` pattern.

### Reset confirmation dialog reuses existing strings

The Reset confirmation `Dialog` reuses the existing
`resetConfirmTitle` / `resetConfirmBody` / `resetConfirmCancel` /
`resetConfirmConfirm` strings from `SettingsAppearanceTabLabels`. No new
dialog strings were added — the dialog content is identical whether
triggered from the tab's action bar (Task 5.2) or the customize toolbar.

### Tooltip + disabled IconButton pattern

MUI `Tooltip` doesn't fire when its child is `disabled`. The standard
workaround (per MUI docs and existing codebase patterns) is to wrap the
disabled `IconButton` in a `<span>`:

```tsx
<Tooltip title={t.toolbarUndo}>
  <span>
    <IconButton size="small" onClick={undo} disabled={!canUndo} aria-label={t.toolbarUndo}>
      <UndoOutlined fontSize="small" />
    </IconButton>
  </span>
</Tooltip>
```

This keeps the tooltip accessible (the `<span>` receives pointer events)
while the button itself remains disabled.

## Decisions

- **Real GraphQL wiring (not stubbed).** The task instructions allowed
  stubbing mutation calls with `// TODO: wire to GraphQL` if wiring was
  complex. Wiring was straightforward because the codegen
  `AppearanceDraftInput` matches the store's `draft` type directly (per
  the "NO MAPPING" rule), and `@apollo/client/react`'s `useMutation` is
  the standard pattern (matches `ManagerRowActions.tsx`). All three
  mutations are wired with try/catch + toast + logger.error on failure.

- **6 new toolbar strings added to `SettingsAppearanceTabLabels`** (not
  a separate `customize.*` namespace). The type file's comment says
  "customize.* are scoped to Task 9", but Task 9 in the current plan is
  the "Public appearance SSR + cache + ThemeRegistry" phase, not the
  customizer overlay. The toolbar strings logically belong to the
  appearance-settings domain, so they live alongside the existing tab
  strings. If Task 9 introduces a broader `customize.*` namespace, the
  toolbar strings can be migrated then (a mechanical rename).

- **`toolbarPublish` separate from `publishNow`.** The prototype uses
  "Publish" (short) in the toolbar and "Publish Now" (long) in the tab's
  action bar. Rather than reusing `publishNow` and truncating via CSS,
  added a separate `toolbarPublish` string. This keeps the i18n keys
  self-documenting (the toolbar label is a different string than the
  tab label, even if they happen to be similar in some locales).

- **Reset handler does not sync local draft from server response.** The
  `resetAppearanceDraft` mutation returns the updated row (with
  `draftFields` matching published values), but the codegen output type
  (`AppearanceFieldsSelectionFragment`) has nullable fields while the
  store's `AppearanceDraftInput` has non-nullable fields — mapping
  would require null-coalescing defaults. Instead, the handler calls
  `markSaved()` (clears `dirty`) and relies on Task 9's customizer
  provider to refetch the `appearanceSettings` query and call
  `loadFromServer()`. The user can still undo via the store's history
  stack if they want to recover their edits.

- **No `refetchQueries` on mutations.** Apollo cache normalization
  handles the update automatically because the mutations return the
  same `AppearanceSettings` row (with `id`). The `appearanceSettings`
  query will be re-emitted when the cache changes. Task 9's provider
  will subscribe to the query and sync the store.

- **Exit button color is `error` (red).** The prototype uses
  `.btn-danger` (red ghost) for Exit, signaling "leave with potential
  unsaved changes". MUI `color="error"` + `variant="outlined"` matches
  this semantics. A future enhancement could add an unsaved-changes
  guard dialog before exit (currently, exit just strips the URL param —
  the draft is preserved in the store, so re-entering customize mode
  restores it until the user navigates away or refreshes).

## Carry-Forward / Deferred

- **Task 9 — customizer provider.** A `useAppearanceSettingsQuery` hook
  + provider that watches the `appearanceSettings` query and calls
  `loadFromServer(draftFields)` to seed the store on mount and re-sync
  after mutations. Currently, the store seeds from
  `DEFAULT_APPEARANCE_DRAFT` (the constants in the store file) on first
  mount — not from the server. This means the toolbar's Save/Publish
  will overwrite the server's draft with the defaults on the very first
  click if the user hasn't edited anything. The provider will fix this
  by loading the actual server draft before the user can save.

- **Task 9 — autosave.** The store's JSDoc mentions "autosave is owned
  by a provider `useEffect` (design §8) which calls `saveAppearanceDraft`
  via `@apollo/client/react`'s `useMutation`, then `markSaved()` on
  success." The toolbar's Save Draft button is a manual save; the
  autosave provider will debounce-save on `dirty` changes. Both can
  coexist (manual save is a no-op if autosave already saved).

- **Unsaved-changes guard on Exit.** Currently, clicking Exit
  immediately strips `?customize=1` from the URL. If `dirty` is true,
  the user loses their unsaved edits (the store state is preserved in
  memory, but navigating away or refreshing clears it). A future
  enhancement could add a `beforeunload`-style confirm dialog when
  `dirty` is true. Deferred to Task 9 or a follow-up.

- **Keyboard shortcuts.** The prototype's Undo/Redo tooltips mention
  "Ctrl+Z" / "Ctrl+Shift+Z". The current implementation does NOT bind
  keyboard shortcuts — only the icon buttons work. A `useEffect` with
  `window.addEventListener("keydown", ...)` could add this; deferred to
  keep the toolbar focused on the visual controls.

- **Mobile density.** The toolbar renders the same set of controls on
  mobile and desktop. On a 360px-wide phone, the chip + 2 icon buttons +
  3 text buttons + hint + exit button may overflow. The hint is hidden
  on `xs` (`display: { xs: "none", sm: "block" }`), but the text buttons
  remain. A mobile-specific layout (e.g. collapsible menu via `Menu`)
  can be added in a follow-up if user testing reveals overflow.
