# Task 9.3 — Settings "Export JSON" Feature

## Summary

Implemented the **Export JSON** button (AC-28) on both the
`AppearanceSettingsTab` (Settings form view) and the `CustomizeToolbar`
(customizer overlay). Clicking the button serializes the in-memory
appearance draft to a pretty-printed JSON document with a `$schema`
header pointing to the canonical JSON Schema from Task 9.1, then
triggers a browser download of `appearance-settings.json`.

A shared, testable helper
(`frontend/common/views/dashboard/appearance/shared/exportAppearanceJson.ts`)
houses the serialization + download logic so both consumers call the
exact same code path — no duplicated download plumbing between the tab
and the toolbar. The helper exposes `buildAppearanceSettingsJson` (pure
string builder, unit-testable without a DOM) and `exportAppearanceJson`
(side-effectful browser download).

## Requirements Coverage

- **AC-28** — "Export JSON" button on `AppearanceSettingsTab` and
  `CustomizeToolbar` exports a valid `appearance-settings.json` file
  with a `$schema` header.
  - The exported JSON object includes `$schema:
    "./shared/schemas/appearance.schema.json"` as the **first key**
    (declared first in the `AppearanceSettingsJson` interface so
    object-literal key ordering puts it at the top of the serialized
    output). VS Code (and any JSON-Schema-aware editor) reads this
    header on file open and auto-validates + offers property/enum
    autocomplete against the Task 9.1 schema.
  - The filename `appearance-settings.json` matches the
    `*appearance*.json` glob registered in `.vscode/settings.json`
    (Task 9.1) — so even if a user strips the `$schema` header, the
    file still gets schema validation when opened inside the repo.
  - The exported payload structurally matches `AppearanceFields` from
    `backend/types/appearance.types.ts` (per-mode colors + 5 scalar
    fields), satisfying the schema's `required` + `additionalProperties:
    false` constraints.

   (~140 lines, 0 runtime deps beyond `logger`)
   - Sibling of the existing `uploadAppearanceLogoFile.ts` (Task 7) —
     same directory, same "shared appearance helper" pattern.
   - Exports three symbols:
     - **`AppearanceSettingsJson`** — interface describing the exported
       document shape (`$schema` + the 6 `AppearanceFields` keys).
       Declared with `$schema` first so it serializes first.
     - **`buildAppearanceSettingsJson(draft): string`** — pure
       serializer. Coerces `logoUrl: undefined` → `null` (the codegen
       `AppearanceDraftInput.logoUrl` is `string | null | undefined`,
       but the schema's `required: ["logoUrl", …]` constraint demands
       the key be present; `JSON.stringify` drops `undefined` values,
       so coercion is mandatory for schema validity). Returns
       pretty-printed JSON (2-space indent) with a trailing newline
       (POSIX file convention).

       trigger. Wraps the JSON in a `Blob` (`application/json;charset=utf-8`
       MIME so the OS recognizes the file type), mints a temporary
       `URL.createObjectURL`, creates an invisible `<a download>`
       element, clicks it, then revokes the URL. Guarded by
       `typeof document === "undefined"` for SSR/test safety.
   - **SSR safety**: the `"use client"` directive + the `typeof document`
     guard mean the module can be imported from a server component (e.g.
     if a future server action wants to reuse `buildAppearanceJson`) —
     only `exportAppearanceJson` is browser-only.
   - **No toast on download**: the browser's native download UI is the
     confirmation. The tab does fire a success toast (because the tab's
     other actions all toast); the toolbar does not (matching the
     toolbar's existing pattern where Save/Publish/Reset toast but
     Undo/Redo do not).

## Design Decisions

### Why a shared helper instead of inline `Blob` logic in each consumer?

- **DRY**: the download plumbing (Blob creation, objectURL minting,
  invisible `<a>` click, URL revocation, Safari-deferred revocation)
  is ~25 lines of side-effectful browser code. Duplicating it in both
  the tab and the toolbar would be a `jscpd` duplicate-code smell and
  a maintenance burden (e.g. if we later want to add a `Content-
  Disposition` fallback for Safari < 14).
- **Testability**: `buildAppearanceSettingsJson` is a pure function
  (string in, string out, no DOM). Extracting it lets a future unit
  test assert the serialized shape — including the `$schema` header,
  `logoUrl: null` coercion, key ordering, and trailing newline —
  without mocking `document` / `URL.createObjectURL` / `Blob`.
- **Consistency**: both consumers serialize the draft identically, so
  an exported file from the tab is byte-identical to one from the
  toolbar (same `$schema`, same key order, same indentation). A user
  who exports from the tab and re-imports (future Task) gets the same
  file a user who exports from the toolbar gets.

### Why `$schema: "./shared/schemas/appearance.schema.json"` (relative path)?

- The Task 9.1 outcome recommended this exact value: "the exported
  `appearance-settings.json` should include a `$schema` header
  (`"$schema": "./shared/schemas/appearance.schema.json"`) so editors
  auto-validate exported files."
- Relative (not absolute) so the export resolves correctly regardless
  of where the repo lives on disk (developer machine vs. CI vs.
  production deploy).
- VS Code resolves `$schema` relative paths from the JSON file's
  location, so a file saved at `<repo>/appearance-settings.json`
  resolves `./shared/schemas/appearance.schema.json` correctly.
- The Task 9.1 `.vscode/settings.json` `json.schemas` glob
  (`*appearance*.json`) is the fallback for files without a `$schema`
  header or files opened outside the repo.

### Why coerce `logoUrl: undefined` → `null`?

- The codegen `AppearanceDraftInput.logoUrl` type is
  `string | null | undefined` (the GraphQL input type allows omitting
  the field entirely).
- The JSON Schema (Task 9.1) declares `logoUrl` as
  `type: ["string", "null"]` AND lists it in `required`. `undefined`
  is not a valid JSON value — `JSON.stringify` drops keys whose value
  is `undefined`, which would produce a file missing the `logoUrl`
  key entirely, failing the schema's `required` constraint.
- Coercing to `null` (the schema-accepted "no logo" sentinel) ensures
  the exported file always validates.

### Why no toast in the toolbar but a toast in the tab?

- The toolbar's existing pattern: Undo/Redo (local state changes) →
  no toast; Save Draft/Publish/Reset (network mutations) → toast.
  Export is a local browser action (no network), so it follows the
  Undo/Redo pattern (no toast). The browser's native download UI is
  the user feedback.
- The tab's existing pattern: every action bar button (Save Draft,
  Publish, Reset) shows a toast. Export follows that pattern for
  consistency within the tab — the user clicking "Export JSON" in the
  sparse action bar expects visible feedback.

### Why a `Button` (not `IconButton`) in the toolbar?

- The toolbar has enough horizontal space (48px tall, full-width) for
  one more small text button. A labeled button is more discoverable
  than a lone download icon — a first-time admin clicking through the
  customizer would not immediately recognize a download icon as
  "Export JSON".
- The button matches the existing "Reset to Defaults" button's style
  (`size="small" variant="outlined" color="inherit" startIcon={...}`)
  for visual consistency.

### Manual verification of exported JSON shape

The serialized output for the default draft (`DEFAULT_APPEARANCE_DRAFT`
from `appearancePreviewStore`) would be:

```json
{
  "$schema": "./shared/schemas/appearance.schema.json",
  "colors": {
    "light": {
      "primaryMain": "#0D9488",
      "secondaryMain": "#4F46E5"
    },
    "dark": {
      "primaryMain": "#2DD4BF",
      "secondaryMain": "#818CF8"
    }
  },
  "logoUrl": null,
  "siteName": "Siraj",
  "siteTitle": "Siraj",
  "siteDescription": "Siraj education management",
  "defaultColorScheme": "dark"
}
```

- `$schema` is the first key (object-literal declaration order).
- `logoUrl` is `null` (not omitted, not `undefined`).
- 2-space indent, trailing newline (POSIX file convention).
- Passes the Task 9.1 JSON Schema validation (all `required` keys
  present, all values match the schema constraints).
