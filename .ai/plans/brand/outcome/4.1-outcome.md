## Design adherence

### §9 — Hook behavior

- Reads `draft.colors[activeMode].primaryMain` / `secondaryMain` (the two atomic
  primitives per decision #2) via the exported `readActiveModeColors` helper.
- Writes `--mui-palette-primary-main` + `--mui-palette-secondary-main` as inline
  CSS vars on `document.documentElement` (inline styles win over MUI's baked
  `:root[data-mui-color-scheme="..."]` stylesheet rules — same specificity,
  inline wins).
- The vars are written on `<html>` (NOT under a `[data-mui-color-scheme="..."]`
  selector) so they remain mode-agnostic when the admin swaps the live mode via
  `useColorScheme().setMode()` (which toggles the `data-mui-color-scheme`
  attribute on `<html>`).
- Cleanup: on unmount or when `enabled` flips to false, `clearAppearanceCssVars`
  removes both vars so the production MUI stylesheet resumes control.
- Separated the "write on color change" effect (no cleanup — next write
  overwrites in place) from the "clear on disable/unmount" effect (cleanup tied
  to `isActive`, not the colors) — this avoids a 1-frame flash of the production
  palette between color picks.

### Decision #3 — Selective `nativeColor: true`

- `AppearanceCustomizeContext` exposes `nativeColorEnabled: boolean`. The
  default value is `false` (outside the customize scope) so consumers safely
  no-op when the overlay is not mounted.
- `<AppearanceCustomizeScope>` sets `nativeColorEnabled: true` for its subtree.
  The actual `cssVariables.nativeColor: true` flag on the MUI theme is set by
  the overlay's theme swap (Phase 6 — depends on `?customize=1` URL parsing +
  the dashboard shell layout per implementation.md §10). This Provider owns the
  React Context + the fallback stylesheet only.
- The hook auto-detects enable state via `useContext(AppearanceCustomizeContext)`
  and accepts an `enabled?: boolean` override (e.g. for Storybook / tests).

### Decision #3 — `@supports` fallback

- The `NATIVE_COLOR_FALLBACK_CSS` constant in
  `AppearanceCustomizeScope.tsx` ships a `@supports not (color: rgb(from black r g b))`
  block scoped to `[data-appearance-customize="true"]`.
- The fallback aliases `--mui-palette-primary-light` / `-dark` /
  `-contrastText` (and the matching secondary tokens) to existing MUI CSS vars
  (`var(--mui-palette-primary-main)` for light/dark, `var(--mui-palette-text-primary)`
  for contrastText). No hardcoded hex colors — satisfies `frontend/AGENTS.md`
  "NO hardcoded colors".
- Injected via `<style dangerouslySetInnerHTML>` with a
  `biome-ignore lint/security/noDangerouslySetInnerHtml` comment + rationale,
  mirroring the pattern in `frontend/common/lib/emotion-cache.tsx` (static CSS
  string, no user input).

## Future wiring (Phase 6 — overlay conditional)

Phase 6 (`?customize=1` overlay) is expected to:

1. Mount `<AppearanceCustomizeScope>` around the overlay subtree (Phase 6.1).
2. Call `useAppearanceCssVars({ draft, activeMode })` from a top-level overlay
   component (Phase 6.2 — `CustomizeToolbar` or `CustomizeSidebar`).
3. Swap the MUI theme to one with `cssVariables: { nativeColor: true, ... }`
   when `?customize=1` is active (Phase 6.1 — likely a new
   `createAppearanceCustomizeTheme` wrapper around `createAppCssVarsTheme` in
   `frontend/common/providers/theme/theme.ts`, plus an overlay-scoped
   `CssVarsProvider` re-mount). The `AppearanceCustomizeScope` Provider doesn't
   own this theme swap — it only owns the Context + the fallback CSS.

The Zustand store (Task 4 — `appearancePreviewStore.ts`) is not yet created
(Phase 4 task 4 is pending). The hook is designed to accept `draft` +
`activeMode` as args so it works with any source — the store will pass these
when wired into the overlay component.

## Issues / open questions

- **Theme swap is deferred to Phase 6.** `<AppearanceCustomizeScope>` does NOT
  itself flip `cssVariables.nativeColor: true` on the MUI theme — that requires
  a `CssVarsProvider` re-mount with a customized theme, which is a Phase 6
  concern (depends on `?customize=1` URL parsing + dashboard shell layout).
  This is by design per implementation.md §9/§10. The hook + context +
  fallback CSS are the building blocks; the wiring happens in Phase 6.
- **Task 4 (Zustand store) not yet done.** The hook accepts `draft` +
  `activeMode` as args (no direct store dependency), so it works whether the
  store passes them in or a test stub does. When the store lands, the overlay
  component will read `draft` + `isDark` from the store and pass them to the
  hook.
- **No consumer hook (`useAppearanceCustomize`) exported.** Following the
  existing `ThemeContext.ts` convention (which exports only the Context — the
  consumer hook `useThemeMode` lives in `frontend/common/hooks/`). If Phase 6
  needs a dedicated consumer hook, it can be added as
  `frontend/common/hooks/useAppearanceCustomize.ts` mirroring `useThemeMode.ts`.
