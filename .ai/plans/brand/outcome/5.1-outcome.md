# Task 5.1 — Settings i18n strings for `appearance` tab label + form view

## Summary

Added a new `appearance` sub-namespace to the compile-time settings locale
(`shared/locale/types/dashboard/settings` + `en` + `ar` impls) per
implementation.md §14 and AC-24. The sub-namespace covers:

1. **`tabs.appearance`** — the tab label (`"Appearance"` / `"المظهر"`) added to
   the existing flat-string `tabs` block in `SettingsLabels` (mirrors the
   pattern of `tabs.general` / `tabs.session` / etc.).
2. **`appearance: SettingsAppearanceTabLabels`** — a new top-level sub-namespace
   on `SettingsLabels` carrying the 26 form-view strings required by Task 5.2
   (`AppearanceSettingsTab`): hero title/subtitle, status badges (Published /
   Draft / No-published), last-published + draft-updated interpolation
   functions, "Enter Customize Mode" CTA + hint, action-bar buttons
   (Save Draft / Publish Now / Reset to Defaults / Export JSON), toast success
   and error messages for each action, the reset-confirmation dialog strings,
   and a permission-banner fallback.

The customizer overlay strings (`customize.enterMode`, `customize.undo`, etc.
listed in implementation.md §14) are scoped to Task 9 per the 3.1-outcome.md
carry-forward note and are NOT added here — this task covers only the in-tab
form view per the task spec ("Add `appearance` tab label + form view strings").

## Requirements Coverage

- **AC-24** — All user-facing strings in the Appearance tab come from the
  compile-time translation system. No hardcoded UI strings introduced for the
  form view. Strings are typed via `SettingsAppearanceTabLabels` so missing
  keys surface as TypeScript errors at build time.

## Design Adherence

### Pattern matching (per `shared/AGENTS.md` §Translation System)

- Each tab has a dedicated `*TabLabels` interface in
  `shared/locale/types/dashboard/settings/<tab>.ts` and a matching
  implementation file in `en/` + `ar/`. Mirrored this pattern for
  `appearance.ts`.
- The `tabs` block in `SettingsLabels` remains a flat record of `string`
  values — added `readonly appearance: string;` to match (no nested
  `{label, description}` shape — that was an optional alternative listed
  in the task spec, but the existing convention is flat strings, so the
  flat-string pattern was used for consistency).
- The top-level `SettingsLabels` interface adds one `readonly <tab>:
  <TabLabels>` field per tab — added `appearance: SettingsAppearanceTabLabels`
  in the same position (alphabetical, before `environment`).
- The `en`/`ar` implementations import the type from
  `@/shared/locale/types/dashboard/settings/appearance` and export a
  const named `dashboardSettingsAppearance<En|Ar>` matching the existing
  `dashboardSettingsSiteContent<En|Ar>` / `dashboardSettingsGeneral<En|Ar>`
  convention.

### Interpolation pattern (per `shared/AGENTS.md` §Interpolation Pattern)

- `lastPublishedBy` and `draftUpdated` are typed as `(arg: string) =>
  string` functional keys — replaces ICU `{placeholder}` strings with
  TypeScript template-literal functions, providing compile-time safety
  and IDE autocomplete on argument shape.
- The Arabic implementation uses the same template-literal form, with the
  placeholders positioned RTL-correct for Arabic grammar
  (`آخر نشر ${when} بواسطة ${actor}` — "Last published ${when} by
  ${actor}").

### String selection (per prototype `prototype/index.html`)

The 26 fields were chosen to cover exactly the form-view elements rendered in
the prototype:

- Hero: page-title + page-subtitle (lines 278-279 of prototype).
- Status row: "✓ Published" / "✎ Draft has changes" badges + "Last published
  2 days ago by administrator" + "Draft updated just now" meta (lines 294-300).
- CTA: "🎨 Enter Customize Mode" button (line 300).
- Action bar: "💾 Save Draft" / "✦ Publish Now" / "↺ Reset to Defaults"
  (lines 515-517) + "Export JSON" per implementation.md §17.
- Confirmation dialog + toasts: standard success/error strings for the three
  actions (no prototype strings — synthesized from existing `siteContent`
  pattern).
- `noPermission`: fallback banner shown by Task 5.2 when
  `SETTINGS_APPEARANCE_MANAGE` is missing but `SettingsView` is present.

## Issues / Open Questions

- **Customizer strings deferred to Task 9.** The `customize.*` sub-namespace
  is not yet created; when Task 9 lands it should either (a) extend
  `SettingsAppearanceTabLabels` with a `customize: { ... }` block, or
  (b) create a separate `SettingsAppearanceCustomizeLabels` interface
  mounted as `appearanceCustomize: SettingsAppearanceCustomizeLabels` on
  the dashboard namespace (option (b) is cleaner if the customizer is
  also mounted outside the Settings route — e.g. as a top-level
  dashboard overlay). Left for Task 9 to decide based on its scope.
- **Tab label shape.** The task spec mentioned "with label + description
  fields if that's the pattern". The existing pattern uses flat strings
  (`tabs.general: "General"`), so `tabs.appearance: "Appearance"` was
  used for consistency. If a description is later needed for the tab
  tooltip, a separate `tabDescriptions` record could be added (none of
  the sibling tabs have descriptions today).
