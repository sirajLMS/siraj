## Implementation details

### Pattern mirrored
The file mirrors `7b-settings-permissions-data.sql` and `9b-cron-permissions-data.sql`:

1. **Trigger toggle (disable)** — `DO $$ ... ALTER TABLE permissions DISABLE
   TRIGGER trg_protect_system_permissions; ... EXCEPTION WHEN OTHERS THEN RAISE
   NOTICE ...` so `is_system = true` INSERTs are allowed. Wrapped in `DO $$ ...
   EXCEPTION` so re-runs do not fail if the trigger is already disabled.
2. **INSERT into `permissions`** — single row:
   - `id` = `gen_random_uuid()`
   - `key` = `settings.appearance_manage`
   - `resource` = `settings` (shares the `settings` resource with other
     `settings.*` permissions so it sorts with them in the catalog)
   - `action` = `appearance_manage`
   - `description` = `{"ar": "إدارة مظهر الموقع والهوية البصرية", "en": "Manage site appearance and branding"}`::jsonb
   - `category` = `{"ar": "الإعدادات", "en": "Settings"}`::jsonb
     (same `Settings` category used by all other `settings.*` siblings in `7b`)
   - `is_system` = `true` (only seedable via migration; cannot be deleted from UI)
   - `ON CONFLICT (key) DO UPDATE SET` refreshes resource/action/description/
     category/is_system on every run → fully idempotent.
3. **Trigger toggle (re-enable)** — same `DO $$ ... EXCEPTION` shape.
4. **Group grants** — `INSERT INTO group_permissions (group_id, permission_id)
   SELECT g.id, p.id FROM permission_groups g, permissions p WHERE g.slug IN
   (super_admin, academy_admin) AND p.key = settings.appearance_manage
   ON CONFLICT DO NOTHING;` — idempotent, matches AC-4 exactly.

### Category choice
The plan instructed `{category}` = `settings` (same as other settings
permissions). The `7b` siblings store category as a localized jsonb object
`{"ar": "الإعدادات", "en": "Settings"}`, NOT a bare string. We mirror that
exact shape so the appearance permission renders in the same Settings
category bucket of the permissions catalog.

### Filename choice & migration ordering
The plan suggested `7c-appearance-permissions-data.sql`. A `7c-quota_permissions_enum.sql`
file already exists, but the auto-bundler in `backend/db/scripts/applyCustomMigrations.ts`
sorts files alphabetically and `7c-appearance...` < `7c-quota...` lexically
(`a` < `q`). Each new/changed custom SQL file is bundled into its OWN drizzle
migration folder (per-file transaction), so the two `7c-*` files do not
conflict — they become two separate incremental drizzle folders. This matches
the existing on-disk pattern (e.g. `20260803041719_custom_7d-quota_permissions_data`
is a separate folder from `20260803041721_custom_9a-cron-permissions-enum`).

The appearance data SQL does NOT depend on the `7c-quota_permissions_enum.sql`
or any `app_permission` PG enum cast — it inserts the permission key as plain
text into `permissions.key`, exactly like `7b` does. So migration ordering
relative to `7c-quota_permissions_enum.sql` is irrelevant.
