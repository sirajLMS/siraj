# Task 9.7 — Multi-Admin Optimistic Concurrency Control

## Summary

Added an `expectedUpdatedAt` optimistic-concurrency guard to the
`saveAppearanceDraft` and `publishAppearance` mutations, and wired the
frontend `CustomizeToolbar` to surface a Reload / Overwrite / Cancel
dialog when the server reports an `APPEARANCE_CONFLICT` error.

This satisfies **AC-33** (multi-admin optimistic concurrency control):
two admins editing the single-row `appearance_settings` entity
concurrently can no longer silently clobber each other. The second
admin to save/publish receives a structured GraphQL error carrying the
server's current `updatedAt`, and the UI offers three explicit
resolution paths (reload from server / force-overwrite / dismiss).

## Requirements Coverage

- **AC-33** — Optimistic concurrency on `saveAppearanceDraft` and
  `publishAppearance`:
  - Backend: `AppearanceSettingsService.saveDraft` and
    `AppearanceSettingsService.publish` accept an optional
    `expectedUpdatedAt: string` (ISO timestamp). When provided and not
    equal to the current row `updatedAt`, they throw a typed
    `AppearanceConflictError` carrying the server's actual
    `updatedAt` (`serverUpdatedAt` field). When omitted (the
    "Overwrite" escape hatch), the check is skipped and the write
    proceeds.
  - The Pothos resolver wraps each mutation in a `runAppearanceMutation`
    helper that translates `AppearanceConflictError` into a
    `GraphQLError` with `extensions.code = "APPEARANCE_CONFLICT"` and
    `extensions.serverUpdatedAt = <iso>` so the frontend can either
    refetch (Reload) or retry with the new value (Overwrite) without an
    extra round-trip.
  - Frontend: `CustomizeToolbar` tracks the server's last-known
    `updatedAt` from the `appearanceSettings(draft: true)` query and
    passes it as `expectedUpdatedAt` on every Save Draft / Publish
    call. On conflict, a MUI `Dialog` opens with three buttons:
      - **Reload** — calls `refetchAppearance()` and reseeds the local
        store via `loadFromServer`, discarding the user's unsaved
        edits and adopting the server's latest draft.
      - **Overwrite** — re-invokes the original mutation with
        `expectedUpdatedAt: undefined`, bypassing the conflict check
        and force-pushing the user's local edits.
      - **Cancel** — dismisses the dialog; local edits are preserved
        untouched (the user can still undo/redo or re-attempt later).

## Design Adherence

### Why a typed Error subclass (not a string code in a thrown Error)

The codebase has an established pattern of typed service-layer Error
subclasses carrying a stable `code` field — e.g.
`SiteContentValidationError` in `backend/services/storage/site-content.service.ts`.
`AppearanceConflictError` follows the same shape (`readonly code`,
`readonly serverUpdatedAt`, named `Error` subclass) so callers and the
Pothos resolver can branch on `instanceof` / `isAppearanceConflictError`
without regex-matching `message`.

### Why `expectedUpdatedAt` is optional (not required)

The frontend "Overwrite" path needs a way to bypass the conflict check
after the user explicitly chooses to force their version through.
Making `expectedUpdatedAt` optional is the documented escape hatch —
when omitted, `assertExpectedUpdatedAt` is a no-op. The same trick
lets the seeding path (no existing row) skip the check, since there's
no prior version to conflict with.

### Why the conflict extension includes `serverUpdatedAt`

The frontend could refetch the query to learn the new `updatedAt`, but
that's an extra round-trip after a failure. Including
`serverUpdatedAt` in the GraphQL error `extensions` lets the
"Overwrite" path retry immediately with the new value (although the
current implementation uses the simpler "omit `expectedUpdatedAt`"
approach — see Carry-Forward). The field is also useful for telemetry
and debugging.

### Why `useQuery` in the toolbar (not just mutations)

The toolbar needs to know the server's last-known `updatedAt` to pass
as `expectedUpdatedAt` on the very first Save Draft / Publish click.
Reading the query result via `useQuery` gives us this without coupling
the toolbar to the (not-yet-existent) Task 9 customizer provider.
Apollo cache normalization keeps `serverUpdatedAt` in sync after each
successful mutation because the mutations return the same
`AppearanceSettings` row with `id` (the cache key) — so the query
result auto-updates and the next mutation sees the new `updatedAt`.

### Type-safe fragment → input coercion (no `as` cast)

The codegen `avoidOptionals: true` config makes every field on
`AppearanceSettingsFieldsSelectionFragment_draftFields` nullable, but
the store's `loadFromServer` expects the non-nullable
`AppearanceDraftInput`. The `toAppearanceDraftInput` builder performs
runtime checks on each required field and constructs a fresh
`AppearanceDraftInput` object — no `as` cast, satisfies the
`no-unsafe-type-assertion` oxlint rule.

### Conflict dialog placement (alongside Reset confirm)

The new conflict `Dialog` lives in `CustomizeToolbar` next to the
existing Reset confirmation dialog. Both use the same MUI `Dialog` +
`DialogTitle` + `DialogContent` + `DialogActions` pattern. The conflict
dialog has three buttons (Cancel / Reload / Overwrite) vs. the Reset
dialog's two (Cancel / Reset) — the warning-colored Overwrite button
matches the existing Publish button's `color="warning"` semantics
("destructive / force-through action").

## Decisions

- **Typed `AppearanceConflictError` over a bare `throw new Error(...)`.**
  Matches the `SiteContentValidationError` pattern. The stable `code`
  field lets the Pothos resolver branch on `instanceof` and the
  frontend branch on `extensions.code` without parsing `message`.

- **`expectedUpdatedAt` optional, not required.** Provides the
  "Overwrite" escape hatch (frontend passes `undefined` to bypass the
  check) AND naturally handles the seeding path (no prior row to
  compare against). A required parameter would have forced every
  non-conflict-aware caller (tests, internal scripts) to pass `null`
  or a sentinel.

- **`serverUpdatedAt` in GraphQL error extensions.** Avoids an extra
  refetch round-trip when the user clicks "Overwrite". The current
  implementation uses the simpler "omit `expectedUpdatedAt`" approach
  for Overwrite (which doesn't need `serverUpdatedAt`), but the field
  is included for future use (see Carry-Forward).

- **`runAppearanceMutation` helper over inline try/catch in each
  resolver.** Two mutations need the same translation
  (`AppearanceConflictError` → `GraphQLError` with the right
  extension code). A helper avoids drift and keeps the resolver bodies
  focused on the service call.

- **Conflict dialog lives in `CustomizeToolbar` (not a separate
  component).** The dialog state (`conflictOpen`, `conflictRetry`) is
  tightly coupled to the mutation handlers — extracting it would
  require prop-drilling the retry closure. The toolbar already owns
  the Reset confirm dialog with the same shape, so the conflict
  dialog fits naturally alongside.

- **Reload uses `refetchAppearance()` + `loadFromServer()` instead of
  relying on Apollo cache normalization alone.** Apollo cache would
  update the query result after a mutation, but the *store* would
  still hold the user's local draft. The Reload path must explicitly
  reseed the store from the server response to actually discard local
  edits.

- **`toAppearanceDraftInput` builder instead of `as AppearanceDraftInput`.**
  The codegen fragment type has all-nullable fields (per
  `avoidOptionals: true`), so a direct cast would trip oxlint's
  `no-unsafe-type-assertion` rule. The builder performs runtime checks
  on each required field and constructs a fresh object — type-safe and
  explicit about which fields are required.

- **Use `serverUpdatedAt` from the conflict error for the Overwrite
  retry.** The current Overwrite path uses `expectedUpdatedAt:
  undefined` to bypass the check. An alternative would be to extract
  `serverUpdatedAt` from the Apollo error's `graphQLErrors[0].extensions`
  and pass it as the new `expectedUpdatedAt` on retry — this would
  re-enable the conflict check on the retry (catching a *third*
  concurrent edit). Deferred because the simpler "omit" approach is
  sufficient for the common case (two admins, one conflict).

- **Customizer provider owns the `appearanceSettings` query.** The
  toolbar currently runs its own `useQuery`. When the Task 9.x
  customizer provider lands, it should own this query and pass
  `serverUpdatedAt` down via context/prop to avoid duplicate

  existing `SettingsAppearanceTabLabels` namespace (alongside the
  Reset confirm strings). If Task 9 introduces a broader `customize.*`

- **Telemetry on conflict resolution choice.** Currently, the
  Reload/Overwrite/Cancel choice is not logged. A future enhancement
