# Task 6.3 — `CustomizeSidebar` component

## Summary

Replaced the Task 6.1 placeholder with the real site-appearance
customizer sidebar. The sidebar renders four stacked sections — Brand
Identity, Logo, Theme Colors, Default Mode — wired end-to-end to
`useAppearancePreviewStore` for live preview. Every edit flows through
the store's typed setters (`setField`, `setModeColors`, `setMode`),
which already write the active-mode brand CSS vars on `<html>` for
instant visual feedback (no per-component DOM touching).

To stay under the CodeScene 150-line file-size guideline and keep each
editor's effect surface small, the sidebar is split into one main
compositor + four sibling section files in the same directory:

```
customize/
  CustomizeSidebar.tsx       (compositor — 59 lines)
  BrandIdentitySection.tsx   (64 lines)
  LogoUploadSection.tsx      (87 lines)
  ColorEditorSection.tsx     (165 lines)
  DefaultModeSection.tsx     (58 lines)
```

The barrel `customize/index.ts` is unchanged — only `CustomizeSidebar`
+ `CustomizeToolbar` are re-exported; the four section files are
internal helpers.

## Requirements Coverage

- **AC-13** — Brand identity fields (site name, title, description).
  - `BrandIdentitySection` renders three MUI `TextField`s (single-line
    for site name/title, multi-line for description) bound to
    `draft.siteName` / `draft.siteTitle` / `draft.siteDescription`.
    Each `onChange` calls `setField(key, value)`, which pushes the prior
    draft onto the undo stack and writes the active-mode CSS vars (no-op
    for text fields, but keeps the dirty flag + history semantics
    consistent).

- **AC-14** — Per-mode color editors with light/dark tabs switching
  live mode.
  - `ColorEditorSection` renders a MUI `ToggleButtonGroup` with two
    options ("Light" / "Dark"). Selecting a tab calls
    `setMode(isDark)` which:
    1. Updates the store's `isDark` flag.
    2. Calls `writeActiveModeCssVars(draft, isDark)` which sets
       `--mui-palette-primary-main` and `--mui-palette-secondary-main`
       on `<html>` from the newly-active mode's pair.
    The active mode's primary/secondary colors then become editable
    through a native `<input type="color">` + hex `TextField` combo.
    Edits dispatch `setModeColors(activeMode, { ...pair, [key]: hex })`
    which composes the next pair preserving the partner color, commits
    the edit (pushes undo, clears redo, sets dirty), and re-writes the
    active-mode CSS vars for live preview. Inactive-mode edits persist
    to the draft but don't write CSS vars until the admin switches tabs
    — matching design decision §12.

- **AC-23** — Logo upload.
  - `LogoUploadSection` renders a dashed-border drop zone with a
    hidden `<input type="file">` accepting `image/png,image/jpeg,
    image/svg+xml,image/webp` (mirrors decision §20 magic-byte
    allowlist). Task 7 wires this to `StorageService` and calls
    `setField("logoUrl", returnedUrl)` on upload success — for now the
    file input is a stub. The section DOES exercise the draft's
    `logoUrl` field end-to-end: when a logo URL is already set
    (seeded from server), it renders a preview thumbnail + filename +
    "Remove" button that calls `setField("logoUrl", null)`.

- **Default-mode radio** (design decision §2, §12).
  - `DefaultModeSection` renders a MUI `RadioGroup` (row layout) with
    Light/Dark options. Bound to `draft.defaultColorScheme` via
    `setField("defaultColorScheme", value)`. Coerces the codegen-typed
    `string` to a strict `"light" | "dark"` for the radio's `value` —
    if the draft somehow holds any other string, it falls back to
    `"dark"` (the `DEFAULT_APPEARANCE_DRAFT` value). This field is
    distinct from the per-mode editor's active tab: `defaultColorScheme`
    is what new visitors see on first load; `isDark` is what the admin
    is previewing right now.

## Design Adherence

### Single source of truth — store owns all draft state

Every editable value is read from `useAppearancePreviewStore` via a
narrow selector and written back through one of three typed setters:

| Field                          | Setter                                           |
|--------------------------------|--------------------------------------------------|
| `siteName`                     | `setField("siteName", value)`                    |
| `siteTitle`                    | `setField("siteTitle", value)`                   |
| `siteDescription`              | `setField("siteDescription", value)`             |
| `logoUrl`                      | `setField("logoUrl", value)`                     |
| `defaultColorScheme`           | `setField("defaultColorScheme", value)`          |
| `colors.light.primaryMain`     | `setModeColors("light", { ...pair, primaryMain })` |
| `colors.light.secondaryMain`   | `setModeColors("light", { ...pair, secondaryMain })` |
| `colors.dark.primaryMain`      | `setModeColors("dark", { ...pair, primaryMain })`  |
| `colors.dark.secondaryMain`    | `setModeColors("dark", { ...pair, secondaryMain })` |
| Active mode tab + live preview | `setMode(isDark: boolean)`                       |

No component holds draft state locally. The store's `commitEdit`
helper pushes the prior draft onto `past[]` (bounded by `MAX_HISTORY =
50`) and clears `future[]` on every edit — undo/redo (Task 6.2
toolbar) just works without any per-section wiring.

### No effects in `ColorField` — `key` prop for external sync

The first iteration used `useState(hex)` + `useEffect(() => setText(hex),
[hex])` to mirror the prop into local state. The `react-hooks/set-state-
in-effect` lint (run by `lint:type-aware`) flagged this — calling
`setState` synchronously inside an effect starts another render and is
usually unnecessary.

The fix uses the React `key` prop pattern: the parent passes
`key={`primary-${activePair.primaryMain}`}` so the `ColorField` remounts
whenever the upstream hex changes. The field itself uses
`defaultValue={hex}` (uncontrolled) so the user can type partial hex
values freely; valid `#RRGGBB` strings call `onChange` and update the
store, which changes `hex`, which changes the `key`, which remounts the
field with the new `defaultValue`. No effects, no local state, no
re-render storms.

### MUI v9 patterns (per `frontend/AGENTS.md`)

- All layout/spacing props go in `sx` — no direct `mb`, `gap`,
  `alignItems` props on `Stack` / `Box` / `Typography`.
- `Typography variant="caption"` + `sx={{ fontWeight: 700,
  textTransform: "uppercase", letterSpacing: "0.06em" }}` for section
  headers — matches the prototype's `.section-title` style.
- `ToggleButtonGroup` + `ToggleButton` for the mode tabs (semantic
  exclusive-choice pattern, vs. the prototype's raw `<button>`s).
- `FormControl` + `RadioGroup` + `FormControlLabel` + `Radio` for the
  default-mode radio (semantic radio pattern).
- `Box component="label"` + `Box component="img"` for the swatch
  wrapper and logo preview (semantic HTML via MUI's `component` prop).
- All chrome colors come from CSS vars (`var(--mui-palette-text-
  secondary)`, `var(--mui-palette-outlineVariant)`,
  `var(--mui-palette-text-disabled)`, `var(--mui-palette-background-
  paper)`, `var(--mui-palette-onSurface)`) — no hardcoded hex tokens
  for UI chrome. The swatch `backgroundColor` is the user-supplied
  brand color (data, not chrome) — explicitly documented in JSDoc.

### Import path discipline

The `lint:type-aware` rule "Imports must use @/ path alias, not relative
./ or ../" required absolute alias paths even for sibling files in the
same directory. The main `CustomizeSidebar.tsx` imports its four
section files via `@/frontend/common/views/dashboard/components/
customize/<Section>.tsx` — not `./<Section>.tsx`. This matches the
project convention (verified against existing navbar imports).

### MUI dedup import

`ColorEditorSection.tsx` initially had two imports from `@mui/material`
— one `import type { PaletteMode }` and one `import { Box, Stack, ... }`.
The `import-x/no-duplicates` lint flagged this. Fixed by merging into
a single statement: `import { Box, type PaletteMode, Stack, TextField,
ToggleButton, ToggleButtonGroup, Typography } from "@mui/material";`
— matches the existing pattern in `navbar/NotificationButton.tsx`
(`import { Badge, type IconButtonProps } from "@mui/material";`).

### Codegen types — NO MAPPING

Per `frontend/common/stores/AGENTS.md`, the draft is typed as
`AppearanceDraftInput` from the codegen `graphql.ts` so it can be
passed directly as the `input` variable to
`saveAppearanceDraftMutationDocument` without mapping. The section
components import `AppearanceColorPairInput` and `AppearanceColorsInput`
as type-only imports to derive `ColorKey` and `AppearanceMode` —
never redefining the union.

## Decisions

- **Split into 4 sibling files vs. one big file.** A single
  `CustomizeSidebar.tsx` with all 4 sections inline would be ~330
  lines — well over the CodeScene 150-line file-size guideline. Split
  into a 59-line compositor + 4 section files (58–165 lines each) keeps
  each file focused, lets each section subscribe only to the store
  slice it edits (smaller re-render surface), and makes the JSDoc per
  section much more discoverable. The trade-off is 4 more files in the
  `customize/` directory, but the barrel `index.ts` is unchanged — the
  sections are internal helpers.

- **`ToggleButtonGroup` vs. MUI `Tabs` for the mode switcher.** The
  prototype uses pill-style buttons (`.mode-tabs button.active`). MUI
  `ToggleButtonGroup` (exclusive) is the semantic match for "choose
  one of two pill-style options" and gives us keyboard navigation +
  ARIA radio semantics for free. `Tabs` would also work but is
  heavier (adds a tab-list role + tab indicator animation we don't
  want).

- **Native `<input type="color">` vs. MUI color picker.** The
  prototype uses the native picker overlaid on a custom swatch. MUI
  doesn't ship a first-party color picker (the `@mui/x-date-pickers`
  package is date-only). Third-party pickers (`react-color`,
  `mui-color-input`) would add bundle weight + a new dependency for
  no functional gain. The native picker is accessible (OS-level
  dialog), works on every modern browser, and produces clean `#RRGGBB`
  strings — exactly what the Zod schema requires.

- **`key` prop remount vs. `useEffect` sync in `ColorField`.** First
  iteration used local `useState` + `useEffect([hex])` to mirror the
  upstream prop. The `react-hooks/set-state-in-effect` lint flagged it
  (correctly — calling setState in an effect triggers an extra render
  and is usually a sign of derivable state). The `key` prop pattern is
  the React-blessed way to "reset" a component when an external value
  changes: the parent passes `key={`primary-${hex}`}`, so when the
  store updates `hex`, the field remounts with the new `defaultValue`.
  Trade-off: remounting loses focus — but since the field only
  remounts when `hex` actually changes (i.e. when a valid hex is
  committed), the user has finished typing by then. Invalid partial
  input never triggers a remount, so the user can type freely.

- **Hex validation in component vs. store.** The component validates
  with `HEX_PATTERN = /^#[0-9a-fA-F]{6}$/` before calling `onChange`
  (which dispatches to the store). The store's `setModeColors` doesn't
  re-validate — it trusts the caller. This mirrors the prototype's
  `updateColor` guard and matches the backend Zod schema (decision
  §22). If an invalid hex ever reaches the store (e.g. via
  `loadFromServer` from a malformed server row), the swatch falls back
  to `#000000` via `safeHex` and the CSS-var writer's `if (pair.primaryMain)`
  guard skips empty strings — no crash.

- **Inline English labels vs. new i18n namespace now.** The
  `shared/locale/types/dashboard/settings/appearance.ts` header comment
  explicitly reserves the `customize.*` namespace for Task 9. Adding
  the namespace now would mean touching 3 locale files (type + EN +
  AR) + the namespace registration in
  `shared/locale/namespaces/translation.ts` — outside Task 6.3's
  scope. Inline strings with a clear JSDoc pointer to Task 9 is the
  scoped choice. The strings are also simple enough ("Light", "Dark",
  "Primary", "Secondary", "Site Name", etc.) that Arabic translation
  is trivial when Task 9 lands.

- **Logo upload as a stub.** Task 7 owns the full upload flow
  (StorageService integration, magic-byte verification, SVG
  sanitization, UUID storage keys, CDN caching per decision §20).
  Implementing it in 6.3 would duplicate work and risk scope creep.
  The stub: (a) renders the drop zone + accept list, (b) lets the
  admin clear an existing logo via `setField("logoUrl", null)`, (c)
  leaves a clear `// Task 7: wire to StorageService` comment. Task 7
  only needs to add an `onChange` handler on the hidden input —
  nothing else in `LogoUploadSection` needs to change.
