# Task 9.4 — Built-in Preset Themes Catalog

## Summary

Created the built-in preset theme catalog (decision §13) — 6 curated
light/dark brand-color pairs (`default`, `ocean`, `emerald`, `violet`,
`crimson`, `slate`) — and wired a `PresetSwatch` selector into both the
`CustomizeSidebar` (overlay) and `AppearanceSettingsTab` (Settings form
view). Clicking a preset dispatches
`useAppearancePreviewStore.setModeColors("light", preset.light)` and
`setModeColors("dark", preset.dark)`, which writes both per-mode pairs
into the draft and re-writes the active-mode brand CSS vars on `<html>`
for instant live preview + undo support (the store already pushes the
prior draft onto the undo stack on every edit).

## Requirements Coverage

- **AC-29** — Built-in preset theme catalog with one-click application.
  - `frontend/common/providers/theme/presets/index.ts` exports the
    `APPEARANCE_PRESETS` array (6 entries) + `AppearancePresetId`
    string-literal union + `findAppearancePreset(id)` lookup helper.
    Each preset has `{ id, name, light: {primaryMain, secondaryMain},
    dark: {primaryMain, secondaryMain} }` — structurally compatible
    with `PerModeColors["light" | "dark"]` from
    `backend/types/appearance.types.ts` (imported as `import type`).
  - Color sources (Material Design 2014 palette):
    - `default`  — Blue 700 / Indigo 500 (light); Blue 400 / Indigo 300 (dark).
    - `ocean`    — Cyan 800 / Cyan 600 (light); Cyan 400 / Cyan 200 (dark).
    - `emerald`  — Green 800 / Light Green 800 (light); Green 500 / Light Green 400 (dark).
    - `violet`   — Purple 700 / Pink 700 (light); Purple 300 / Pink 300 (dark).
    - `crimson`  — Red 800 / Orange 800 (light); Red 400 / Orange 400 (dark).
    - `slate`    — Blue Gray 700 / Blue Gray 500 (light); Blue Gray 400 / Blue Gray 200 (dark).
  - **CustomizeSidebar selector**: Added a new `PresetThemeSection`
    sibling section file (`frontend/common/views/dashboard/components/
    customize/PresetThemeSection.tsx`) and rendered it in
    `CustomizeSidebar` between `LogoUploadSection` and
    `ColorEditorSection` — so admins pick a preset to seed colors
    before fine-tuning with the per-mode color pickers.
  - **AppearanceSettingsTab selector**: Added a "Quick Presets" panel
    inside the Settings form view with a 3-column responsive grid of
    the same `PresetSwatch` cards (reused via export, no duplication).
    Clicking a preset writes the colors to the in-memory draft and
    shows a success toast — the admin then clicks "Enter Customize
    Mode" to refine, or "Publish Now" to make the preset live.

## Design Notes

- **No duplicated markup**: `PresetSwatch` is exported from
  `PresetThemeSection.tsx` and reused by `AppearanceSettingsTab.tsx`
  (the settings tab uses a 3-column grid + outlined-button style
  inherited from `ButtonBase`'s `sx` — visually consistent with the
  sidebar's 2-column grid despite the different layout density).
- **Live preview without entering customize mode**: clicking a preset
  on the Settings tab writes the brand CSS vars on `<html>` via the
  store's `writeActiveModeCssVars` helper, so the admin sees the
  color change across the entire dashboard instantly. The store's
  `isCustomizeMode` flag is NOT set by the preset click — the overlay
  only mounts when the URL has `?customize=1` (Task 6.1 owns that).
  Inline CSS vars persist on `<html>` until `clearActiveModeCssVars()`
  is called (currently only on `exitCustomizeMode`). This is the
  intended UX: "preview before you commit to editing."
- **Hex literals in the catalog** are NOT UI chrome tokens — they are
  user-selectable brand-color data, same exemption as
  `ColorEditorSection`'s color-picker swatches (see
  `frontend/AGENTS.md` "no hardcoded colors" rule). Documented in the
  catalog header.
- **`PerModeColors` import**: The catalog imports the canonical type
  from `@/backend/types/appearance.types` (Task 2.1) via `import
  type` only. No runtime backend code is pulled into the client
  bundle.

## Cross-file Dependencies

- **Reads (types only)**: `backend/types/appearance.types.ts` —
  `PerModeColors` interface (re-exported from `backend/types/index.ts`).
- **Consumed by**: `frontend/common/stores/appearancePreviewStore.ts`
  — `setModeColors(mode, pair)` action called by the selector.
- **Future consumers (Task 9.2)**: `getResolvedAppearance()` will
  read `findAppearancePreset(process.env.APP_THEME_PRESET)` as the
  tier-4 fallback (decision §14).

## Deferred / Follow-up Items

- **i18n**: The preset section heading ("Preset Themes") and the
  settings-tab panel heading ("Quick Presets") + helper text are
  currently hardcoded English strings (matching the existing
  `ColorEditorSection` pattern, which uses "Theme Colors" / "Light" /
  "Dark" / "Primary" / "Secondary" as bare strings). Task 9 (i18n
  frontend labels) will add `customize.presetThemes` and
  `appearance.presetName.<id>` keys; the selector should then map
  preset names through `t()`.
- **Active-preset highlighting**: The current selector does NOT
  highlight the preset that matches the current draft colors. Adding
  this requires a deep-equality check between `draft.colors` and each
  preset's `colors` — deferred to avoid pulling in a deep-equal util
  in this minimal wiring (the task prompt explicitly allows minimal
  wiring).
- **`APP_THEME_PRESET` env-var resolution** (decision §13 / §14) is
  scoped to Task 9.2 (tiered caching fallback). The catalog + lookup
  helper (`findAppearancePreset`) are in place for Task 9.2 to
  consume.
