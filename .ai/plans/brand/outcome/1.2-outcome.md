# Task 1.2 — Run migration against dev DB

## Summary

Applied the appearance-permissions migration to the dev DB and verified the
`settings.appearance_manage` permission row + both group grants
(`super_admin`, `academy_admin`) exist per AC-4.

**Initial migration attempt FAILED** because Task 1.1's deliverable was
incomplete: the data SQL file assumed `permissions.key` was plain text, but
it is actually a PG enum column (`app_permission`). This task expanded scope
to fix Task 1.1's bug by adding the missing enum-alter migration and
renaming the data file so the auto-bundler applies the enum BEFORE the data
(required by PostgreSQL `check_safe_enum_use`).

## Migration execution

### Command used

```bash
cd /home/ahmed/Projects/siraj && bun run db migrate
```

**NOT `bun run db push`** — the plan task spec suggested `db push`, but the
auto-bundler (`backend/db/scripts/applyCustomMigrations.ts`) that detects new
SQL files in `backend/db/migration/` is only invoked by `db migrate` (action 5
in `scripts/dbActions/actions.ts` -> `backend/db/scripts/migrate.ts`).
`db push` (action 6) only runs `ensureExtensions()` + `drizzle-kit push --force`,
which syncs the Drizzle schema file to the DB but does NOT execute the custom
SQL migrations. The carry-forward note in `1.1-outcome.md` that said
"`bun run db push` triggers the auto-bundler" was incorrect; this task used
`db migrate` (the actual migration path used for `7b` and all other custom
SQL files).

### First attempt — FAILED

```
DrizzleQueryError: Failed query:
INSERT INTO permissions (id, key, resource, action, description, category, is_system)
VALUES (gen_random_uuid(), 'settings.appearance_manage', 'settings', 'appearance_manage', ...)
...
error: invalid input value for enum app_permission: "settings.appearance_manage"
  code: "22P02"
  routine: "enum_in"
```

### Root cause

The `permissions.key` column is typed as the PG enum `app_permission` (created
from the TS `AppPermission` enum via `createPgEnumFromEnum("app_permission",
AppPermission)` in `backend/db/schema/enums.ts:126` and used as
`appPermissionEnum("key")` in `backend/db/schema/permissions/permissions.ts`).
It is **NOT** plain `varchar`.

Task 1 added `SETTINGS_APPEARANCE_MANAGE = "settings.appearance_manage"` to
the TS `AppPermission` enum, but that only changes the TypeScript type — it
does NOT add the value to the existing PG enum on the dev DB. To INSERT the
new value into `permissions.key`, the PG enum must first be extended via
`ALTER TYPE app_permission ADD VALUE IF NOT EXISTS 'settings.appearance_manage'`.

Task 1.1's outcome file explicitly (and incorrectly) claimed:
> The appearance data SQL does NOT depend on the `7c-quota_permissions_enum.sql`
> or any `app_permission` PG enum cast — it inserts the permission key as plain
> text into `permissions.key`, exactly like `7b` does.

This was wrong. The `7a`/`7b` pattern exists precisely because `7a` adds the
enum values and `7b` then INSERTs rows using them — two separate drizzle
folders (transactions) because PostgreSQL `check_safe_enum_use` forbids using
a freshly-added enum value inside the same transaction that added it.

### Fix applied (scope expansion to repair Task 1.1)

1. **Created** `backend/db/migration/7c-appearance-permissions-enum.sql` —
   single statement `ALTER TYPE "app_permission" ADD VALUE IF NOT EXISTS
   'settings.appearance_manage'`, mirroring `7a-settings-permissions-enum.sql`
   and `7c-quota_permissions_enum.sql`.

2. **Renamed** `backend/db/migration/7c-appearance-permissions-data.sql` ->
   `backend/db/migration/7d-appearance-permissions-data.sql`. The rename is
   REQUIRED because the auto-bundler sorts custom SQL files alphabetically and
   assigns sequential drizzle-folder timestamps (base + index*1000ms) in that
   order. With the original names `7c-...-data` < `7c-...-enum` (`d` < `e`),
   the data folder would get the earlier timestamp and be applied first ->
   fail again. Renaming to `7c-...-enum` + `7d-...-data` guarantees
   `7c-...-enum` (alphabetically earlier) is applied first, matching the
   `7a`/`7b` convention. The renamed file's header comment now explicitly
   documents the dependency on `7c-appearance-permissions-enum.sql`.

   The `7d` prefix does NOT conflict with the existing `7d-quota_permissions_data.sql`
   because `7d-appearance-...` < `7d-quota-...` lexically (`a` < `q`); each
   becomes its own drizzle folder.

3. **Deleted** the failed drizzle folder
   `backend/drizzle/20260822053811_custom_7c-appearance-permissions-data/`
   (generated by the first failed attempt; its INSERT transaction rolled
   back, so the permission row was never persisted).

4. **Reverted the sidecar** `backend/drizzle/.custom-migrations.json`:
   removed the stale `7c-appearance-permissions-data.sql` manifest entry and
   the failed folder from `appliedFolders`, then recomputed `manifestHash`.
   This returns the sidecar to the state it was in BEFORE the first failed
   migrate, so the auto-bundler correctly treats both new files as a fresh
   delta.

## Carry-Forward Knowledge for Phase 2

1. **`permissions.key` is a PG enum (`app_permission`), NOT plain text.**
   Any future permission addition requires TWO migration files:
   - `<prefix>-<topic>-enum.sql`: `ALTER TYPE app_permission ADD VALUE IF
     NOT EXISTS '<permission_key>'` (own drizzle folder / transaction).
   - `<prefix+1>-<topic>-data.sql`: `INSERT INTO permissions ...` (own drizzle
     folder / transaction, applied AFTER the enum folder).
   The enum file MUST sort alphabetically BEFORE the data file so the
   auto-bundler assigns it an earlier drizzle-folder timestamp. The `7a`/`7b`,
   `7c-quota`/`7d-quota`, and now `7c-appearance-enum`/`7d-appearance-data`
   conventions all follow this pattern.

2. **Use `bun run db migrate`, NOT `bun run db push`, to apply custom SQL
   migrations.** Only `db migrate` invokes `applyCustomMigrations()` (the
   auto-bundler) + `runDrizzleMigrations()`. `db push` runs
   `drizzle-kit push --force` which only syncs the Drizzle schema file to the
   DB and does NOT execute the custom SQL files in `backend/db/migration/`.
   The Task 1.1 outcome's carry-forward claim that "`bun run db push`
   triggers the auto-bundler" was incorrect.

3. **Failed migrations leave the sidecar in an inconsistent state.** The
   auto-bundler writes the sidecar (manifest + appliedFolders) BEFORE
   `runDrizzleMigrations()` runs. If drizzle then fails, the sidecar claims
   the file was applied but the DB transaction rolled back. Recovery requires:
   (a) delete the failed drizzle folder, (b) remove the stale entries from
   the sidecar manifest + appliedFolders, (c) recompute `manifestHash` as
   `sha256(JSON.stringify(manifest))`, (d) re-run `bun run db migrate`.

4. **`check_safe_enum_use` is a hard PostgreSQL constraint** (referenced in
   `7a`, `8a-whatsapp`, `9a-cron`, `31-user-admin-reset-password`). It
   forbids using a freshly-added enum value in the same transaction. The only
   safe pattern is: enum file in its own drizzle folder, data file in a
   later drizzle folder.

5. **`academy_admin` slug exists** and was successfully granted
   `settings.appearance_manage` (AC-4). Phase 2's service layer can rely on
   this grant for authorization checks.

6. **The PG enum `app_permission` on the dev DB now contains
   `'settings.appearance_manage'`** — Phase 2 repos/services can INSERT/UPDATE
   rows with this key without enum-cast errors.

7. **Filename references in `implementation.md:261` and `tasks.md:36`** still
   mention the old name `7c-appearance-permissions-data.sql`. These are
   historical (describe the original Task 1.1 plan) and are superseded by the
   `7d-` rename. Future agents should reference `7d-appearance-permissions-data.sql`
   and `7c-appearance-permissions-enum.sql`.

8. **Drizzle migration folder naming**: `<YYYYMMDDHHMMSS>_custom_<slug>`
   where slug is derived from the source SQL filename (with non-alphanumerics
   replaced by `_`). The auto-bundler uses `Date.now() + index*1000` ms as
   the timestamp base for a single delta run, so the alphabetically-first
   delta file always gets the earliest timestamp.
