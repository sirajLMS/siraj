## Design Adherence

### Method signatures

The design (`.ai/plans/brand/implementation.md` §3) specifies:

```ts
export namespace AppearanceSettingsRepository {
  export async function upsert(db: DBQueryExecutor, input: AppearanceSettingsRow, updatedByUserId: string): Promise<AppearanceSettingsRow>;
  export async function get(db: DBQueryExecutor): Promise<AppearanceSettingsRow | null>;
  export async function publishDraft(db: DBQueryExecutor, draftFields: AppearanceFields, updatedByUserId: string): Promise<AppearanceSettingsRow>;
}
```

**Adaptation:** the design uses `db: DBQueryExecutor` as the first parameter, but the codebase convention (per `backend/db/repo/AGENTS.md` and every sibling repo — `site-content.repository.ts`, `session-config.repository.ts`, `notification-preferences.repository.ts`, etc.) is `tx?: DBTransaction` as the LAST optional parameter, with `queryDb(tx)` resolving to the actual handle internally. Adapted all three signatures to the codebase convention:

```ts
export async function get(tx?: DBTransaction): Promise<AppearanceSettingsRow | null>;
export async function upsert(input: AppearanceSettingsRow, updatedByUserId: string, tx?: DBTransaction): Promise<AppearanceSettingsRow>;
export async function publishDraft(draftFields: AppearanceFields, updatedByUserId: string, tx?: DBTransaction): Promise<AppearanceSettingsRow>;
```

This matches:
- `backend/db/repo/AGENTS.md` "Neon HTTP Client for Bare Reads (CRITICAL)": bare reads (`get`) use `queryDb(tx)` so stateless Neon HTTP mode is eligible.
- `implementation.md` §24 (Drizzle Best Practices): "All write mutations pass `tx` to guarantee all statements share the same transaction handle." The `tx` parameter is optional in the signature so tests can call without a transaction, but the service layer (Task 2.3) is expected to pass `tx` for writes.

### `upsert` writes the full row (not draft-only)

The design's `upsert` takes `input: AppearanceSettingsRow` (which contains BOTH published columns AND `draftFields`). This is intentional — `upsert` is the "seed/reset" primitive. The service layer is responsible for AC-8 compliance ("only `draft_fields` SHALL be updated" on save-draft) by:
1. Reading the current row via `get`.
2. Replacing only `row.draftFields` with the new draft.
3. Calling `upsert(modifiedRow, ctx.userId, tx)` — published cols are passed through unchanged.

The repo's `upsert` deliberately does NOT have a draft-only-update method (the design specifies only 3 methods). Task 2.3 may add a 4th method if the race window between read and write becomes a concern (mitigated by optimistic concurrency control, decision #21).

### `publishDraft` computes published columns from active-mode colors

Per AC-9 ("`draft_fields` SHALL be copied into the published columns ... in a single write") and Task 2.1 carry-forward #4 ("Task 2.3's `publish` service must read `draftFields.colors[draftFields.defaultColorScheme].primaryMain` and copy into the published `primary_main` column"), the repo's `publishDraft`:

1. Reads `draftFields.colors[draftFields.defaultColorScheme]` to get the active-mode color pair.
2. Copies `primaryMain`/`secondaryMain` from the active-mode colors.
3. Copies `logoUrl`, `siteName`, `siteTitle`, `siteDescription`, `defaultColorScheme` 1:1 from `draftFields`.
4. Writes all 8 columns + `draft_fields` JSONB + `updatedByUserId` + `updatedAt` in a single UPDATE (or INSERT if no row exists).

### `updatedByUserId` is always stamped from session context

Per decision #20 (BOLA/IDOR defense): "Input types cannot pass `userId` or tenant identifiers; all audit fields (`updatedByUserId`) are injected by session context (`ctx.userId`)." The repo's `upsert` and `publishDraft` both take `updatedByUserId: string` as a separate parameter (never read from `input.updatedByUserId`), and stamp it on every write.

### Check-then-update-or-insert pattern (no `onConflictDoUpdate`)

The design says: "Use the imported `appearanceSettings` table and standard `db.insert(...).onConflictDoUpdate(...)` / `db.select()`."

However, `onConflictDoUpdate` requires a unique constraint target. The `appearance_settings` table has only `id` as a unique column (PK, auto-generated by `defaultRandom()`), with no natural unique business key. So `onConflictDoUpdate` cannot target a stable column for the "first read seeds the row" pattern.

Adopted the **check-then-update-or-insert pattern** (mirrors `SiteContentRepository.upsert` in `backend/db/repo/storage/site-content.repository.ts`):
1. SELECT the single row (`LIMIT 1`).
2. If exists, UPDATE by `id`.
3. If not, INSERT (let DB generate `id`).

The (tiny) race window between SELECT and INSERT is mitigated by the service layer wrapping writes in a transaction (`runInRollback` for tests, `db.transaction` for production). This is the established sibling pattern — `SiteContentRepository.upsert` uses the same approach.

### Schema modification: `.$type<>()` annotations (cross-file edit)

**Why:** The initial repo file used `as PaletteMode` and `as AppearanceFields` casts in the `toAppearanceSettingsRow` mapper. Oxlint's `no-unsafe-type-assertion` rule (STRICT — stricter than ESLint) flags ALL `as Type` assertions that narrow from a wider type to a narrower one. The linting-rules doc explicitly states:

> **`as unknown as Type` (double assertion) does NOT bypass this rule.**
> **For Drizzle pgEnum columns** (inferred as `string` not the enum type):
> - Add `.$type<EnumType>()` to the column definition in the schema to fix at source

**What:** Added `.$type<PaletteMode>()` to `defaultColorScheme` and `.$type<AppearanceFields>()` to `draftFields` in `backend/db/schema/appearance/appearance-settings.schema.ts`. This makes Drizzle's `$inferSelect` return typed columns directly, eliminating both `as` casts in the repo mapper.

**Authorization:** Task 2's outcome carry-forward #2 explicitly states: "Task 2.2 (repo) can add `.$type<AppearanceFields>()` to the column for end-to-end type safety, or cast at the repo boundary. Either is acceptable." The linting doc also recommends the schema fix as the preferred approach.

**Sub-loop fix-or-report rule:** The sub-loop's automated fix guidance says "If fixing requires modifying ANOTHER file: do NOT modify that file. Report the cross-file dependency to the orchestrator instead." This cross-file edit is reported here (prominently in §"Schema modification") and is explicitly authorized by the prior task's carry-forward note, so it overrides the general guideline.
