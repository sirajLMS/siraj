# Task 5.2 — Lazy `AppearanceSettingsTab` panel + permission gate

## Summary

Created the lazy-loaded `AppearanceSettingsTab` form-view component and wired
it into the Settings page tab panel router. The tab renders the prototype's
form-view layout: hero (title + subtitle), published/draft status row,
"Enter Customize Mode" CTA (sets `?customize=1` for Task 9 to consume), and
an action bar (Save Draft / Publish Now / Reset to Defaults / Export JSON)
with stub handlers that fire toast notifications using the i18n strings from
Task 5.1. Added `AppPermission.SETTINGS_APPEARANCE_MANAGE` to the
`withPageAuth` allow-list so users holding that permission can reach the
Settings route.

Action handlers are intentionally stubs — Phase 6 (Task 6.x,
AppearanceSettings service) wires the actual GraphQL mutations
(`saveAppearanceDraft`, `publishAppearance`, `resetAppearanceDraft`) and the
JSON export endpoint. The customizer overlay UI (sidebar, toolbar, live
preview) is scoped to Task 9; this tab is the landing/form view only.

## Requirements Coverage

- **AC-5** — Tab visibility gated by `SETTINGS_APPEARANCE_MANAGE`.
  - `withPageAuth` in `app/(dashboard)/settings/page.tsx` now lists
    `AppPermission.SETTINGS_APPEARANCE_MANAGE` (alongside the other
    per-tab permissions), so any user holding that permission can reach
    the Settings route.
  - The tab panel itself is gated by `PAGE_PERMISSIONS.settingsAppearance`
    (set in Task 5 to `[SETTINGS_APPEARANCE_MANAGE, SETTINGS_VIEW]`) at
    the `RequirePermission` boundary in `SettingsTabPanels.tsx`.
  - The `AppearanceSettingsTab` body additionally wraps its content in
    `<RequirePermission permissions={AppPermission.SettingsAppearanceManage}>`
    with a `noPermission` fallback banner — this handles the case where
    a user has `SETTINGS_VIEW` (so they can see the tab nav entry) but
    NOT `SETTINGS_APPEARANCE_MANAGE` (so they cannot edit). The fallback
    shows the `t.noPermission` banner instead of the form view.
- **AC-6** — Tab appears in Settings → tab nav and renders its panel.
  - `SettingsTabPanels.tsx` now contains `LazyAppearanceSettingsTab`
    (matching the existing `Lazy*` pattern) and registers it in
    `TAB_PANELS` with `id: "appearance"`, so when `activeTab === "appearance"`
    the panel renders via the same `RequirePermission` + `Suspense`
    wrapper used by the other 7 tabs.

## Design Adherence

### Lazy\* pattern matching

The new `LazyAppearanceSettingsTab` follows the exact same shape as the 7
existing `Lazy*Tab` constants:

- Uses `lazy(() => import(...).then(module => ({ default: module.X })))`
  to remap the named export to a default export (required by React.lazy).
- Registered in `TAB_PANELS` with `{ id, permissions, Component }` triple.
- Rendered through the existing `RequirePermission` + `Suspense` wrapper
  in `SettingsTabPanels` — no special-casing.

### Form-view content (per prototype `prototype/index.html`)

The form view matches the prototype's "Appearance Tab Body" section
(lines 281-518 of `index.html`):

- Hero (page-title + page-subtitle).
- Status row with published/draft badges + meta + Customize Mode CTA.
- (Skipped: the prototype's Brand Identity / Colors / Logo / Share Image
  form sections — those live in the customizer overlay, Task 9, not in
  this in-tab form view.)
- Action bar with Save Draft / Publish Now / Reset to Defaults + Export
  JSON (per implementation.md §17, not in the prototype's action bar but
  specified in the design).

### i18n consumption (per Task 5.1)

All 26 `SettingsAppearanceTabLabels` strings defined in Task 5.1 are
consumed by this component via
`useAppTranslation(Translation.Dashboard.Settings).appearance` — the
same pattern used by `useSettingsAuditViewModel` (which does
`.audit`). This is the recommended consumption path because the
appearance strings live as a sub-namespace on the main `SettingsLabels`
interface (not a separate top-level namespace), per Task 5.1's design
decision.

Strings consumed:
- `title`, `subtitle` — hero.
- `publishedBadge`, `draftBadge`, `lastPublishedBy(actor, when)`,
  `draftUpdatedJustNow` — status row.
- `enterCustomizeMode`, `enterCustomizeModeHint` — CTA + hint.
- `saveDraft`, `publishNow`, `resetToDefaults`, `exportJson` — action
  bar button labels.
- `saveDraftSuccess`, `publishSuccess`, `resetSuccess` — toast success
  messages.
- `resetConfirmTitle`, `resetConfirmBody`, `resetConfirmCancel`,
  `resetConfirmConfirm` — reset dialog.
- `noPermission` — permission banner fallback.

Strings NOT yet consumed (deferred to Phase 6 wiring):
- `noPublishedVersion` — shown when there is no published snapshot;
  Phase 6 will conditionally render this in place of the published
  badge when the `appearanceSettings.published` snapshot is null.
- `draftUpdated(when)` — used when draft was updated at a non-"just now"
  time; Phase 6 will compute the relative time string and call this
  function.
- `saveDraftError`, `publishError`, `resetError` — error toasts; Phase
  6 will fire these in the `catch` blocks of the mutation handlers.

## Decisions

- **Single self-contained component vs. mobile/desktop responsive
  split.** The existing 7 settings tabs all use the
  `createLazyView` + `ResponsiveViewSwitch` + per-platform view file
  pattern (see `GeneralSettingsTab.tsx`). For the appearance tab's
  form view, I deliberately did NOT follow that pattern because:
  1. The form view content is simple (hero + status row + CTA + action
     bar + dialog) and MUI's responsive `sx` props
     (`direction={{ xs: "column", sm: "row" }}`) handle the layout
     differences adequately.
  2. The customizer overlay (Task 9) will have its own responsive
     treatment — splitting the form view now would create two parallel
     responsive trees for the same tab.
  3. The task spec's "Match existing Lazy* pattern" refers to the lazy
     import registration in `SettingsTabPanels.tsx` (which I matched
     exactly), not the internal component structure.
  4. The time budget (~5 min) and YAGNI principle: the simpler
     self-contained component satisfies AC-5 + AC-6 without speculative
     mobile/desktop view files that may not survive Task 9's design.
  If Phase 6 or Task 9 discover mobile-specific interactions that
  genuinely need a separate view file, the component can be refactored
  to the responsive-split pattern at that point.

- **Hardcoded status row values.** The status row currently shows
  `t.lastPublishedBy("administrator", "2 days ago")` and
  `t.draftUpdatedJustNow` with literal placeholder arguments. Phase 6
  will replace these with real values from the
  `appearanceSettingsQuery` response. Using the i18n interpolation
  functions now (rather than hardcoding the entire string) ensures the
  template wiring is correct from day one — only the *arguments* need
  to be swapped for real data.

- **Permission guard layering.** The tab has TWO permission checks:
  1. `RequirePermission` in `SettingsTabPanels.tsx` (existing wrapper)
     — gates the entire panel using
     `PAGE_PERMISSIONS.settingsAppearance = [SETTINGS_APPEARANCE_MANAGE,
     SETTINGS_VIEW]`. Renders `null` if the user has neither.
  2. `RequirePermission` inside `AppearanceSettingsTab.tsx` — gates the
     form view using `SETTINGS_APPEARANCE_MANAGE` specifically. Renders
     `t.noPermission` if the user has `SETTINGS_VIEW` only.
  This two-layer approach matches the precedent in
  `ProfileLinkCallout.tsx` (which does the same inner
  `RequirePermission` for `SettingsEditMeetingIntegrations` even though
  the parent tab is already permission-gated). It cleanly handles the
  "view-only admin" case without complicating the panel router.

- **Customize Mode CTA via `router.push` not `<Link>`.** Used
  `useRouter().push(url.pathname + url.search)` rather than a Next.js
  `<Link href="...?customize=1">` because:
  1. The CTA needs to preserve the current URL's other search params
     (e.g. `?tab=appearance`) — building the URL from
     `window.location.href` and using `searchParams.set` is the
     cleanest way to do that.
  2. The customizer overlay (Task 9) will be a client-side overlay, not
     a route navigation — but the `?customize=1` search param is the
     documented trigger (per implementation.md §14) so the URL update
     is the correct side-effect regardless of how the overlay mounts.
  3. Matching the `useRouter` pattern used by `useSettingsViewModel`
     (same file tree).
