# Task 9.1 — JSON Schema & IDE Integration

## Summary

Created the canonical JSON Schema for `AppearanceFields`, wired it into the
VS Code JSON language server (autocomplete + validation for any
`*appearance*.json` / `.brand.json` file), and implemented a schema-driven
runtime validator in `shared/lib/`. The validator is self-contained (no Ajv
dependency) and reads its constraints directly from the JSON Schema file, so
tightening the schema automatically tightens runtime validation — a single
source of truth for both IDE tooling and runtime defense.

This satisfies **AC-25** (JSON Schema validation for appearance fields) and
unblocks Task 9.2 (ENV hydration parser) + Task 9.3 (Export JSON feature),
both of which import the validator.

## Requirements Coverage

- **AC-25** — JSON Schema for `AppearanceFields`:
  - `shared/schemas/appearance.schema.json` (draft 2020-12) defines the
    canonical shape: `colors.{light,dark}.{primaryMain,secondaryMain}` (hex
    pattern `^#[0-9a-fA-F]{6}$`), `logoUrl` (nullable URI), `siteName` /
    `siteTitle` / `siteDescription` (string with min/max length), and
    `defaultColorScheme` (enum `["light","dark"]`).
  - VS Code `json.schemas` association auto-validates any file matching
    `*appearance*.json` or `.brand.json` against the schema (inline errors +
    property/enum autocomplete in the editor).
  - Runtime validator `validateAppearanceFields(data: unknown)` re-checks
    the same constraints server-side (defense-in-depth on the
    `saveDraft`/`publish` boundary) and client-side (future "Import JSON"
    customizer flow).

## Files Created / Modified

### Created (2 files)

1. **`shared/schemas/appearance.schema.json`** (2.5 KB, draft 2020-12)
   - `$schema`: `https://json-schema.org/draft/2020-12/schema`.
   - `$id`: `https://siraj.local/shared/schemas/appearance.schema.json`
     (stable local identifier; not fetched).
   - `type: object`, `additionalProperties: false`, `required`: all 6
     top-level keys (`colors`, `logoUrl`, `siteName`, `siteTitle`,
     `siteDescription`, `defaultColorScheme`).
   - `colors` is an object with `light` + `dark`, each a `$ref` to
     `#/$defs/perModeColors` (DRY — single definition reused for both modes).
   - `$defs.perModeColors`: object with `primaryMain` + `secondaryMain`,
     each `type: string` with `pattern: "^#[0-9a-fA-F]{6}$"`.
   - `logoUrl`: `type: ["string","null"]`, `format: "uri"` (nullable — `null`
     is valid when no logo is published).
   - `siteName`: `minLength: 1`, `maxLength: 80` (short brand).
   - `siteTitle`: `minLength: 1`, `maxLength: 120` (full title).
   - `siteDescription`: `minLength: 0`, `maxLength: 300` (meta description;
     empty string allowed).
   - `defaultColorScheme`: `enum: ["light","dark"]`.

2. **`shared/lib/appearance-schema-validator.ts`** (5.8 KB, 0 deps)
   - Exports `AppearanceValidationResult` (`{ valid: boolean; errors?: string[] }`)
     and `validateAppearanceFields(data: unknown): AppearanceValidationResult`.
   - **Schema-driven**: imports `appearanceSchema` from
     `@/shared/schemas/appearance.schema.json` (`resolveJsonModule: true`),
     reads `required`, `properties`, `$defs`, and each property's `pattern` /
     `enum` / `minLength` / `maxLength` / `format` at module-load time.
     Tightening the JSON Schema automatically tightens runtime validation.
   - **No Ajv dependency**: Ajv 6.x is present in `node_modules` as a
     transitive dep but is NOT declared in `package.json`; a direct import
     would be fragile (could be pruned on the next install). The validator
     implements the subset of JSON Schema needed for `AppearanceFields`
     (string type, pattern, enum, length bounds, `format: uri`, `$ref` to
     `$defs`, nullable via `type: ["string","null"]`). Compiled regexes are
     cached in a `Map` (the hex pattern is reused 4× via `$ref`).
   - **Layer-isolated**: lives in `shared/` and accepts `unknown` — no import
     of `AppearanceFields` from `@/backend/types` (which would violate the
     `shared/` layer isolation rule in `shared/AGENTS.md`). Both the backend
     publish/saveDraft path and the frontend "Import JSON" flow can call it.
   - **Error format**: one message per violated constraint, instance-path
     prefixed (e.g. `colors.dark.primaryMain: must match pattern ^#[0-9a-fA-F]{6}$`).
   - **Nullable `logoUrl`**: `null` short-circuits to valid (per
     `type: ["string","null"]`); non-null values are validated as URI via
     `URL.canParse(value)` (Node 18.17+ / Bun built-in).

## Design Decisions

### Why draft 2020-12 (not draft-07)?

Draft 2020-12 is the current JSON Schema standard. VS Code's JSON language
server supports it natively. The only feature used that post-dates draft-07
is the standardized `$defs` keyword (draft-07 used `definitions`); everything
else (`pattern`, `enum`, `minLength`/`maxLength`, `format`, `type` array,
`$ref`) is identical across both drafts. The runtime validator's `$ref`
resolver handles the `#/$defs/<name>` form.

### Why a self-contained validator instead of Ajv?

- Ajv 6.x (the version in `node_modules`) is a transitive dependency, not
  declared in `package.json`. Importing it directly from `shared/` would
  create a hidden coupling that could break on the next `bun install` if the
  transient dep is pruned or upgraded.
- Adding Ajv as a declared dep would require `bun add ajv` + version pinning
  + a license review — out of scope for a 5-minute task and a heavyweight
  payload for validating a 6-field object.
- The `AppearanceFields` schema uses only string constraints (pattern, enum,
  length, URI format) — a ~120-line focused validator covers the full
  surface with zero deps and better error messages (instance-path prefixed).
- The validator is still **schema-driven** (reads constraints from the JSON
  file), preserving the "single source of truth" property. If a future task
  adds non-string fields (e.g. numbers/arrays), the validator can be
  extended or Ajv can be properly vendored at that point.

### Why `additionalProperties: false`?

Defensive: prevents typos in exported JSON (e.g. `primaryColor` instead of
`primaryMain`) from silently round-tripping through the system. The
`AppearanceFields` type is a closed interface; the schema mirrors that
closure.

### Why `logoUrl` uses `format: "uri"` + `URL.canParse` (not a regex)?

URI validation via regex is brittle (RFC 3986 is complex). `format: "uri"`
in the schema is a hint to VS Code (which uses its own URI check), and the
runtime validator delegates to the platform `URL.canParse()` built-in
(Node 18.17+ / Bun), which is correct and zero-dependency. Empty strings
short-circuit to valid (an unset logo is represented as `null`, not `""`,
but `""` is tolerated defensively).
