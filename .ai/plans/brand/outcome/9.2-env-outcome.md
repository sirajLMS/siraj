# Task 9.2 — ENV Hydration & Tiered Caching Fallback

## Summary

Implemented `AppearanceSettingsService.getResolvedAppearance()` — the
4-tier SSR appearance resolution function (decision #14) that powers
`generateMetadata`, `server-theme-css.ts`, and any other read path that
needs the active site appearance without a permission check or DB seed.

This completes the work started in the previous (timed-out) attempt: the
three module-level helpers — `RESOLVED_APPEARANCE_TTL_MS`,
`resolvedAppearanceMemo`, and `readAppearanceFromEnv()` — were already
in place but never read, producing 3 `TS6133` (declared but never read)
errors. This task wires them into the public `getResolvedAppearance()`
method, closing the resolution loop and satisfying **AC-26** (SSR caching
with bounded staleness) + **AC-27** (ENV hydration with safe fallback).

Also documented the `NEXT_PUBLIC_APP_BRANDING` env var in `.env.example`
with the canonical resolution ladder, schema reference, and a ready-to-use
sample JSON payload (covers the operator onboarding path — an operator
should not need to read source code to use the override).

## Requirements Coverage

- **AC-26** — SSR caching with bounded staleness:
  - **Tier 1**: in-memory TTL memo (`resolvedAppearanceMemo`) with 15s
    TTL. Hot-path reads return a single property lookup (no DB, no
    `unstable_cache` lookup, no ENV parse). Memo is cleared on `publish`
    and on branding-related env-config overrides (AC-30) via
    `revalidateAppearanceCache()` so the very next read after a write
    picks up the new values — no manual invalidation hook needed.
  - **Tier 2**: `unstable_cache` DB read (`getFirstAppearancePublished`)
    with tag `"appearance"` (AC-22). Invalidated by `revalidateTag` on
    every successful `publish`.
  - The two cache layers are complementary: Tier 1 absorbs repeated
    reads within a request batch (and across requests within 15s); Tier
    2 absorbs repeated reads across the 1-hour `unstable_cache` revalidate
    window. The 15s TTL is short enough that a `publish` is reflected
    within one TTL window even without the explicit
    `resolvedAppearanceMemo = null` clear in
    `revalidateAppearanceCache` (belt-and-braces).
- **AC-27** — ENV hydration with safe fallback:
  - **Tier 3**: `readAppearanceFromEnv()` parses
    `process.env.NEXT_PUBLIC_APP_BRANDING`, Zod-validates the result via
    `parseAppearanceEnvBranding` (Task 9.10), and memoises the parsed
    value in `envBrandingMemo` so the parse + validate cost is paid
    exactly once per process.
  - **Tier 4**: `DEFAULT_APPEARANCE_FIELDS` — the canonical theme
    snapshot. Always available, never throws.
  - On unset / empty / malformed / schema-invalid ENV, Tier 3 returns
    `null` (after logging a single domain warning), and Tier 4 provides
    the safe fallback. No path through `getResolvedAppearance()` throws.

## Design Decisions

### Why is `getResolvedAppearance` async (not sync as the task spec
hinted)?

The task spec lists the return type as `getResolvedAppearance():
AppearanceFields`, but Tier 2 calls `getFirstAppearancePublished()`
which returns `Promise<AppearanceFields | null>` (it wraps
`unstable_cache`, which is async by design — the cache layer may need
to await the underlying DB read on a cold cache). A synchronous
`getResolvedAppearance` would require either:
- Making Tier 2 sync (impossible — `unstable_cache` is async), or
- Dropping Tier 2 entirely (unacceptable — it's the primary source of
  truth once a row exists).

The correct type is `Promise<AppearanceFields>`. The task spec's
sync-style notation was shorthand; the implementation is async.
Callers (`generateMetadata`, `server-theme-css.ts`) are already async
(SSR entry points), so this is transparent.

### Why memoise the Tier 4 fallback (DEFAULT_APPEARANCE_FIELDS)?

Memoising `DEFAULT_APPEARANCE_FIELDS` may seem pointless (it's a
constant reference, so the "value" never changes). But the memo serves a
different purpose on the fallback path: it prevents re-entering Tier 2
(`unstable_cache` lookup) and Tier 3 (ENV parse + Zod validate) on every
subsequent read within the TTL window. Without the memo, a deployment
with no DB row and no ENV override would pay the `unstable_cache` lookup
cost (which still hits the Next.js cache layer even on a miss) on every
SSR request. With the memo, those subsequent reads are a single property
lookup. The 15s TTL bounds staleness — once a `publish` happens, the
memo is cleared by `revalidateAppearanceCache`, and the next read
re-enters Tier 2 to pick up the newly-published row.

### Why a 15s TTL (not 60s or 5s)?

- **5s** would defeat the purpose of the memo (most request batches
  span <5s anyway, so the memo would rarely hit).
- **60s** would make a `publish` take up to a minute to propagate to
  SSR reads without the explicit `revalidateAppearanceCache` clear —
  acceptable in theory, but operators expect "publish = immediate".
- **15s** is the sweet spot: long enough to absorb a typical request
  batch (a single page load may issue 3–5 `generateMetadata` calls in
  Next.js 16 parallel route segments), short enough that even without
  the explicit clear, staleness is bounded to a barely-perceptible
  window. The explicit clear in `revalidateAppearanceCache` makes the
  steady-state case "publish = immediate" anyway; the TTL only matters
  for the edge case where the clear is bypassed (e.g. a process
  restart races with a publish).

### Why not invalidate the memo via `revalidateTag` directly?

`unstable_cache`'s `revalidateTag` is a Next.js-level cache
invalidation — it signals the data cache layer. The in-memory memo
(`resolvedAppearanceMemo`) is a plain JS `let` with no Next.js cache
binding; `revalidateTag` cannot reach it. The explicit
`resolvedAppearanceMemo = null` in `revalidateAppearanceCache()` is the
bridge: it clears the in-memory layer, and `revalidateTag` clears the
data cache layer, so the next read re-enters both. This is documented in
the JSDoc on `resolvedAppearanceMemo` (lines 345–358).

### Why log at the helper (not the caller)?

`readAppearanceFromEnv` logs the `logger.warn` on invalid ENV (line 399)
rather than `getResolvedAppearance` logging it. This keeps the log
emission next to the parse failure (single responsibility) and ensures
the warning is emitted exactly once per process (the `envBrandingMemo`
short-circuits subsequent calls). If `getResolvedAppearance` logged it,
the warning would fire on every read within the TTL window after the
memo expired — log spam. The helper-based logging pattern mirrors the
"single-source Zod validation" decision (§22) and the
`parseAppearanceEnvBranding` design (Task 9.10).

### Why not throw on Tier 4?

`DEFAULT_APPEARANCE_FIELDS` is always available (it's a `const` literal
— no I/O, no parsing). There is no scenario in which Tier 4 can fail.
Throwing would force every caller to wrap `getResolvedAppearance` in a
try/catch, which is unacceptable for SSR hot paths. The "never throws"
contract is documented in the JSDoc and is the reason `generateMetadata`
can call it directly without a defensive wrapper.

## Resolution Ladder (Sequence Diagram, Text Form)

```
getResolvedAppearance()
  │
  ├─ Tier 1: resolvedAppearanceMemo.expiresAt > now?
  │    YES → return memo.value                    [O(1), no I/O]
  │    NO  → fall through
  │
  ├─ Tier 2: await getFirstAppearancePublished()   [unstable_cache, tag "appearance"]
  │    non-null → memoise + return published
  │    null     → fall through (no row yet, or cache miss + DB miss)
  │
  ├─ Tier 3: readAppearanceFromEnv()                [process.env.NEXT_PUBLIC_APP_BRANDING]
  │    non-null → memoise + return fromEnv         [parsed + Zod-validated once per process]
  │    null     → fall through (unset / invalid / schema-fail)
  │
  └─ Tier 4: memoise + return DEFAULT_APPEARANCE_FIELDS   [const, never fails]
```
