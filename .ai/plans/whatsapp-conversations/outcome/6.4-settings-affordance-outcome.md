# Outcome 6.4 — Settings Numbers card manage-recipients affordance

Date: 2026-09-11.

## Decision: new self-contained dialog (not panel extraction)

`TestRecipientsPanel.tsx` internals stayed untouched (agent A's in-flight 6.2
PhoneInput work, observed mid-task via the new `addPhoneValid` prop). The panel
is a fully controlled presentational component, so the settings surface gets a
new dialog that composes the panel and drives it with its own account-scoped
registry ViewModel — exactly the fallback route in the task brief.

## New files (conversations feature folder)

- `frontend/common/views/dashboard/whatsapp/conversations/useTestRecipientsManageViewModel.ts`
  — `useTestRecipientsManageViewModel(accountId)` hook returning the full
  `TestRecipientsPanelProps` shape: own `whatsappTestRecipients` query
  (`cache-and-network`, fresh per dialog mount), add/remove/verify mutations
  with `errorPolicy: "none"` and domain-code mapping
  (`WHATSAPP_RECIPIENT_LIMIT_REACHED` / `WHATSAPP_RECIPIENT_CONFLICT` →
  `errors` namespace strings; else server-localized message; else
  `recipientAddFailed`), 5-recipient cap, `addPhoneValid` via
  `parsePhoneToE164`, E.164 digit normalization on submit (`phoneDigitsOnly`),
  `canManage` from `AppPermission.WhatsappConversationsManage`.
- `frontend/common/views/dashboard/whatsapp/conversations/TestRecipientsManageDialog.tsx`
  — `TestRecipientsManageDialog({ accountId, open, onClose, fullScreen })`
  (AppDialog-style MUI `Dialog`): title from `manageRecipientsTitle`, hint body
  from `manageRecipientsHint` (both whatsappConversations namespace), close
  IconButton, and `TestRecipientsPanel` inside `DialogContent` via
  `ManageDialogBody` — the registry body only mounts while open, so each open
  fires a fresh query; reload/refetch are handled entirely by the dialog's own
  query usage. The hook lives in a separate `.ts` file because
  `react-refresh/only-export-components` rejects hook+component co-exports.
- Barrel: `conversations/index.ts` re-exports both new modules (alphabetical,
  adjacent to the panel/hook entries).

## Settings wiring

- `types/whatsappSettingsTypes.ts`
  - `WhatsappDialogState.type` gains `"manageRecipients"` (uses the existing
    `accountId` slot).
  - `WhatsappSettingsLabels["page"]` partial pick extended with
    `manageRecipients` (same opt-in pattern as `testNumberBadge` from 4.6).
  - `WhatsappSettingsViewModel` gains
    `openManageRecipientsDialog: (accountId: string) => void`.
- `useWhatsappSettingsViewModel.ts`
  - `useWhatsappDialogs` adds `openManageRecipientsDialog` (sets
    `{ type: "manageRecipients", accountId }` through the same consolidated
    `dialogState`).
  - `useWhatsappLabels` now merges `{ testNumberBadge, manageRecipients }` from
    the already-loaded `Translation.WhatsappConversations` namespace into
    `labels.page` — the settings VM therefore loads both namespaces (whatsapp +
    whatsappConversations), as required. No new namespace key duplication.
- `tabs/whatsappTabSharedProps.ts` — `NumbersTabSharedProps` gains
  `onOpenManageRecipients`.
- `WhatsappTabPanels.tsx` — `NumbersTabPanel` passes
  `onOpenManageRecipients: viewModel.openManageRecipientsDialog`.
- Desktop `NumbersTab.desktop.tsx`
  - `ManageRecipientsAction` — `PersonAddAlt1Outlined` Tooltip+IconButton in
    the card action row, rendered only when `account.isTestNumber === true` and
    the merged label exists; mirrors the existing deactivate affordance's
    disabled semantics (`isLocalDeactivating || isSyncing`) and `account.id`
    guard.
  - `TestRecipientsManageDialog` rendered when
    `dialogState.type === "manageRecipients"` with the dialog account id;
    `onClose` → `onCloseDialog`.
- Mobile `NumbersTab.mobile.tsx` — `ManageRecipientsMobileAction` (IconButton,
  same gating/disabled rules) in the `NumberCardContent` action row; dialog
  mounted with `fullScreen` per mobile dialog convention.

Both tier files carried unrelated in-flight diffs at edit time; they were
re-read immediately before each edit and only the affordance/dialog lines were
added.

- The component-test theme has `theme.vars === null`, so any test rendering
  `BaseCard` (desktop `NumberCard` shell) throws
  `TypeError: null is not an object ('theme.vars.palette')`. Confirmed against
  a clean `git archive HEAD` tree in /tmp: this is why the affordance tests
  drive `NumbersTabMobile` (card body without `BaseCard`).
  `whatsappLocalDeactivateConfirmDialog.test.tsx` and
  `whatsappMobileParity.test.tsx` (OptInTab cards tests + the mobile pagination
  test) fail identically on the HEAD baseline — 6.0 should record these.
- Apollo `MockLink` in this setup does not invoke `newData`-only mocks
  (warn-log observed); mutation-firing is therefore asserted via the ordered
  registry-mock consumption + rendered status flip instead.
