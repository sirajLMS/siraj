  right before the mutation input is formed. The existing `ui.phoneInput`
  namespace supplies the invalid-phone helper (no new key, per 6.1 audit).

## 6.3 — New-conversation initiation on `/whatsapp`

- VM: `onStartNewConversation()` (closes any open thread, sets `initiating`,
  resets the composer to TEMPLATE). While no conversation is open
  (`showRecipientPicker`), the mode is hard-forced to
  `WhatsappConversationSendMode.TEMPLATE`; `onComposerModeChange` ignores TEXT.
- `ComposerShared` initiation mode shows the translated
  `newConversationTitle`/`newConversationSubtitle` heading and disables the
  Text toggle (`textModeLocked`). Test accounts get the registry-only `Select`
  (`registryTargetOnly` + `registryTargetPhones`); regular accounts get the
  PhoneInput.
- `executeSend` sends with `conversationId: null`; the service upserts the
  thread by `accountId + to`. The returned message's `conversationId` is then
  selected and the list refetched (tests assert both).
- Header: desktop/mobile workspace views expose the "New conversation" action
  wired to `vm.onStartNewConversation`.

## Teaching notes (driving PhoneInput in Happy DOM tests)

- The per-digit `fireEvent.keyDown` route is unstable in component tests: each
  digit re-emits through the controlled parent, the hook's value-sync effect
  re-splits the partial number, and intermediate calls diverge from any clean
  sequence. Prefer the paste/fill path the component explicitly supports for
  automation: `fireEvent.input(<national textbox>, { target: { value: "+201001234567" } })`
  on the input labelled `phoneLabels.phoneNumber`; a >1-char delta routes
  through `handleNationalChange`, which splits prefix/national and re-emits
  E.164 exactly once.
- National-only fills (no `+`) are NOT equivalent to typing into the prefix
  field — an empty prefix emits `null` (mapped to `""`), so assert with a full
  E.164 string.
- MUI `Dialog` exit transitions in Happy DOM can take several seconds to unmount
  the portal (RTL `asyncUtilTimeout` is 5000ms). For close-transition
  assertions pass an explicit `waitFor(..., { timeout: 20_000 })`.
- The component-test theme declares `theme.vars = null`: anything rendering
  `BaseCard` throws. Assert card content through the mobile leaf (no BaseCard
  wrapper) instead.
