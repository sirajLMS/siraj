# 2.6 outcome — `isTestNumber` computed during sync-from-Meta

## Changes
- `backend/lib/whatsapp-coercion.ts`: added `isMetaTestNumber(verifiedName,
  codeVerificationStatus, displayPhoneNumber)` — pure, exported via the
  `@/backend/lib` barrel. Rule (from `outcome/research-meta-capabilities.md`):
  `verified_name === "Test Number"`, OR `codeVerificationStatus` is present and
  not `"VERIFIED"` while the digits-only display phone starts with `1555`.
  Absent signals resolve to `false` (fail-open — Meta still enforces the real
  allowlist server-side).
- `backend/services/whatsapp/whatsapp-account.service.ts` (`processPhoneNumber`):
  computes `isTestNumber` from the parsed detail and passes it into BOTH the
  update payload (existing accounts) and the create payload (new accounts),
  and reflects it on the returned account object. The `fields=` lists already
  request `verified_name` + `code_verification_status` — untouched.

## Notes / deviations
- The "token-validation account path" named in the task (`verifyTokenAndIdentity`
  / `upsertTokenValidationAccount`) does not exist in the codebase. The only
  other account-creation flow is `completeEmbeddedSignup` (coexistence), which
  never materializes `verified_name` / `code_verification_status` (it resolves
  only the phone id + display number + platform type), so no flag is set there;
  the next `syncFromMeta` stamps it. This is documented rather than shoehorned.
- Repo confirmed: `WhatsappAccountUpdateInput` retains `isTestNumber` and
  `WhatsappAccountRepository.create` takes `WhatsappAccountInsertType` (column
  has `default(false)`), so both payloads compile with no cross-file edits.
