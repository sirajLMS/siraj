# Outcome 4.6 — Settings "Test number" badge on `NumberCardContent`

Date: 2026-09-11.

## Change

`frontend/common/views/dashboard/settings/whatsapp/tabs/shared/NumberCardContent.tsx`
(only file touched):

- **Test-number chip**: standalone `StatusBadge` rendered inside the existing badges
  flex row, directly after the meta-status chip (per design-04), gated on
  `account.isTestNumber === true && t.testNumberBadge`. Uses the fragment's
  `isTestNumber` field (generated `WhatsappAccountFieldsFragment` already includes
  it from task 3.6 — no codegen needed).
- **Config**: module-level `TEST_NUMBER_BADGE` constant
  (`{ category: "syncStatus", status: "partial" }`, teal) instead of a new helper —
  a two-state presence/absence badge needs no enum→config mapping helper (the
  existing `whatsappStatusBadge.tsx` helpers all map multi-value states). No helper
  file edit was needed.
- **Label source**: `NumberCardLabels` extended with
  `Partial<Pick<WhatsappConversationsLabels, "testNumberBadge">>` — the key from the
  `whatsappConversations` namespace (per outcome 4.1: reuse `testNumberBadge`; the
  whatsapp settings namespace has no equivalent key — verified via grep).
  **Optional (`Partial`) on purpose**: current consumers (desktop `NumberCard`,
  mobile `NumbersTab`, component tests) pass plain `WhatsappLabels`; a required key
  would break repo-wide tsgo. The chip renders only when a host supplies the label.

## Badge label wiring (carry-forward resolved)

Date: 2026-09-11.

- **Approach 1 chosen (merge in the ViewModel), not a duplicated namespace key.**
  The whatsapp settings ViewModel now also loads `Translation.WhatsappConversations`
  and merges `testNumberBadge` into the `page` label pack that flows to
  `NumbersTab.desktop.tsx` / `NumbersTab.mobile.tsx` and onward into
  `NumberCard` / `NumberCardContent`:
  - `frontend/common/views/dashboard/settings/whatsapp/useWhatsappSettingsViewModel.ts` —
    `useWhatsappLabels(whatsappLabels, testNumberBadge)` now composes
    `page: { ...whatsappLabels, testNumberBadge }`; main hook calls
    `useAppTranslation(Translation.WhatsappConversations)` and passes
    `conversationsLabels.testNumberBadge`.
  - `frontend/common/views/dashboard/settings/whatsapp/types/whatsappSettingsTypes.ts` —
    `WhatsappSettingsLabels["page"]` widened to
    `WhatsappLabels & Partial<Pick<WhatsappConversationsLabels, "testNumberBadge">>`.
- **Why not approach 2 (duplicate `testNumberBadge` into the `whatsapp` namespace):**
  it would duplicate one translated string across two namespaces plus both locale
  leaves and require snapshot regeneration — a larger diff with ongoing drift risk.
  Merging at composition time reuses the single canonical key from the
  `whatsappConversations` namespace (registered in task 4.1).
- **Why the key stays optional (`Partial`) on the composed type:** several component
  tests construct `WhatsappSettingsLabels` literals from bare
  `readTranslation(Translation.Whatsapp, ...)` output (`whatsappTemplatesTab`,
  `whatsappOptInTab*`, `whatsappCredentialDialogs`, `whatsappMobileParity`,
  `numbersHeaderSyncReason`, `whatsappLocalDeactivateConfirmDialog`). A required key
  would force edits to all of them outside the wiring scope. Runtime is still
  guaranteed: the ViewModel always supplies the merged value, so the settings-page
  chip renders with a defined label whenever `account.isTestNumber === true`.
- **Verification**:
  - `bun run scripts/health/sub-loop.ts` → **exit 0** for both edited files
    (`whatsappSettingsTypes.ts`, `useWhatsappSettingsViewModel.ts`).
  - `bun tsgo` repo-wide → 0 errors.
  - `bun run test/scripts/run-test.ts` →
    `test/ui/components/whatsapp/useWhatsappSettingsViewModel.test.tsx` 20/20 pass;
    `test/ui/components/whatsapp/whatsappNumberCardPurposeSync.test.tsx` 15/15 pass.
- `NumberCardContent.tsx` itself needed no change — its `NumberCardLabels`
  (`Partial<Pick<WhatsappConversationsLabels, "testNumberBadge">>`) already accepts
  the merged pack.
