## MEDIUM Severity

### M1 — Client-log ingestion has no batch/size caps or rate limit (disk-write DoS)

- **File**: `app/api/logs/route.ts`
- **Lines**: 188–226 (POST handler), 152–173 (`writeBatchLogs`)
- **Layer**: App Router API
- **Problem**: Authenticated (any logged-in user) POST writes attacker-supplied log entries verbatim to `logs/client_<sessionId>.log` on the server filesystem. There is no cap on `body.logs` array length, no per-message length limit, and no rate limit. An authenticated client (or a stolen access token) can write unbounded data to disk, and the `logBuffers`/`cleanedSessions` Maps grow unboundedly in-process. Gating is `CLIENT_LOGS_ENABLED` (line 186: `NODE_ENV === "development" || ENABLE_LOGGING === "true"`) — so this is live wherever `ENABLE_LOGGING=true`, including any opt-in production deployment.
- **Fix**:
  1. Cap the batch: reject `body.logs.length > 500` with 400 `tErrors.invalidRequestFormat` (existing key — verified `shared/locale/en/errors/index.ts:524`, `shared/locale/ar/errors/index.ts:522` vicinity) or map to `tErrors.rateLimitExceeded` (verified: en line 405, ar line 401).
  2. Truncate per-message: in `writeLogEntry` (line 137), truncate `entry.message` and `entry.caller` to ~4000 chars **after** `sanitizeForRendering`.
  3. Rate-limit per session/user: reuse `checkRateLimit` from `@/backend/lib/ratelimit` with a dedicated limiter (pattern: `app/api/webhooks/whatsapp/route.ts:68-72` — `webhookRateLimiter` with scoping key `whatsapp-webhook-verify:${ip}`; here key as `client-logs:${userId}`).
- **Code change** (sketch — exact placement in POST, before `writeBatchLogs` at line 224):
  ```ts
  // app/api/logs/route.ts — after isValidLogEntry checks (line 208-210)
  const MAX_LOG_ENTRIES_PER_BATCH = 500;
  if (body.logs.length > MAX_LOG_ENTRIES_PER_BATCH) {
    return NextResponse.json({ error: tErrors.invalidRequestFormat }, { status: 400 });
  }
  const rl = await checkRateLimit(`client-logs:${userId}`, clientLogsRateLimiter);
  if (!rl.success) {
    return NextResponse.json({ error: tErrors.rateLimitExceeded }, { status: 429 });
  }
  ```
- **i18n**: No new keys — `invalidRequestFormat`, `missingRequiredFields`, `rateLimitExceeded` all verified in en + ar.
- **Types**: None. New limiter constant in `backend/lib/ratelimit.ts` mirroring `authRateLimiter`/`webhookRateLimiter` definitions (verify field names there before implementing).
- **Tests**: Add component/route test asserting 400 for 501-entry batch and 429 past limit. Existing: none cover caps (search `app/api/logs` tests before adding).

### M2 — Non-platform deployments trust client-controlled `x-forwarded-for` (rate-limit bucket spoofing)

- **File**: `backend/graphql/gqlContextFactory.ts`
- **Lines**: 105–153 (`getIpAddress`)
- **Layer**: Backend GraphQL context
- **Problem**: `x-forwarded-for`/`x-real-ip` are honored unconditionally when not on Vercel/Cloudflare (lines 123–142). On a bare/VPS deployment without a trusted edge, any client sends its own `X-Forwarded-For` header and freely rotates IPs — defeating `checkRateLimit(ipAddress, …)` on `login`/`demoLogin`/`refreshToken`, `suggestion` and `complaintResponse` mutations, and `RateLimitService.recordAttempt` lockout tracking (which is keyed on `(ipAddress, email)` in `auth.mutation.ts:249` etc.).
- **Fix**: Gate raw header trust behind an explicit env flag, e.g. `TRUSTED_PROXY` (bool). When not set and not on Vercel/CF, skip `x-forwarded-for`/`x-real-ip` and fall through to the existing `anon:` UA+Accept-Language fingerprint (lines 148–152). Alternative: accept a `TRUSTED_PROXY_CIDRS` allowlist and only honor XFF when the immediate peer matches (requires access to `request.ip`/peer address — confirm availability in the current runtime first).
- **Code change** (sketch):
  ```ts
  // backend/graphql/gqlContextFactory.ts — before line 123
  const trustRawProxyHeaders = process.env.TRUSTED_PROXY === "1"; // document in .env.example
  if (trustRawProxyHeaders) {
    const forwardedFor = headersList.get("x-forwarded-for");
    // …existing lines 123-142 body…
  }
  // fall through to anon fingerprint
  ```
- **i18n**: No new keys.
- **Types**: None. Add `TRUSTED_PROXY` to `backend/lib/env-config-keys.ts` registry (pattern: existing `"ADMIN_PASSWORD"` entry at line 104) and `.env.example`.
- **Tests**: `backend/lib/ratelimit.test.ts` neighbors — add a context-factory unit test asserting XFF is ignored when `TRUSTED_PROXY` unset. Also update `docs/backend/login-cold-start-resilience.md` deployments note.

## LOW Severity

### L1 — Dead-code anonymous fallback `ctx.user?.id ?? ""` in Pothos resolvers

- **Files / lines** (all verified with grep):
  - `backend/graphql/pothos/parents/parent-document.pothos.ts:26, 42`
  - `backend/graphql/pothos/parents/parent-profile.pothos.ts:119, 132, 149, 164, 177, 194`
  - `backend/graphql/pothos/parents/parent-lifecycle.pothos.ts:27`
  - `backend/graphql/pothos/scheduling/schedule.pothos.ts:196`
- **Layer**: Backend GraphQL (Pothos)
- **Problem**: Each of these fields already carries `authScopes: { loggedIn: true }`, so `ctx.user` is non-null at resolve time; the `?? ""` fallback is dead code. Currently harmless because the downstream services re-gate permissions on the (possibly empty) id — e.g. `ParentProfileService.getProfile` (`backend/services/parent/parent-profile.service.ts:126-137`) throws `insufficientPermissions` for any actor lacking view-other permissions, including `""`. But the pattern hides wiring errors: if a service ever treats an empty userId as "no actor restriction", these become silent IDOR bypasses.
- **Fix**: Replace `ctx.user?.id ?? ""` with `ctx.user.id` at all 10 call sites. If tsgo complains about `ctx.user` nullability, add the existing resolver-level non-null assertion pattern used elsewhere (check how `logout`/`changePassword` in `auth.mutation.ts:474-509` rely on `ctx.user` after `authScopes`) — do **not** introduce new ad-hoc `?? ""` fallbacks.
- **i18n**: No new keys.
- **Types**: Depends on `ctx.user` typing in `gqlContextFactory.ts/context types` — if `BaseContext.user` is nullable by design, the field-level fix is the authScoping, not the type.
- **Tests**: Existing GraphQL integration tests under `frontend/common/graphql/test/parents/` exercise these resolvers with real sessions; verify they still pass after the change.

### L2 — `sql.raw` enum-append without membership validation (defense-in-depth)

- **File**: `backend/services/auth/permission-management.service.ts`
- **Line**: 503 (verified): `` sql.raw(`ALTER TYPE app_permission ADD VALUE IF NOT EXISTS '${key}';`) ``
- **Layer**: Backend services (bootstrap/seeder path)
- **Problem**: `ensurePermissionEnumValues(keys: readonly AppPermission[])` interpolates each key directly into raw SQL. All callers are internal bootstrap code (verified: only self-references under `backend/services/auth/`), and the parameter is typed `AppPermission[]` — so today this is not reachable with attacker input. But `sql.raw` bypasses Drizzle parameterization entirely; any future caller passing user-derived strings gets instant DDL injection.
- **Fix**: Validate before interpolation (one-line guard):
  ```ts
  // top of ensurePermissionEnumValues, before line 503
  const valid = new Set<string>(Object.values(AppPermission));
  for (const key of keys) {
    if (!valid.has(key)) throw new Error(`Unknown app_permission key: ${key}`);
  }
  ```
- **i18n**: No — internal invariant error, matches existing pattern in the same file (e.g. `CRITICAL: JWT_SECRET…` style internal throws in `backend/lib/env.ts:112` are intentional non-localized).
- **Types**: None (`AppPermission` already imported in this file).
- **Tests**: Service tests exist (`backend/graphql/mutation/auth/test/…` neighbors; find `permission-management` tests under `backend/services/**/test/`) — add a rejection case for an invalid key.

### L3 — GraphQL scalar validation errors are hardcoded English

- **Files / lines**:
  - `backend/graphql/scalars/stringMapScalar.ts:17–104` (5 throw sites × 2 — serialize + parse)
  - `backend/graphql/scalars/localizedStringScalar.ts:13–60` (similar)
- **Layer**: Backend GraphQL scalars
- **Problem**: Scalar parse/serialize errors throw English-only `GraphQLError` messages, violating the "no hardcoded user-facing strings" convention (backend instruction files). Mitigating factor: scalar coercion runs before GraphQL context is reliably available, and every throw already carries `extensions: { code: "BAD_USER_INPUT", … }` (verified lines 17–48), so clients can localize by code.
- **Fix**: Document as accepted exception (add a comment block in both scalar files citing this decision), OR add machine-readable `extensions.detail` (e.g. `part: "maxLength"`) so frontend locale files map precisely to labels. Do **not** attempt to thread locale through the scalar layer.
- **i18n**: If the `extensions.detail` route is chosen: new keys in the `errors` namespace of `shared/locale/types/errors/index.ts` + en/ar implementations, consumed client-side by clients on `BAD_USER_INPUT` responses. Keep strings English at the server.
- **Types**: If new keys, update `ErrorsLabels` type schema first (compile-time system enforces en/ar parity automatically).
- **Tests**: Existing scalar tests (check `backend/graphql/scalars/*.test.ts`) assert messages — update to assert `extensions.code`/`detail` instead where applicable.

### R2 — 🟡 L1 silent behavior change for unauthenticated test clients
- **Fix**: L1
- **Description**: Some GraphQL integration tests may call these resolvers without a session. Under `authScopes: { loggedIn: true }` they already get rejected before the resolver runs, so no behavior change — but if any test bypasses the builder (direct resolver invocation), `ctx.user.id` will now throw a TypeError instead of returning `""`.
- **Impact**: Potential new test failures in `frontend/common/graphql/test/parents/` if any test invokes the resolver layer directly.
- **Status**: **MITIGATED** — plan instructs to run the parents GraphQL test suite after the change; failures (if any) are the intended detection mechanism.

### R3 — 🟡 M2 env-var breadth
- **Fix**: M2
- **Description**: Adding `TRUSTED_PROXY` to `env-config-keys.ts` requires matching the existing entry shape (at line 104: `key: "ADMIN_PASSWORD"` with surrounding metadata). A partial registry entry can break the environment-config admin UI or its validation.
- **Impact**: `bun tsgo` or environment-config page errors if the registry shape is wrong.
- **Status**: **FIXED in this refinement** — plan names the file, pattern anchor, and requires reading surrounding entries before adding.
