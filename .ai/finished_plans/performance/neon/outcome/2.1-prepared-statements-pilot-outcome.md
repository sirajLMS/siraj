## Technical Decisions & Rationale

### Why Prepared Statements Can't Use Transactions

Drizzle's prepared statements are bound to the database session/client they were created with. The module-level `db` instance is a singleton with a specific session. When `db.transaction()` creates a transaction, it creates a **new session** (`tx`), and prepared statements created on the global `db` cannot be executed on `tx`.

This is a known Drizzle limitation (see [GitHub Issue #2826](https://github.com/drizzle-team/drizzle-orm/issues/2826)).

### Our Pattern: Transaction-Aware Prepared Statements

```typescript
export const existsByEmail = async (email: string, tx?: DBTransaction): Promise<boolean> => {
  const queryDb = tx ?? db;
  // Use prepared statement ONLY when no transaction
  if (!tx) {
    const [result] = await existsByEmailPrepared.execute({ email });
    return Number(result?.count ?? 0) > 0;
  }
  // Fall back to regular query for transactions
  return (await queryDb.$count(users, eq(users.email, email))) > 0;
};
```

This pattern:
- ✅ Uses prepared statements for the common case (no transaction)
- ✅ Maintains transaction support for write operations
- ✅ Zero behavioral change for callers
- ✅ Maximum performance for read-only queries

## Performance Impact

Prepared statements provide significant performance benefits:
- **Query planning happens once** at `.prepare()` time (module load)
- **Subsequent executions skip SQL parsing/planning** 
- **Parameter binding is faster** than string interpolation
- **Driver-level caching** of execution plans

For high-frequency queries like `findById`, `findByEmail`, and `existsByEmail`, this eliminates repeated SQL compilation overhead.

## Carry-Over Knowledge for Task 2.2 (Rollout)

### Pattern to Replicate
1. Define prepared statements at **module level** (not inside functions)
2. Use `sql.placeholder("name")` for dynamic parameters
3. Use `.prepare("descriptive_name")` with clear, unique names
4. Execute with `.execute({ placeholderName: value })`
5. For methods accepting `tx?: DBTransaction`:
   - Use prepared statement when `!tx`
   - Fall back to regular query when `tx` is provided

### Repositories to Refactor (Priority Order)
1. `backend/db/repo/auth/` - High-frequency auth queries
2. `backend/db/repo/classes/` - Class scheduling queries
3. `backend/db/repo/scheduling/` - Complex scheduling queries
4. `backend/db/repo/students/` - Student management queries
5. `backend/db/repo/teachers/` - Teacher queries
6. `backend/db/repo/parents/` - Parent queries

### Common Query Patterns to Convert
- Single-record lookups by ID: `where(eq(table.id, sql.placeholder("id")))`
- Single-record lookups by unique field: `where(eq(table.field, sql.placeholder("field")))`
- Existence checks: `select({ count: count() }).from(table).where(eq(table.field, sql.placeholder("field")))`
- Batch lookups: `where(inArray(table.id, sql.placeholder("ids")))`
- Count totals: `select({ total: count() }).from(table)`
