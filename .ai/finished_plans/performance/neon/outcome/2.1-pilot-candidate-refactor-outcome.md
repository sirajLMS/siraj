### 3. Transaction Fallback Pattern
**Critical Design Decision:** Drizzle prepared statements are bound to the session they were created with (the global `db` instance). They **cannot** be used inside transactions with a different `tx` client.

Implemented a fallback pattern for methods that accept `tx?: DBTransaction`:
```typescript
if (!tx) {
  // Use prepared statement (fast path)
  const [result] = await preparedStmt.execute({ param: value });
  return result;
}
// Fall back to regular query for transactions
return await tx.select().from(users).where(...);
```

This maintains:
- Performance benefits for read-only single queries (no transaction)
- Correctness for multi-statement transactions
- API compatibility (same method signatures)

### 4. Fixed $count Prepared Statement Limitation
Drizzle's `db.$count()` does NOT support `.prepare()` (known limitation). Workaround: use regular select with `count()` aggregation:
```typescript
const existsByEmailPrepared = db
  .select({ count: count() })
  .from(users)
  .where(eq(users.email, sql.placeholder("email")))
  .prepare("user_exists_by_email");
```

## Edge Cases & Learnings

1. **Prepared Statements + Transactions Don't Mix**: This is a Drizzle architectural constraint. The prepared statement is tied to the session (`db.session`). When using `db.transaction()`, a new session is created. The workaround is the fallback pattern above.

2. **$count() Has No .prepare()**: See GitHub issue #3084. Use `select({ count: count() })` instead.

3. **Complex WHERE Clauses**: Dynamic conditions (like search with optional filters) are difficult to prepare. Kept `findUsers()` and `findUsersPaginated()` as regular queries since they accept dynamic search parameters.

4. **Return Type**: Prepared statement `.execute()` returns an array. Access first element with `[0]` and handle null with `?? null`.
