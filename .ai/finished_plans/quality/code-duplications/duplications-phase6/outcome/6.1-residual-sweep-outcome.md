### Deferred Pairs (11 pairs, 1,111 tokens)

#### Pair #8: Excel Export Title Cell (84t) — DEFERRED
- `report-export.ts` `writeTitleAndSubtitle()` ↔ `shared-export-logic.ts` `writeMergedTitleCell()`
- **Reason:** `writeTitleAndSubtitle` writes BOTH a merged title cell AND a subtitle cell with `fromDate`/`toDate` range, while `writeMergedTitleCell` writes ONLY a merged title cell. The functions have different signatures (`writeTitleAndSubtitle` takes `fromDate`/`toDate`/`pageTitle`/`totalCols`, `writeMergedTitleCell` takes `pageTitle`/`totalCols`) and different behavior (subtitle row). The shared 6-line fragment is the merge-assignment + encode-cell + assignment pattern, which is too small to extract without changing the semantic boundary between "title-only" and "title+subtitle" functions. Already documented in outcome 4.4 as "already properly delegated."

#### Pairs #9-11: Billing ViewModels (303t) — DEFERRED
- `useParentBillingViewModel.ts` ↔ `useUserBillingProfileViewModel.ts`
- **Reason:** These are two different view models for two different billing pages (parent billing vs user billing profile). The duplicated fragments are invoice-mapping and summary-formatting logic that reference different GraphQL query shapes (`parentBillingSummary` vs `userBillingSummary`), different invoice types, and different page-specific fields. The mapping functions transform different data models into different view-model shapes. Extracting a shared mapping helper would require abstracting over both data models, which would be over-engineering for two consumers. Already documented in outcome 4.4 as "structurally too different."

#### Pair #12: Profile Loading Skeletons (83t) — DEFERRED
- `ParentProfileLoadingSkeleton.tsx` ↔ `StaffProfileLoadingSkeleton.tsx`
- **Reason:** Both files already delegate to a shared `ProfileLoadingSkeleton` component with a config object. The duplicated 10-line fragment is the `import` + `config` declaration + `export function` wrapper. The config values differ (4 gridCards vs 3 gridCards, different `rectHeight` values). The shared component is already extracted — the remaining duplication is just the import + config + export boilerplate, which is too small and too semantically different (parent profile layout vs staff profile layout) to justify further extraction. Already documented in outcome 4.4 as "already properly de-duplicated."

#### Pair #13: Supervisor Hero Cards (89t) — DEFERRED
- `common/.../heroSummaryCardShared.tsx` ↔ `mobile/.../supervisorHeroCardShared.tsx`
- **Reason:** Both are already shared scaffold components. The common variant renders `DesktopPrimaryPageAction` with `mt: "auto"` and `gap: 0.75`; the mobile variant renders `MobilePrimaryPageAction` without `mt` and with `gap: 0.5`. The duplicated 12-line fragment is the `<Stack>` + `<Typography>` title/subtitle block. The action components are tier-specific (desktop vs mobile), so extracting the title/subtitle Stack into a shared sub-component would require accepting the action component as a slot prop — but the action component is the only tier-specific part, and the Stack layout differs in `gap` and `mt`. The structural difference (different gap, different action component, different `mt` on the action) makes extraction not worthwhile for 12 lines.

#### Pair #14: Status Tracking DataGrid Suspended Row Styling (83t) — DEFERRED
- `desktop/.../statusTrackingDataGrid.desktop.tsx` ↔ `mobile/.../statusTrackingDataGrid.mobile.tsx`

The desktop and mobile variants use different grid configurations (different columns, different row height, different components). The duplicated 14-line fragment is the `paginationOptions` + `getRowClassName` + `sx` block. Extracting these into shared props would require a shared `useStatusTrackingGridProps()` hook, but the desktop and mobile data grids use different column definitions and different `AppDataGrid` configurations. The styling props are tightly coupled to each tier's grid setup.

#### Pair #15: Schedule Alerts View Props Interface (90t) — DEFERRED
- `desktop/.../scheduleAlertsView.desktop.tsx` ↔ `mobile/.../scheduleAlertsView.mobile.tsx`
- **Reason:** The duplicated fragment is the inline props interface type for the view body component: `{ loading, labels, classes, totalClasses, currentPage, pageSize, onFilter, onExport, onLeave, onViewClassAudit, onPageChange, gridLabels }`. Both desktop and mobile body components accept the same props, but they render completely different layouts (desktop uses `DesktopScheduleDataGrid`, mobile uses `MobileScheduleDataGrid`). The props interface could be extracted to a shared type, but it's an inline type annotation — extracting it to a shared `ScheduleAlertsViewBodyProps` type would add a new shared types file for a single-use interface. The two body components are structurally different (different grid components, different layout) and already delegate to tier-specific shared scaffolds.

#### Pair #16: Search Schedule View Props Forwarding (98t) — DEFERRED
- `desktop/.../searchSchedule.desktop.tsx` ↔ `mobile/.../searchSchedule.mobile.tsx`
- **Reason:** Both desktop and mobile views forward identical props to their tier-specific shared form components (`SearchScheduleFormDesktop` vs `SearchScheduleFormMobile`). The 18-line duplicated fragment is the props-forwarding block: `{ error, labels, draft, isSearching, onDraftChange, onSearch, ... }`. Both views destructure the same props from their view model and forward them, but they render different tier-specific components. The desktop view uses `SearchScheduleFormDesktop`, the mobile uses `SearchScheduleFormMobile` — these are already separate shared scaffolds. Extracting a shared "props forwarder" would require creating a shared component that accepts a slot for the form component, but the form components have different prop types.

#### Pair #17: Create Recurring Class Dialog Body (173t) — DEFERRED
- `desktop/.../createRecurringClassDialog.desktop.tsx` ↔ `mobile/.../createRecurringClassDialog.mobile.tsx`
- **Reason:** Both body components destructure the same viewModel fields and forward them to `CreateRecurringClassDialogShared` with identical prop-forwarding, then differ only in the `slots` object (tier-specific `DialogShell`, `StudentSelect`, `TimezoneSelect`, and `layout` config). The duplicated 49-line fragment is the destructure + forward block. Both already delegate to `CreateRecurringClassDialogShared` — the remaining duplication is the viewModel destructure + prop-forwarding (25 fields). Extracting a shared `useCreateRecurringClassDialogProps` hook that returns the destructured props would eliminate the destructure duplication, but the `slots` object (which is the tier-specific part) is interleaved with the forwarded props in the JSX. A factory pattern similar to the phone input factory could work, but the 25-prop forwarding + slots object is complex enough that the factory would be nearly as large as the duplication.

#### Pair #18: User Billing Profile View Props Forwarding (108t) — DEFERRED
- `desktop/.../userBillingProfile.desktop.tsx` ↔ `mobile/.../userBillingProfile.mobile.tsx`

The 23-line duplicated fragment is the props-forwarding block. The desktop view wraps in `DesktopPageContainer` + `DesktopPageHeader` and forwards to `BillingSectionDesktop`; the mobile view forwards to `BillingSectionMobile` with additional `pageTitle`/`pageSubtitle`/`metrics` props that the desktop variant doesn't have. The two section components accept different prop sets (mobile has `pageTitle`, `pageSubtitle`, `metrics`; desktop doesn't). This structural difference means a shared forwarder would need to handle the different prop sets, which would be over-engineering.
