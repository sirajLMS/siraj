# Task 6.1 — Overlay conditional in root layout + dashboard shell

## Summary

Implemented the `?customize=1` URL-param conditional that mounts the
site-appearance customizer overlay (toolbar above + sidebar beside the
app) and collapses the dashboard sidebar to icon-only (64px) with
hover-to-expand, restoring state on exit.

A new `useCustomizeMode()` client hook reads the `customize` search param
via `useSearchParams()` AND verifies the user holds
`SETTINGS_APPEARANCE_MANAGE` — a defense-in-depth re-check on top of the
`RequirePermission` wrapper around the header `CustomizeButton` (Task 6),
since a user could hand-craft a `?customize=1` URL even without the button
being rendered.

When customize mode is active:
- **Desktop**: `CustomizeToolbar` renders as a fixed 48px bar at `top: 0`
  (amber bottom border via `theme.palette.warning.main`). The dashboard's
  `NavbarStaticShell` (MUI `AppBar position="fixed"`) is pushed down 48px
  via a CSS descendant-selector override (`& .MuiAppBar-root { top: 48px }`).
  `CustomizeSidebar` (300px) renders as a flex item beside the dashboard
  content. The dashboard sidebar (in `SidebarShell`) force-collapses to
  64px icon-only and expands to full width on hover.
- **Mobile**: `CustomizeToolbar` renders as the same fixed 48px bar.
  `CustomizeSidebar` is hidden (`display: { xs: "none", md: "flex" }`) — no
  horizontal room beside the app on phone viewports. The mobile sidebar
  (temporary `Drawer`) is unaffected by customize mode.
- **Exit**: When `?customize=1` is removed from the URL (via the toolbar's
  Exit button — Task 6.2 — or by navigating away), `useCustomizeMode()`
  returns `false` and all overlay UI disappears. The dashboard sidebar
  state is automatically restored because the customize-mode logic never
  mutates the persisted `layoutStore.sidebarOpen` — it only overrides
  `isCollapsed` locally via `customizeMode ? !isHovered : !sidebarOpen`.

`CustomizeToolbar` and `CustomizeSidebar` are intentionally placeholders
(amber-bordered header + aside with a label string). Tasks 6.2 and 6.3
will implement the real controls (Exit/Undo/Redo/Save/Publish/Reset and
Brand Identity/Color editors/Logo upload/Default-mode radio).

## Requirements Coverage

- **AC-15** — Customizer overlay mounts via `?customize=1`.
  - `useCustomizeMode()` reads `useSearchParams().get("customize")` and
    returns `true` when the value is `"1"` AND the user has
    `SETTINGS_APPEARANCE_MANAGE`. The desktop and mobile dashboard
    layouts call this hook and conditionally render `CustomizeToolbar`
    + `CustomizeSidebar` (desktop only for the sidebar).
- **AC-16** — Dashboard sidebar collapses to icon-only in customize mode.
  - The inner `SidebarDesktop` component in `SidebarShell.tsx` calls
    `useCustomizeMode()`. When active, `collapsedWidth` changes from
    `"80px"` to `"64px"`, and `isCollapsed` is driven by hover state
    (`!isHovered`) instead of the persisted `sidebarOpen` flag. The
    edge toggle button is hidden (`{customizeMode ? null : (...)}`) to
    avoid a no-op affordance.
- **AC-17** — Hover-to-expand + state restoration on exit.
  - `onMouseEnter`/`onMouseLeave` handlers toggle `isHovered`, expanding
    the sidebar from 64px to `sidebarWidth` (260px). The 300ms CSS
    `transition: width` on the outer Box animates the expansion. On exit
    (`customizeMode → false`), `isCollapsed` falls back to
    `!sidebarOpen` without any store mutation, so the user's previous
    sidebar preference is preserved.

## Design Adherence

### No prop-drilling — hook called at the leaf

Instead of adding a `customizeMode` prop to `DashboardLayoutProps` and
threading it through `DashboardLayout` (switcher) →
`DashboardLayoutDesktop`/`Mobile` → `DashboardLayoutIsland` →
`SidebarDesktop` → `SidebarShell` (6 layers), the hook is called
directly in the 3 leaf components that need it:
- `dashboardLayout.desktop.tsx` — to render toolbar + sidebar
- `dashboardLayout.mobile.tsx` — to render toolbar
- `SidebarShell.tsx` (inner `SidebarDesktop`) — to collapse + hover-expand

This follows the existing pattern where `usePathname()`, `useFxLiveRefresh()`,
and `useAppTranslation()` are called directly in leaf components rather
than prop-drilled. The hook is cheap (one `useSearchParams` + one
`useUserStore` selector read), so calling it in 3 places has no
measurable performance impact.

### CSS descendant-selector for navbar offset

Both `NavbarStaticShell` (desktop) and `NavbarChrome` (mobile) use MUI
`<AppBar position="fixed">` which defaults to `top: 0` via the
`.MuiAppBar-positionFixed` CSS class. Rather than editing both navbar
components to accept a `topOffset` prop (2 extra files + API change), the
dashboard root `Box` applies a CSS override when customizeMode is active:

```tsx
sx={{
  ...(customizeMode && {
    paddingTop: "48px",
    "& .MuiAppBar-root": { top: "48px" },
  }),
}}
```

The selector `.css-hash .MuiAppBar-root` (specificity 0,2,0) overrides
`.MuiAppBar-positionFixed` (specificity 0,1,0). The `paddingTop` on the
root pushes in-flow children (the content area) down by 48px; the
AppBar's `top: 48px` shifts the fixed navbar below the toolbar. No
edits to `NavbarStaticShell.tsx` or `NavbarChrome.tsx` required.

### Sidebar state restoration — zero-mutation design

The customize-mode sidebar collapse does NOT mutate `layoutStore.sidebarOpen`.
Instead, `isCollapsed` is computed locally:

```tsx
const isCollapsed = customizeMode ? !isHovered : !sidebarOpen;
```

When customizeMode turns off (user exits), `isCollapsed` immediately
falls back to `!sidebarOpen` — the user's persisted preference from
`layoutStore`. No cleanup effect, no state reset, no race condition. The
`sidebarOpen` value in the store is untouched throughout the customize
session.

### Placeholder components — Tasks 6.2/6.3 contract

`CustomizeToolbar` and `CustomizeSidebar` are minimal placeholders:
- `CustomizeToolbar`: a `<Box component="header">` with fixed positioning,
  48px height, amber bottom border, and a `<Typography>` label
  "Customize Mode — placeholder (Task 6.2)".

## Decisions

- **Hook-at-leaf vs. prop-drilling.** Chose to call `useCustomizeMode()`
  directly in the 3 leaf components rather than adding a `customizeMode`
  prop to `DashboardLayoutProps` and threading it through 6 layers. The
  hook is a pure read of URL + user store state, so calling it in
  multiple places is safe and avoids touching the switcher
  (`DashboardLayout.tsx`), `DashboardLayoutIsland`, and `sidebar.desktop.tsx`.
  This matches the existing pattern where `usePathname()` and
  `useAppTranslation()` are called at the leaf.

- **CSS descendant-selector vs. `topOffset` prop on navbar shells.**
  Rather than editing `NavbarStaticShell.tsx` and `NavbarChrome.tsx` to
  accept a `topOffset` prop (2 extra files + API change), used a CSS
  override on the dashboard root `Box`: `& .MuiAppBar-root { top: "48px" }`.
  This works because MUI's `.MuiAppBar-positionFixed` sets `top: 0` at
  specificity 0,1,0, and our descendant selector wins at 0,2,0. No
  navbar component files were modified.

- **64px collapsed width (was 80px).** The task spec says "icon-only
  (64px)". The existing `SidebarDesktop` uses `collapsedWidth = "80px"`.
  In customize mode, `collapsedWidth` is set to `"64px"` to match the
  spec. The 16px difference gives more room for the `CustomizeSidebar`
  (300px) beside the collapsed dashboard sidebar.

- **Hide toggle button in customize mode.** The edge toggle button
  (`<Box onClick={toggleSidebar}>`) is rendered as `null` when
  customizeMode is active. Reason: clicking it would toggle
  `layoutStore.sidebarOpen`, but `isCollapsed` is driven by `!isHovered`
  in customize mode, so the toggle would have no visual effect — a
  confusing no-op. Hiding it is cleaner than disabling it.

- **Mobile: no CustomizeSidebar.** The 300px sidebar doesn't fit beside
  the app on phone viewports. `CustomizeSidebar` uses `display: { xs:
  "none", md: "flex" }`. The toolbar still renders on mobile (48px fixed
  bar above the navbar) so the Exit/Save/Publish controls (Task 6.2)
  will be accessible. A mobile-friendly sidebar (e.g. bottom sheet or
  full-screen panel) can be added in a follow-up if needed.
