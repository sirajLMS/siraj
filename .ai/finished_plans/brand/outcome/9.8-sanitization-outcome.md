# Task 9.8 — Defense-in-Depth Input Sanitization & Long-Lived Asset Caching

## Summary

Added three defense-in-depth input sanitizers (`normalizeHexColor`,
`sanitizeMetadataHtml`, `sanitizeSiteName` / `sanitizeSiteTitle` /
`sanitizeSiteDescription`) in a new `shared/lib/appearance.helpers.ts`,
wired them into `AppearanceSettingsService.saveDraft` as the upstream guard
*before* the Task 9.10 Zod re-validation, and upgraded the file-serving
route to emit `Cache-Control: public, max-age=31536000, immutable` for
appearance-logo assets (UUID-keyed, effectively immutable per decision §20).

This satisfies **AC-34** (defense-in-depth input sanitization + long-lived
CDN cache headers for logo uploads): every free-form field that crosses the
GraphQL → JSONB boundary is now sanitized before schema validation, and
logo assets are served with a one-year immutable cache header so the CDN
edge can cache them indefinitely without revalidation.

## Requirements Coverage

- **AC-34** — Defense-in-depth input sanitization & long-lived asset caching:
  - **Hex color normalization**: `normalizeHexColor(input)` trims
    whitespace, strips internal whitespace, prepends `#` if missing,
    lowercases, and validates against the canonical `APPEARANCE_HEX_PATTERN`
    (`^#[0-9a-fA-F]{6}$` from `shared/schemas/appearance.zod.ts` — Task
    9.10). Returns `INVALID_HEX_FALLBACK` (`#000000`) for unsalvageable
    inputs so no malformed color string can ever reach the JSONB column.
  - **Metadata HTML sanitization**: `sanitizeMetadataHtml(html)` runs the
    input through `isomorphic-dompurify` (declared in `package.json`) with
    a tight `ALLOWED_TAGS` allowlist (`b`, `i`, `em`, `strong`, `a`, `p`,
    `br`) and `ALLOWED_ATTR: ["href"]`. Strips `<script>`, `onload=`,
    `javascript:` URIs, and other XSS vectors. Never throws — falls back
    to a regex-based tag strip if jsdom is unavailable.
  - **Site name / title sanitization**: `sanitizeSiteName(name, maxLength)`
    pipes through `sanitizeMetadataHtml` then strips ALL remaining HTML
    tags via `/<[^<>]*>/g` (linear regex, satisfies `sonarjs/super-linear-regex`)
    and truncates to `maxLength` (defaults: 80 for siteName, 120 for
    siteTitle — matches the Zod schema bounds).
  - **Service integration**: `AppearanceSettingsService.saveDraft` calls
    `sanitizeAppearanceFields(input)` *before* `zAppearanceFields.safeParse`
    so the Zod validator sees already-clean input. Sanitize early, validate
    late, persist only validated-and-sanitized payloads.
  - **Immutable logo cache headers**: `app/api/storage/files/[[...path]]/route.ts`
    now calls `resolveCacheControl(relativePath)` for every served file.
    Paths under `public/appearance/` (matched via the new
    `isAppearanceLogoStoragePath` helper in `shared/utils/appearance-logo-storage.utils.ts`)
    return `"public, max-age=31536000, immutable"`; all other paths keep
    the existing `"public, max-age=3600"` default. Applied to both the
    `200 OK` response and the `206 Partial Content` (range request) response.

## Design Decisions

### Why sanitize BEFORE Zod validate (not after)?

The Zod schema (Task 9.10) is the *final* guard — it rejects inputs that
don't match the canonical shape. But Zod does not *normalize* inputs: a
hex color `"  #0D9488  "` (with whitespace) would fail the strict
`APPEARANCE_HEX_PATTERN` even though a human would consider it valid.
Sanitizing first means:

1. The Zod validator sees already-clean input — fewer false-negative
   rejections for benign variations (whitespace, case, missing `#`).
2. The persisted payload is *canonical* — `#0d9488`, not `#0D9488` or
   `  #0d9488  `. This keeps the JSONB column tidy and makes
   equality-based diffing (e.g. "has the draft changed since the last
   publish?") reliable.
3. Defense-in-depth: even if a future code path bypasses the Zod schema
   (e.g. a direct service caller, an ENV-config override replay), the
   sanitization layer still strips XSS vectors before the payload reaches
   the JSONB column.

The order is: **GraphQL input type → sanitize → Zod validate → persist**.
Each layer catches a different failure mode; none is bypassed.

### Why DOMPurify (not a regex strip)?

A naive `/<[^>]*>/g` strip is insufficient for XSS defense because it
can be confused by malformed input like `<scr<script>ipt>` — the inner
`<script>` is stripped, leaving `<script>` which is then a live tag.
DOMPurify (via `isomorphic-dompurify`, already in `package.json`) parses
the HTML into a DOM tree, walks it, and removes disallowed tags/attributes
*recursively* — there's no way for a malformed-nesting attack to survive.

For `sanitizeMetadataHtml`, we use a tight `ALLOWED_TAGS` allowlist
(`b`, `i`, `em`, `strong`, `a`, `p`, `br`) and `ALLOWED_ATTR: ["href"]`.
This is stricter than DOMPurify's default (which preserves `<table>`,
`<h1>`, `<div>`, etc.) because metadata descriptions are short blurbs —
there's no legitimate reason for a `<script>` or `<iframe>` to appear in
a site description.

### Why `sanitizeSiteName` strips ALL tags (not just dangerous ones)?

`siteName` and `siteTitle` are documented as plain text — they're
rendered in `<title>`, `og:site_name`, and the navbar brand. Any HTML
tag in these fields is either:
1. A copy-paste mistake (e.g. the admin pasted "Siraj <b>Platform</b>"
   from a marketing doc) — stripping the tags recovers the plain text.
2. An XSS attempt — stripping the tags neutralizes it.

Either way, the right action is to strip ALL tags. `sanitizeSiteName`
pipes through `sanitizeMetadataHtml` first (to neutralize malformed
nesting) then strips any remaining tags via `/<[^<>]*>/g`.

### Why `INVALID_HEX_FALLBACK = "#000000"` (not throw, not null)?

Three options for handling unsalvageable hex input:
1. **Throw** — would create an inconsistent UX (the GraphQL layer should
   have already rejected; throwing here would surface a 500 to the user).
2. **Return `null`** — would violate the Zod schema (which requires a
   non-null string) and force every caller to branch on null.
3. **Return a safe sentinel (`#000000`)** — pure black, handled by MUI's
   `nativeColor` derivation and the WCAG contrast math without producing
   NaN or CSS parse errors. The admin sees a visible "your input was
   invalid" signal (the color turns black) and can correct it.

Option 3 is the same pattern as `parseHex` in
`shared/lib/color-contrast.utils.ts` (Task 9.6), which returns
`{ r: 0, g: 0, b: 0 }` for invalid hex. Consistent across the codebase.

### Why the regex `/<[^<>]*>/g` (not `/<[^>]*>/g`)?

The `sonarjs/super-linear-regex` lint rule flags `/<[^>]*>/g` as
super-linear due to potential backtracking. In practice `[^>]*` is
linear (it matches anything except `>`, so there's no ambiguity), but
the rule is conservative. Switching to `[^<>]*` (matches anything except
`<` or `>`) is strictly linear by the rule's analysis and behaves
identically for tag stripping: `<a>b<c>` matches as `<a>` then `<c>` in
both patterns. Documented in the regex's JSDoc.

### Why immutable cache headers for logos are safe

Logos are stored under UUID-randomized keys
(`public/appearance/logo-<uuid>.<ext>` — Task 7). A re-upload of the same
logical logo produces a *new* URL (new UUID), not an overwrite of the
prior asset. This means:

- The bytes behind any given logo URL never change for the lifetime of
  the deployment — the asset is effectively immutable.
- A `Cache-Control: public, max-age=31536000, immutable` header is safe:
  no client will ever see a stale logo (a new logo just gets a new URL,
  and the old URL stays valid for any cached published row that still
  references it — see Task 7 outcome §"Architecture Decision").
- The `immutable` directive tells browsers/CDNs to skip the conditional
  revalidation on reload (saving a 304 round-trip per asset), which
  shifts read traffic off the Next.js server and onto the CDN edge.

If the storage pipeline ever adds an in-place overwrite path for logos
(decision §20 explicitly *forbids* this, but if it ever changes), the
cache header would need to be downgraded — the `resolveCacheControl`
helper is the single seam to change.

### Why `resolveCacheControl` is a function (not a const)

The cache-control value depends on the *path* of the served file, not
just the content-type. A function lets the route handle both appearance
logos (immutable) and other public assets (short-lived) with a single
call site. If the rule ever needs to consider content-type too (e.g.
immutable for all images, short-lived for documents), the function is
the natural extension point.

## Decisions

- **Sanitize BEFORE Zod validate.** See "Why sanitize BEFORE Zod validate"
  above. The order is: GraphQL input type → sanitize → Zod validate →
  persist. Each layer catches a different failure mode; none is bypassed.

- **DOMPurify via `isomorphic-dompurify` (not a regex strip).** See "Why
  DOMPurify (not a regex strip)?" above. DOMPurify parses into a DOM
  tree and removes disallowed tags recursively — no malformed-nesting
  attack can survive. `isomorphic-dompurify` is already declared in
  `package.json` (`^3.22.0`) and works isomorphically (server + browser).

- **Tight `ALLOWED_TAGS` allowlist for metadata HTML.** `b`, `i`, `em`,
  `strong`, `a`, `p`, `br` — sufficient for a description blurb, and
  auditable. DOMPurify's default (which preserves `<table>`, `<h1>`,
  `<div>`, etc.) is unnecessarily permissive for a metadata context.

- **`INVALID_HEX_FALLBACK = "#000000"` (not throw, not null).** See "Why
  `INVALID_HEX_FALLBACK = "#000000"`?" above. Consistent with the
  `parseHex` pattern in `color-contrast.utils.ts` (Task 9.6).

- **`/<[^<>]*>/g` (not `/<[^>]*>/g`).** Strictly linear, satisfies
  `sonarjs/super-linear-regex`, identical tag-stripping behavior.

- **`sanitizeAppearanceFields<T extends SanitizableAppearanceFields>(input: T): T`
  is generic.** Preserves the input type (no `as` cast, no unsafe
  assertion). The `SanitizableAppearanceFields` interface has every
  field `unknown`-typed so it's structurally compatible with
  `AppearanceFields`, `AppearanceSettingsSubmitInput`, JSONB blobs, or
  ENV parses — no circular type import from `@/backend/types` (which
  would violate `shared/` layer isolation).

- **`resolveCacheControl(relativePath)` is a function (not a const).**
  See "Why `resolveCacheControl` is a function" above. The cache-control
  value depends on the path; a function is the natural extension point
  if the rule ever needs to consider content-type too.

- **Immutable cache header for logos is safe because of UUID keying.**
  See "Why immutable cache headers for logos are safe" above. The
  storage pipeline (Task 7) writes logos under UUID-randomized keys, so
  re-uploads produce new URLs — the bytes behind any given URL never
  change. No cache-invalidation story is needed.
