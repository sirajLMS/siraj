## Implementation Details

### Exports
- **Object types** (4 — all expose `id` for Apollo cache normalization):
  - `AppearanceColorPairPothosObject` — `{ primaryMain, secondaryMain }` (one mode).
  - `AppearanceColorsPothosObject` — `PerModeColors` (light + dark pairs).
  - `AppearanceFieldsPothosObject` — full `AppearanceFields` bundle (nested
    `colors`, `logoUrl`, scalars, `defaultColorScheme`).
  - `AppearanceSettingsPothosObject` — canonical
    `AppearanceSettingsReturnType` (full row + nested `draftFields`).
- **Input types** (3):
  - `AppearanceColorPairInputRef` — input mirror of the color pair.
  - `AppearanceColorsInputRef` — input mirror of `PerModeColors`.
  - `AppearanceDraftInputPothosRef` — input mirror of
    `AppearanceSettingsSubmitInput` (= `AppearanceFields`).
- **Query**: `appearanceSettings(draft: Boolean = false): AppearanceSettings`
  - `authScopes: { loggedIn: true }` (Pothos-level minimum).
  - Resolver-level permission gate: `draft=true` →
    `assertCanManageAppearance` (SETTINGS_APPEARANCE_MANAGE or superAdmin);
    `draft=false` → `assertCanViewAppearanceSettings` (SETTINGS_VIEW or
    SETTINGS_APPEARANCE_MANAGE or superAdmin).
  - Delegates to `AppearanceSettingsService.getAppearance({ actorUserId, draft })`.
- **Mutations** (all return `AppearanceSettings`, not `Boolean` — matches
  sibling `upsertSiteContent` pattern so the frontend Apollo cache can update
  the entity directly):
  - `saveAppearanceDraft(input: AppearanceDraftInput!): AppearanceSettings!`
  - `publishAppearance: AppearanceSettings!`
  - `resetAppearanceDraft: AppearanceSettings!`
  - All three: `authScopes: { permission: SETTINGS_APPEARANCE_MANAGE,
    notImpersonating: true }` + `requireAuth(ctx)` for the userId.

### Key Design Decisions
- **`defaultColorScheme` exposed as `String!` (not a Pothos enum)**: per
  `backend/graphql/pothos/AGENTS.md`, GraphQL enums MUST be backed by a real
  TypeScript `enum` in `backend/enum/`. `PaletteMode` is a MUI string-union
  type alias, not an enum. A `coercePaletteMode` runtime helper bridges the
  GraphQL `string` → `PaletteMode` ("light" | "dark") at the resolver level
  (defaults to `"dark"` for invalid input). A follow-up task should create a
  canonical `PaletteMode` enum and migrate — see "Carry-Forward".
- **Custom `AppearanceDraftInputShape` type**: the input ref's type parameter
  is `AppearanceDraftInputShape` (a locally-defined `Omit<…> & {…}`) rather
  than `AppearanceSettingsSubmitInput` directly, because Pothos input field
  semantics don't perfectly align with `AppearanceFields`:
  - `defaultColorScheme` is `string` (GraphQL), not `PaletteMode` (service).
  - `logoUrl` is `string | null | undefined` (omittable + nullable in GraphQL),
    not `string | null` (always present in service).
  A `toAppearanceSubmitInput` helper does the runtime conversion.
- **Mutations return entity, not `Boolean`**: design §5 sketch used
  `type: "Boolean"` for mutations, but the sibling `upsertSiteContent`
  pattern returns the entity. Returning `AppearanceSettings` lets the frontend
  update its Apollo cache in-place after a mutation. This is the standard
  pattern in the codebase.
- **`draft` query arg is a permission-gate marker**: per Task 2.3 carry-forward
  note, `getAppearance` always returns the full row (including `draftFields`).
  The `draft` flag does NOT change the data returned — it only escalates the
  required permission. `draft=true` requests the live (possibly unpublished)
  draft state and requires `SETTINGS_APPEARANCE_MANAGE`. `draft=false` is the
  general admin view (SETTINGS_VIEW suffices).
- **No DataLoader**: this entity is a single global row (no per-parent lookups),
  so DataLoader batching is unnecessary. The read path goes through
  `getAppearance` → `AppearanceSettingsRepository.get()` → single SELECT.

### GraphQL Schema Layout (post-codegen)
```
type AppearanceSettings {
  id: String!
  primaryMain: String!
  secondaryMain: String!
  logoUrl: String
  siteName: String!
  siteTitle: String!
  siteDescription: String!
  defaultColorScheme: String!  # NOTE: not an enum yet (see Carry-Forward)
  draftFields: AppearanceFields!
  updatedByUserId: String
  updatedAt: DateTime!
  createdAt: DateTime!
}

type AppearanceFields {
  colors: AppearanceColors!
  logoUrl: String
  siteName: String!
  siteTitle: String!
  siteDescription: String!
  defaultColorScheme: String!
}

type AppearanceColors {
  light: AppearanceColorPair!
  dark: AppearanceColorPair!
}

type AppearanceColorPair {
  primaryMain: String!
  secondaryMain: String!
}

input AppearanceDraftInput {
  colors: AppearanceColorsInput!
  logoUrl: String
  siteName: String!
  siteTitle: String!
  siteDescription: String!
  defaultColorScheme: String!
}

input AppearanceColorsInput {
  light: AppearanceColorPairInput!
  dark: AppearanceColorPairInput!
}

input AppearanceColorPairInput {
  primaryMain: String!
  secondaryMain: String!
}

type Query {
  appearanceSettings(draft: Boolean = false): AppearanceSettings
}

type Mutation {
  saveAppearanceDraft(input: AppearanceDraftInput!): AppearanceSettings!
  publishAppearance: AppearanceSettings!
  resetAppearanceDraft: AppearanceSettings!
}
```

## Issues Encountered
- **Initial design mismatch on mutation return type**: design §5 sketch used
  `type: "Boolean"` for all 3 mutations. Adjusted to return
  `AppearanceSettings` (entity) to match the sibling `upsertSiteContent`
  pattern and enable Apollo cache normalization. This is a deviation from
  the literal design but aligns with the established codebase pattern.
- **`defaultColorScheme` enum absence**: no canonical `PaletteMode` enum
  exists in `backend/enum/`. Used `String!` + runtime coercion as a
  stopgap. Documented as a follow-up task.
- **Pothos `t.arg` vs `t.field` in InputFieldBuilder**: the `t.arg` method
  exists on QueryFieldBuilder/MutationFieldBuilder (for query args) but NOT
  on InputFieldBuilder (for input type fields). Nested input refs must use
  `t.field({ type: X, required: true })`. This wasn't immediately obvious
  from the design sketch.
