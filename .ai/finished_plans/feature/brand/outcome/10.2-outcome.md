feature. The suite covers **Tier 1** (happy-path read/write through the

## Requirements Coverage

- **AC-5** — `appearanceSettings(draft)` query: both `draft=false` and
  `draft=true` happy-path tests assert the super admin can read the row
  without throwing a permissions error.
- **AC-6** — Draft-view permission escalation: a dedicated test asserts
  that `draft=true` succeeds for the super admin (who has
  `SETTINGS_APPEARANCE_MANAGE`), and a Tier-4 test asserts it's denied
  for `teacher_default` (who does not).
- **AC-7** — Permission gating: four Tier-4 tests assert that
  `teacher_default` (no `SETTINGS_APPEARANCE_MANAGE`) is denied on
  `saveAppearanceDraft`, `publishAppearance`, `resetAppearanceDraft`,
  and the draft-view query.
- **AC-8** — `saveAppearanceDraft` happy path: asserts the returned row's
  `draftFields` match every input field (siteName, siteTitle,
  siteDescription, defaultColorScheme, colors.light.primaryMain,
  colors.dark.secondaryMain).
- **AC-9** — `publishAppearance` happy path: asserts the published columns
  match `draftFields` after publish, and that `resetAppearanceDraft`
  re-aligns `draftFields` to the published state.
- **AC-34** — XSS sanitization: a Tier-4 test submits
  `<script>alert("xss")</script>SafeName` in `siteName`,
  `<img src=x onerror="alert(1)">SafeTitle` in `siteTitle`, and
  `<p>ok</p><script>alert(1)</script>` in `siteDescription`. Asserts the
  persisted values do NOT contain `<script>` tags or `onerror` attributes
  (sanitized by the Task 9.8 `sanitizeAppearanceFields` layer).
- **AC-39** — Mutation auth: every mutation has at least one
  unauthorized-attempt test (`teacher_default` is denied).

## Design Decisions

### Why `teacher_default` for the unauthorized tests?

The `teacher_default` permission group (defined in
`shared/constants/permission-group.enum.ts`) is a specialized
non-administrative role — it does NOT carry `SETTINGS_APPEARANCE_MANAGE`
nor `SETTINGS_VIEW`. This makes it the cleanest negative-control subject
for all four unauthorized scenarios (mutations + draft-view query). The
`assertOperationDenied` helper logs in via `demoLogin` with the
`teacher_default` group slug, executes the operation with
`errorPolicy: "all"`, and returns `true` if either a thrown error or
`result.error` is present — which is exactly what the Pothos
`authScopes: { permission: SETTINGS_APPEARANCE_MANAGE }` gate produces.

### Why `expectedUpdatedAt: undefined` on every mutation variable object?

The codegen for `saveAppearanceDraft` and `publishAppearance` produces
an `Exact<{ input: …; expectedUpdatedAt: string | null | undefined }>`
type. The `Exact` utility (from `@graphql-typed-document-node/core`)
makes every property required at the type level — you must *pass* the
key, even if the value is `undefined`. Passing `{ input: … }` alone
fails tsgo with `TS2741: Property 'expectedUpdatedAt' is missing`.
Adding `expectedUpdatedAt: undefined` satisfies the type without
actually sending the field over the wire (Apollo Client omits
`undefined` values). This matches the pattern used by other settings
tests that pass optional variables.

### Why a cleanup test at the end (not `afterAll`)?

The `appearance_settings` table is a single global row — there's no
per-test isolation. The Tier-4 XSS test (test #11) leaves a sanitized
payload in `draft_fields`, and the Tier-1 publish test (test #5)
mutates the published columns. To keep the suite idempotent across
repeated runs, the final test (test #12) saves + publishes + resets
back to `DEFAULT_INPUT`. Using a `test()` (not `afterAll`) keeps the
cleanup visible in the test report and surfaces failures (e.g. if the
server crashes mid-run, the cleanup test will fail loudly rather than
silently swallowing in an `afterAll` hook).

### Why `loginAndProvision` (not just `loginDemoUser`)?

`loginAndProvision` is the convention used by sibling settings tests
(`site-content-settings.test.ts`, `general-settings.test.ts`). It
logs in the super admin AND provisions a set of test entities (teacher,
student, parent, class, etc.) — slightly heavier than we need for
appearance-only tests, but it keeps the test file consistent with the
existing pattern and doesn't require a new helper. The provisioned
entities are unused by the appearance tests; they're a harmless
side-effect.

### Why assert `not.toContain("<script>")` (not `toBe("SafeName")`)?

The Task 9.8 sanitizer (`sanitizeSiteName`) pipes the input through
DOMPurify (tight `ALLOWED_TAGS` allowlist) and then strips any
remaining HTML tags via `/<[^<>]*>/g`. The exact output depends on
DOMPurify's behavior on malformed nesting, which can vary across
versions. Asserting the absence of `<script>` and `</script>` is a
robust, version-independent invariant: no XSS payload can survive the
sanitizer. Asserting the exact string would be brittle and would
duplicate the unit tests planned for Task 10.1.

## Decisions

- **`teacher_default` as the negative-control role.** See "Why
  `teacher_default` for the unauthorized tests?" above. Cleanest
  specialized non-admin role; no `SETTINGS_VIEW` or
  `SETTINGS_APPEARANCE_MANAGE` permission.

- **`expectedUpdatedAt: undefined` on every mutation variable object.**
  See "Why `expectedUpdatedAt: undefined` on every mutation variable
  object?" above. Required by the `Exact<…>` codegen utility.

- **Cleanup as a `test()` (not `afterAll`).** See "Why a cleanup test
  at the end (not `afterAll`)?" above. Keeps cleanup visible in the
  test report and surfaces failures loudly.

- **Assert `not.toContain("<script>")` (not `toBe("SafeName")`).** See
  "Why assert `not.toContain('<script>')` (not `toBe('SafeName')`)?"
  above. Robust, version-independent invariant.

- **`DEFAULT_INPUT` typed `as const`.** Propagates the literal types
  (`"#1976d2"`, `"light"`, etc.) into the GraphQL variable
  type-check, so tsgo can verify the colors match the
  `AppearanceDraftInput` shape exactly.

## Carry-Forward / Deferred

- **Optimistic-concurrency conflict test (AC-33).** The
  `expectedUpdatedAt` argument is exercised only as `undefined` (force
  write). A dedicated test that passes a stale `expectedUpdatedAt`
  and asserts the `APPEARANCE_CONFLICT_ERROR_CODE` GraphQL error code
  is deferred to Task 10.1 (service tests) where the conflict path
  can be unit-tested without the full HTTP round-trip. The plumbing
  is in place here — a follow-up test would just pass a known-stale
  timestamp and assert `result.errors[0].extensions.code ===
  "APPEARANCE_CONFLICT"`.

- **Argument-permutation tests.** The task description mentions "full
  argument permutation tests". The current suite covers the
  `draft: true/false` permutation on the query and the
  `expectedUpdatedAt: undefined` (omitted) path on every mutation.
  A exhaustive permutation matrix (e.g. `logoUrl: null` vs
  `logoUrl: "https://…"`, `defaultColorScheme: "light"` vs `"dark"`
  vs invalid) is deferred — the Zod schema (Task 9.10) and the
  service tests (Task 10.1) cover the validation boundary; the
  GraphQL layer just forwards to the service.

- **Full `test:graphql` run.** Not executed here (budget). The
  single-file run validates the suite; the full run is part of the
  Task 11 quality gate.
