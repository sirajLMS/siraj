## Summary

Registered two branding env-config descriptors (`NEXT_PUBLIC_APP_BRANDING` and
`APP_THEME_PRESET`) in `backend/lib/env-config-keys.ts` under a new `branding`
category, and wired the env-config override write/delete paths to invalidate the
SSR appearance cache (`revalidateTag("appearance")`) in addition to the
module-scoped `EnvironmentConfigService` cache. This closes AC-30: an admin
overriding either branding env key from the Settings → Environment Config tab
will see the new branding/preset value picked up on the next SSR render.

## Design Decisions

### D1: Why a `BRANDING_ENV_KEYS` Set instead of a `category === "branding"` check?

A category-based check (`descriptor.category === "branding"`) would have
required resolving the descriptor inside `maybeInvalidateAppearanceCache`. The
Set-based check is O(1) and decoupled from the descriptor index — it answers
the question "does this env key affect appearance?" directly, without
indirection through the descriptor's UI grouping.

This also future-proofs against the case where a branding-related env key is
added under a different category (e.g. a future `SITE_LOGO_URL` might be
grouped under `"storage"` because it's a URL, but it still affects
appearance). The Set is the canonical "appearance-affecting env keys" list.

### D2: Why delegate to `revalidateAppearanceCache()` instead of importing `next/cache` directly?

The `environment-config.service.ts` module's top-of-file docstring declares it
"isomorphic-safe: it imports only from `@/backend/**` and never touches
`@/app/**` or `next/*` APIs." Importing `next/cache` directly would violate
that contract. Delegating to `revalidateAppearanceCache()` (exported from
`appearance-settings.service.ts`, which already imports `next/cache`) keeps
the `next/*` surface area localised to the appearance service module and
centralises the cache-life profile (`"max"`) in one place.

### D3: Why `try/catch` around `revalidateAppearanceCache()`?

`revalidateTag` from `next/cache` is a server-runtime API. In rare cases
(e.g. invoked outside a request context, or during build), it may throw.
The env-config override write has already persisted to `system_settings` and
invalidated the env-config cache by the time `maybeInvalidateAppearanceCache`
runs — a failure here only delays the new branding by one TTL window (the
`unstable_cache` layer will eventually expire and re-fetch). Wrapping in
`try/catch` with a `logger.warn` ensures the write succeeds even if the
cache invalidation fails. This mirrors the existing best-effort audit-emit
pattern in `appearance-settings.service.ts:emitPublishAudit`.

### D4: Why `excludeFromDb: false` for `NEXT_PUBLIC_APP_BRANDING`?

The top-of-file docstring in `env-config-keys.ts` (lines 16-18) warns that
"`NEXT_PUBLIC_*` keys are intentionally excluded from the registry when they
ARE build-time-inlined into client bundles (DB overrides at runtime would NOT
reach already-shipped client code — misleading and dangerous)."

`NEXT_PUBLIC_APP_BRANDING` is the exception: it is consumed server-side at
runtime by `getResolvedAppearance()` (per implementation.md §16.3, tier-4
fallback) and `readAppearanceFromEnv()` (per Task 9.2 — see
`appearance-settings.service.ts:384`). It is NOT inlined into client bundles
at build time. DB overrides at runtime DO reach the consumer. This matches
the precedent set by `NEXT_PUBLIC_ENABLE_USERS_DIRECTORY` (descriptor at
line 645), which is also `excludeFromDb: false` for the same reason.

## Cache Invalidation Flow (AC-30)

```
Admin clicks "Save" on NEXT_PUBLIC_APP_BRANDING in Settings → Environment Config tab
  ↓
GraphQL mutation → upsertEnvConfigOverride({ key: "NEXT_PUBLIC_APP_BRANDING", value: "..." })
  ↓
SystemSettingsRepository.upsertSetting({ key: "env::NEXT_PUBLIC_APP_BRANDING", ... })
  ↓ (row persisted in system_settings)
invalidateEnvConfigCache("NEXT_PUBLIC_APP_BRANDING")
  ↓ (module-scoped env-config cache entry dropped — next resolveEnvConfig() re-queries DB)
maybeInvalidateAppearanceCache("NEXT_PUBLIC_APP_BRANDING")
  ↓ (key is in BRANDING_ENV_KEYS → revalidateAppearanceCache())
revalidateTag("appearance", "max")
  ↓ (Next.js unstable_cache tag invalidated — next getFirstAppearancePublished() re-queries DB)
resolvedAppearanceMemo = null
  ↓ (in-memory Tier 1 memo cleared — next getResolvedAppearance() re-parses env / re-queries DB)
```

Both caches (env-config + appearance) are invalidated atomically after the
DB write. The next SSR pass picks up the new branding value.
