### 0.4 Migration — **custom SQL path, NOT `drizzle-kit generate`** (deviation, deliberate)
- `drizzle-kit generate` was **intentionally not run**: the shared tree carries another plan's
  in-flight schema (whatsapp v2: 5 new tables, 7 new pg enums, new columns on
  `whatsapp_accounts`) that exists in TS but not in any snapshot. `generate` diffs the whole
  tree and would have swept that DDL into Plan 6's migration folder.
- Instead, schema shipped as **`backend/db/migration/45-expenses-table.sql`** (custom SQL,
  same class as `42-carryover-items-original-partial-percentage.sql`): guarded
  `CREATE TYPE expense_type`, `CREATE TABLE IF NOT EXISTS expenses`, DO-guarded CHECK + 3 FK
  ADD CONSTRAINTs, 9 `CREATE INDEX IF NOT EXISTS`. Fully idempotent; constraint names follow
  drizzle conventions (`expenses_teacher_id_teachers_id_fkey`, …).
- Both 44/45 were bundled with the bundler's own per-file logic (folders
  `20260906091745_custom_44-accounting-expenses-permissions` and
  `20260906091746_custom_45-expenses-table`); sidecar updated with **only** these two manifest
  entries — the other agent's `43-whatsapp-webhook-event-processing.sql` entry was left as-is
  (see Cross-plan note below).
- Applied on **both** DBs: `bun run db migrate` (dev `siraj`) + `bun run db migrate --env-file
  .env.test` (`siraj_test`).

## Carry-forward knowledge

- **DB pair discipline** (confirmed again): `bun run db migrate` covers `.env` (siraj) only;
  tests read `.env.test` (`siraj_test`) — always migrate both.
- **Cross-plan note (whatsapp2 owner)**: `db migrate` auto-bundles every unbundled custom SQL
  file; the run that applied 44/45 also bundled the in-flight
  `43-whatsapp-webhook-event-processing.sql` into
  `backend/drizzle/20260906091949_custom_43-whatsapp-webhook-event-processing/` (content = the
  file verbatim, idempotent `ALTER TYPE ... ADD VALUE IF NOT EXISTS`, now applied to both DBs).
  Do not re-bundle it; the sidecar already records it.
- **Snapshot drift**: drizzle snapshots do NOT contain the `expenses` table or `expense_type`
  enum (no `generate` was run, by design). The next snapshot-diffing `generate` (by anyone)
  will re-emit `CREATE TABLE expenses` etc.; `ensureIdempotentMigrations` (runs inside
  `db migrate`) rewrites those to idempotent forms, so application stays a no-op.
- `createdByUserId` is `NOT NULL` with `ON DELETE SET NULL` — parity with
  `carryover_balances.created_by_user_id`; deleting a referenced user would raise an FK
  error at the DB level. Existing convention, not new.
- Money columns are `text` (exact decimals), matching the carryover tables; `numericColumn`
  exists in the dialect builder but the schema decision (implementation §2.3) is `textColumn`.
