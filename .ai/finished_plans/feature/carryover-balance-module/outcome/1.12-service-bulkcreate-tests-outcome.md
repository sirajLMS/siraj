### Tier coverage vs. the task list

- **Happy path** — 3 teachers, 5 mixed sessions (2/1/2 split; CALCULATED /
  PARTIALLY / REFUND statuses): 3 carryover inserts (studentsText, from/to
  dates, disabled-teacher snapshot for the third group, `paid "0"` /
  `isPaid false`), 3 item batches with original-amount snapshots, 3 link
  calls, 5 session patches to `WAITING_PAID`, 5 `PAYROLL_STATUS_TRANSITION`
  events, 3 replay-keyed `CARRYOVER_CREATE` audit rows, advisory-lock key
  `carryover-bulk-create:<hash>`, permission gate on
  `ACCOUNTING_CARRYOVER_MANAGE`, structured "Carryover balances created" log.
- **All-not-audited rejection** — `CARRYOVER_SESSION_NOT_AUDITED`, zero writes.
- **Already-linked rejection** — `CARRYOVER_SESSION_ALREADY_LINKED`, zero writes.
- **Unknown instance id** (tampered payload) — `NotFoundError` with
  `CLASS_INSTANCE_NOT_FOUND`, lock read ran once, zero writes.
- **Cross-currency FX conversion** — SAR + USD sessions under one teacher
  (1-1 tie resolves to the teacher's `rateCurrency` fallback, SAR); USD item
  converts at 2dp half-up (`40.00 × 3.75 = 150.00`), `originalAmount "40.00"`
  / `originalCurrency USD` preserved, group `payable "250.00"`; FX repo called
  exactly once inside the sentinel tx.
- **FX rate missing rejection** — parametrized over both failure shapes
  (`rate: null` and `stale: true`) → `CARRYOVER_FX_RATE_MISSING`, zero writes
  (conversion runs before the carryover insert).
- **Idempotent re-submit** — identical re-submit inside the 60s window (fresh
  `clientRequestId`, changed note) replays the first result equality-deep;
  exactly one write round; lock re-acquired, audit re-queried.
- **Concurrent replay burst (Tier 4)** — two parallel submissions settle on
  one write round. Mock serializes transactions via a chained promise —
  mirroring the real advisory lock (`payroll-calculation.service.test.ts`
  precedent).
- **Tampered re-submit (Tier 4)** — same `clientRequestId` but an expanded
  instance list is NOT a replay (input ids are hashed, `clientRequestId` is
  not); the previously linked session trips `CARRYOVER_SESSION_ALREADY_LINKED`.
- **studentsText truncation** — 40 students join to >500 chars; persisted
  text is 497 chars + single `…` (length 498, within the 500-column limit),
  `studentsCount` stays 40, `logger.warn("Carryover students text truncated")`.
- **Permission denied** — `ForbiddenError` (`FORBIDDEN`, "Insufficient
  permissions") propagates; no transaction opened, no lock, zero writes.
- **Empty instanceIds** — `ValidationError` (`VALIDATION`) before any
  transaction work.

### Mock wiring details worth knowing

- `SchedulingRepository.getByIdsForUpdate` mock returns rows **in input
  order** (real repo is unordered, but `groupInstancesByTeacher` produces
  first-appearance grouping either way — assertions pin input order as a
  readable fixture choice, not a service contract).
- `linkToCarryover` mock mutates the fixture rows' `carryoverBalanceId` so
  the tampered-re-submit test exercises the real already-linked guard path.
- `AuditRepository.queryAuditLogs` mock filters the captured audit store by
  actor + action and returns newest-first (`toReversed()`), matching the real
  repo's `desc(createdAt)`; the service's replay reconstruction reverses back
  to creation order.
- The students-name lookup (`tx.select().from(students).where(...)`) is served
  by a select-chain on the sentinel executor, not a repo mock.
- Audit metadata assertions go through an `isMetadataRecord` type guard (the
  jsonb column types metadata as unknown-ish; no assertions used).
