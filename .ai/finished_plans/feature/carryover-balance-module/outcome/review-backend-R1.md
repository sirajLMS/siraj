# Backend Review R1 — Carryover Balance Module

Read-only review. Scope: carryover-owned backend files only (schema, relations, repos, services, types, GraphQL, CSV route, migrations, migration/repo tests). Findings verified against the actual code; line numbers refer to the files as of this review.

## Findings

### HIGH

1. **Replay lookup silently truncates large batches** — `backend/services/teachers/carryover-balance.service.ts:216-228` (`findReplayAuditLogs`, `REPLAY_LOOKUP_LIMIT = 100`). `AuditRepository.queryAuditLogs` applies `limit: 100` (`backend/db/repo/audit/audit.repository.ts:280-289`, ordered `desc(createdAt)` with no tiebreaker) **before** the metadata `idempotencyKey` filter runs in JS. Both bulk inputs allow up to 500 items (`carryover.pothos.ts:218`, `:229`), so one bulk create can emit up to 500 `CARRYOVER_CREATE` audit rows (one per teacher group) and one bulk-to-expense up to 500 `CARRYOVER_TO_EXPENSE` rows. Replaying such a submission inside the 60 s window fetches only the newest ~100 matching rows and `reconstructBulkCreate` / `reconstructToExpense` happily return that partial set as the full result — the client gets a wrong (incomplete) result presented as a successful replay. Fix: page through the window until no more rows for the key (or filter by key server-side), raise the cap above the max batch, and add a secondary sort key (`desc(id)`) for deterministic ordering.

2. **Soft-deleted class instances can be aggregated and paid out** — `backend/db/repo/scheduling/class-instances.ts:556-566` (`getByIdsForUpdate`) has no `isNull(classInstances.deletedAt)` filter, unlike every other read path in the same repo (e.g. lines 289, 319, 338, 436, 635). `softDeleteClassInstance` (`class-instances.ts:239-260`, called from `class-session.service.ts:662` with no calculation-status guard) only sets `deletedAt`; a soft-deleted session keeps `CALCULATED`/`PARTIALLY` status, so `bulkCreateCarryoverBalances` (`carryover-balance.service.ts:797-799`) accepts it, snapshots its amount, links it, and settles money for a deleted session. Same gap lets a session be deleted after linking and still be paid via bulk-to-expense (`findLinkedSessions`, `carryover-balance.repository.ts:174-186`, also missing the filter). Fix: add `isNull(deletedAt)` to `getByIdsForUpdate` (missing rows then surface via the existing not-found count check) and decide/handle deleted-linked sessions in the settlement paths.

3. **`updateCarryoverBalance` mutates paid rows, breaking the money invariant** — `backend/services/teachers/carryover-balance.service.ts:1232-1303`. The schema contract (`carryover-balances.ts:40`: "paid … Equals `payable` once `isPaid = true`") and the linked expense amount are silently violated: the patch allows changing `payable` and `teacherCurrency` on an already-paid row, after which `paid ≠ payable`, the settlement history no longer reconciles, and the CSV/report aggregates mix inconsistent rows. Spec (specs.md AC-4.6) only blocks *delete* on paid rows, but nothing in the plan sanctions editing the settled amount. Fix: reject updates on `isPaid` rows, or at minimum forbid `payable`/`teacherCurrency` changes once paid.

### MEDIUM

4. **Deadlock risk from unordered instance row locks** — `SchedulingRepository.getByIdsForUpdate` (`class-instances.ts:556-566`) takes `FOR UPDATE` with no `ORDER BY` and ids arrive set-dedup'd but unsorted. Two concurrent bulk creates with overlapping but non-identical id sets yield different advisory-lock keys (`carryover-bulk-create:<content-hash>`), so both proceed and can acquire row locks in scan-order-dependent sequences → deadlock. (The carryover repo's own `getByIdsForUpdate` orders by id — `carryover-balance.repository.ts:145-151` — though comment-level, note `ORDER BY` in the same statement does not strictly guarantee lock acquisition order; a sorted subquery or sorted per-id advisory locking is the robust fix.)

5. **Session transitions in settle/unpay/delete run without live-state guards or locks** — `transitionSessions` (`carryover-balance.service.ts:409-424`) writes whatever target the flow derived; `updatePayrollCalculation` supports an `expectedStatus` optimistic guard (`class-instances.ts:529-531`) but the carryover flows never pass it, and in delete/unpay the session rows are read unlocked (`findLinkedSessions` inside `revertAndUnlinkCarryoverSessions`, line 1318, and `markCarryoverPaidAndSettleSessions`, line 928). A concurrent payroll recalculation between read and write is silently clobbered (status and amount). Practical exposure is small (linked sessions sit in WAITING_PAID/PAID, which recalculation normally skips), but the unguarded write contradicts the module's own lock-then-write design. Fix: lock linked sessions `FOR UPDATE` (or pass `expectedStatus`) in the revert/settle paths.

6. **Unvalidated free-form `teacherId` filter reaches a uuid column** — `carryover.query.ts:61` (`teacherId: filter?.teacherId ?? null`) and `app/api/carryover/export/route.ts:120` pass the string straight to `eq(carryoverBalances.teacherId, …)` in `buildConditions` (`carryover-balance.repository.ts:45-47`). A malformed (non-uuid) value escapes PostgreSQL as a `22P02` syntax error → 500, inconsistent with the module's otherwise careful `assertUuidId` treatment. Fix: validate shape at the query/route boundary (reject with `tErrors.invalidInput`).

### LOW

7. **Dead production surface kept for tests only** — `CarryoverBalanceRepository.bulkDelete` (`carryover-balance.repository.ts:292-299`), `CarryoverBalanceRepository.findByTeacherId` (`:160-167`) and `SchedulingRepository.findByCarryoverId` (`class-instances.ts:573-579`) have no production callers (only the repo test files). Likewise the input types `UnpayCarryoverInput`, `DeleteCarryoverInput`, `BulkDeleteCarryoverInput` (`carryover-balance.types.ts:101-124`) are unused — the service inlines the shapes. Fix: delete or wire them.

8. **Inconsistent `clientRequestId` handling** — accepted on both bulk inputs (`carryover.pothos.ts:220,233`; types 28, 60) but ignored by `deriveBulkCreateIdempotencyKey` / `deriveBulkToExpenseIdempotencyKey` (`carryover-idempotency.ts:27-47`), while `deriveCrudIdempotencyKey` does honor it. Fix: include it in the bulk keys (as an entropy segment) or drop the field from the bulk inputs.

9. **Redundant index** — `carryover_balances_expense_id_idx` (`carryover-balances.ts:67`) duplicates the unique index `carryover_balances_expense_id_unique_idx` (`:72`). Drop the plain one.

10. **Replay window staleness (documented trade-off)** — bulk-create replay returns reconstructed group results without verifying the rows still exist (`carryover-balance.service.ts:793-795`); a delete inside the 60 s window yields replayed ids that 404. Single-create handles this correctly (`:1212-1215` falls through to a fresh create). Acceptable at this window size; worth a code comment.

11. **Hardcoded English session-event descriptions** — `"Linked to carryover …"`, `"Settled via expense …"`, `"Carryover … unpaid/deleted"` (`carryover-balance.service.ts:693,938,1091,1337`) land in `class_status_events.description`. Consistent with existing precedent (`credit.service.ts:323`), but `softDeleteClassInstance` localizes its description (`class-instances.ts:245` via `tFuncSession`); if these descriptions surface in the session event timeline UI, they should come from translations.

## Verified clean (no finding)

- **Authorization**: every GraphQL query/mutation carries `authScopes` + `requireAuth`, and every service entry point re-checks `requirePermission(...CARRYOVER_VIEW/MANAGE)` before any data access. `countLinkedSessionsByCarryoverIds` is ungated by design (documented; reachable only through the gated parent object). CSV route checks session + permission before reading.
- **Idempotency ordering**: all three write flows take the advisory lock before the replay lookup and before any write (lock-then-replay, single transaction). Key derivation is deterministic (sorted ids, null/undefined normalized); replay fixtures confirmed by `carryover-balance.service.test.ts` coverage.
- **Money handling**: decimal strings end-to-end; integer minor-unit `bigint` arithmetic (`toAmountMinorUnits`/`formatAmountMinorUnits`); FX conversion rounds half-up on a fixed 1e6 scale; negative payables rejected (`normalizePayableAmount`, :1121-1127).
- **Migrations**: `40-accounting-carryover-permissions.sql` and `42-…partial-percentage.sql` are additive and idempotent (`IF NOT EXISTS`, `ON CONFLICT`, guarded trigger toggling); the migration test asserts additivity (no DROP/DELETE/TRUNCATE/SET NOT NULL) and re-run safety.
- **i18n of errors**: all user-facing failures go through `tErrors.*` (resolver, service, route); locale keys exist under `shared/locale/{ar,en}/errors` and `dashboard/accounting/carryover`.
- **Cross-layer imports / logging**: no shared→backend violations; pothos/query/mutation layers import types from `@/backend/types`; all logging via `@/backend/lib` logger (no `console.*`).
- **CSV export**: RFC 4180 quoting + formula-prefix neutralization (`= + - @ \t \r`), 10 000-row cap with `X-Export-Truncated`, input params validated with localized 400s.
- **Tests reviewed** (structure only): `carryover.repository.test.ts`, `class-instances-carryover.repository.test.ts`, `carryover-tables.test.ts` use `runInRollback`, entity-setup helpers, and tx propagation correctly.
