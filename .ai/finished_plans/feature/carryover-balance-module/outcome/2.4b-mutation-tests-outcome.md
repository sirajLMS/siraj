### Coverage

- **Result shapes (all 7)**: `bulkCreateCarryoverBalances` (groups `id` mirrors
  `carryoverId`, `totalInstanceIds`, `auditLogIds`), `bulkCarryoverToExpense` (items `id`
  mirrors `expenseId`, `auditLogIds`), `createCarryoverBalance` / `updateCarryoverBalance` /
  `unpayCarryoverBalance` (full `CarryoverBalance` row shape via `expectCarryoverRowShape`),
  `deleteCarryoverBalance` (`{ id, deleted }`), `bulkDeleteCarryoverBalances`
  (`deletedIds`, `auditLogIds`).
- **Permission denied → GraphQL error** for every mutation, parameterized in
  `shared authorization guard`: view-only actor (`ACCOUNTING_CARRYOVER_VIEW`) and logged-out
  caller each get `FORBIDDEN` + `insufficientPermissions` and the mocked service is never
  invoked; permissioned-but-anonymous context reaches the resolver and fails `requireAuth`
  with `UNAUTHENTICATED`; super admins without the explicit permission pass.
- **Mutation-argument coverage** (`docs/testing/mutation-argument-coverage.md`): every
  input field passed with meaningful non-null values on each happy path; each optional field
  additionally tested with `null` (bulkCreate `clientRequestId`/`note`, toExpense
  `expenseDate`/`note`/`clientRequestId`, create's seven optional fields, update's full-null
  patch, unpay's `note`). The bulkCreate/toExpense/create null-optionals tests and the three
  bulk selection-limit tests are parameterized loops to avoid intra-file clones.
- **Empty-array rejection**: all three bulk mutations surface the service's
  `ValidationError` (`carryover.noInstances` / `carryover.noCarryovers`) as `VALIDATION`
  GraphQL errors (tolerance contract: resolver forwards the empty array, service rejects).
- **Oversized arrays (501 ids)**: forwarded unchanged to the service — see cross-file
  dependency below.
- **Idempotency `clientRequestId` forwarding**: dedicated tests assert the value reaches
  `bulkCreateCarryoverBalances`, `bulkCarryoverToExpense`, and `createCarryoverBalance`
  service inputs verbatim.
- **Actor injection / never-from-input**: captured service inputs equal
  `{ ...input, actorUserId: <ctx.user.id> }` via the shared `expectSingleForwardedInput`
  helper; passing `actorUserId` inside `CreateCarryoverInput` fails variable coercion
  (field does not exist in the schema).
- **Code propagation**: `DomainError("CARRYOVER_PAID_CANNOT_DELETE", …)` from the delete
  path surfaces with its `extensions.code` preserved.

## CROSS-FILE DEPENDENCY (reported, not executed)

- **No GraphQL-level cap on selection sizes.** `BulkCreateCarryoverInput.instanceIds`,
  `BulkToExpenseInput.carryoverIds` (both in the 2.1-owned
  `backend/graphql/pothos/teachers/carryover.pothos.ts`) and `bulkDeleteCarryoverBalances`'s
  `ids` arg (2.3-owned `carryover.mutation.ts`) carry no `minItems`/`maxItems` `constraint`
  directives, and the service layer does not cap them either (empty arrays are rejected,
  size is not). This diverges from the repo's security guidance (`t.arg.*List()` inputs
  should have `maxItems`, e.g. `teacher-due.mutation.ts` uses `maxItems: 500`) and from the
  "oversized array capped" testing bullet. Recommended follow-up: add
  `directives: { constraint: { minItems: 1, maxItems: 500 } }` to the three list inputs.
  The oversized-selection tests therefore assert *forwarding* (the current contract), and
  will keep passing if a constraint plugin starts rejecting above the cap — at which point
  they should be flipped to expect the cap error.

## Carry-forward notes

- Scalar-registration guard symbol is deliberately the same one the payroll pair and the
  2.4a query-test file use; any new carryover test file must reuse it (re-registering
  `DateTime`/`JSON` on the shared builder would double-register).
- The mock service mirrors the real empty-selection contract (`ValidationError` via
  `tErrors.carryover.noInstances` / `noCarryovers`); if the real messages change, only
  `tErrorsEn` lookups change — tests compare against the translation object, not literals.
- Task 2.6 (schema regen + codegen) is unaffected; this file builds its own schema
  in-process and needs no generated frontend types.
