## Summary

Extended the EXISTING shared sanitizer `backend/lib/sanitize/richTextSanitizer.ts`
with `sanitizePlainText(text, maxLength = 2000)` — the XSS-hardening control for
free-form plain-text columns that are rendered as text and must never be interpreted
as markup (the payroll note on `class_instances`, edge cases E15/E16). The addition
is **purely additive**: the sibling credit-adjustment feature's `sanitizeRichText`
and all of its machinery are byte-identical to before (verified: lines 1–166 of the
file diff-identical to the pre-edit snapshot; `git diff` = +62/−0).

Behavior contract:

- **Strips ALL HTML tags — no allowlist** (the core difference from
  `sanitizeRichText`): dangerous container elements (`script`, `style`, `iframe`,
  `object`, `embed`, `svg`, `math`) are removed together with their contents by
  reusing the file's existing linear `stripContainerBlocks` scans (payload text
  never survives), and every remaining tag is removed with all of its attributes —
  so no element, event handler, or URL can survive.
- **Escapes stray `<`** to `&lt;` (reusing the sibling's concatenation-vector
  defense: markup appended after the stored value cannot complete an unterminated
  tag).
- **Entities pass through as inert text** (`&lt;`, `&#x61;`, …): entity references
  never re-tokenize as markup at render time — same policy as the rich-text
  sanitizer's "already-escaped entities are left as inert text".
- **Truncates to `maxLength` UTF-16 units with a trailing `…` (ellipsis included in
  the budget)** — the output is at most `maxLength` characters so it always fits the
  `varchar(2000)` `payroll_note` column; the cut never splits a surrogate pair, so
  the stored value stays valid UTF-16 (an unpaired surrogate would be rejected or
  mangled by PG/Node string encoding).
- Pure, synchronous, never throws, idempotent
  (`sanitizePlainText(sanitizePlainText(x)) === sanitizePlainText(x)`).

**Spec adaptation (documented):** implementation.md §3.4 shows the caller doing
`sanitizePlainText(input.note).slice(0, 2000)` — the `.slice` is redundant with the
sanitizer's built-in default (maxLength 2000, ellipsis included). Task 1.7 should
call `sanitizePlainText(input.note)` and rely on the default; the redundant slice is
harmless if kept.

## Security Audit

This task IS a security control. Contract summary:

- **All tags removed** (allowlist-free) — element construction, event handlers, and
  URL attributes are dropped by construction; nothing survives to be rendered as
  markup.
- **Dangerous containers removed WITH contents** — script/style/iframe/object/embed/
  svg/math payload text never leaks into the stored value (reuses the sibling's
  linear, non-backtracking scans that are safe on adversarial nesting).
- **Stray-`<` escaping** closes the unterminated-tag completion vector when the
  stored value is concatenated into markup elsewhere.
- **Entities are inert by design** — they pass through as text; HTML entity decoding
  happens in the renderer's text nodes and never re-tokenizes as markup, so encoded
  payloads cannot smuggle tags past the stripper.
- **Length bound is part of the security posture** — the ellipsis-inclusive
  `maxLength` cap keeps the value inside its `varchar(2000)` column (no DB
  truncation-error DoS on the override path) and the surrogate-safe cut keeps the
  string valid UTF-16 for PG persistence.
- No secrets, no network, no filesystem, no dynamic code; function never throws.

   grapheme-perfect cuts are ever needed, that is a separate
   `Intl.Segmenter`-based enhancement, not a defect.
