## Summary

Delivered `resolveGraceSettings()` in `backend/services/teacher/payroll-grace-settings.ts`
— the runtime resolver that reads the three payroll grace-period thresholds from
`system_settings` on every invocation (no caching) and applies the default/fallback
contract: absent rows fall back silently to 3/6/30; any present-but-invalid row
(non-integer value, negative short/long grace, threshold below one minute) logs a
structured `logger.warn` and returns ALL defaults (a partially trusted grace
configuration is never partially trusted — wholesale fallback prevents silent
mispricing). Optional `tx?: DBTransaction` forwards the caller's executor to the
repository reads so task 1.6 can keep them inside the calculation transaction.

**Path adaptation (documented per task instruction):** the plan writes
`backend/services/teachers/` (plural) but the existing domain directory is
`backend/services/teacher/` (SINGULAR) — sibling teacher services and the task-1.3
agent's `payroll-override.idempotency.ts` both live in the singular dir. The file was
created at `backend/services/teacher/payroll-grace-settings.ts` (singular).

**Spec adaptation (mechanical, semantics preserved):** implementation.md §3.2's snippet
calls a `SystemSettingsRepository.getMany([...])` method that does not exist. The real
repository exposes `getByKey` (and `getIntValue`). The resolver reads the three rows via
three concurrent `getByKey` calls (`Promise.all` — `no-await-in-loop` gate) and parses
them locally, which additionally allows distinguishing absent rows (silent default) from
present-but-unparseable rows (warning) — covering AC-8.2's unparseable case that
`getIntValue`'s fallback semantics cannot express.

**Fallback semantics reconciliation (AC-3.1/AC-8.2 vs implementation.md §3.2):** the
specs disagree on whether MISSING rows should warn (AC-8.2 says yes, AC-3.1 and the
§3.2 snippet say silent default). The task's test list ("missing settings → defaults;
negative setting → defaults + warning; threshold < 1 → defaults + warning") and the
implementation spec both treat absence as silent, so absence = silent default;
present-but-invalid = warning + wholesale defaults. The resolver-level warning is the
runtime safety net for negative values because the AC-8.4 settings-layer CHECK was
never implemented (new deferred item D8).

## Security Audit

- Read-only: the resolver performs three `getByKey` SELECTs per invocation — no
  writes, no DDL, no privilege surface.
- No secrets, tokens, or credentials handled; no network; no filesystem access.
- Fail-safe on bad config: misconfigured thresholds can never produce negative or
  zero-threshold grace windows at calculation time (wholesale default fallback +
  structured warning), which is the money-safety property the risk table requires.
- No injection surface: the setting keys are compile-time constants; the parsed
  values are used only as numbers.
