## Deliberate deviations from implementation.md §5.1 (documented for reviewers)

1. **File placement `teachers/` instead of `billing/`** — the §5.1 snippet wrote
   `sharedDocuments/billing/payroll.documents.ts`, but the authoritative
   trackable-tasks.md 4.1 entry specifies `sharedDocuments/teachers/payroll.documents.ts`,
   matching the backend placement (`pothos/teachers/`, `query/teachers/`,
   `mutation/teachers/`) landed in 2.1–2.4. Same supersession the 2.3–2.4 outcome
   recorded for the backend files.
2. **Nested `aggregates { … }` instead of the snippet's flattened
   `totalPaidAmount`/`totalPaidCurrency`/`rowCountByStatus` on the page** — the flattened
   fields do not exist on `PayrollReportPage` in the actual schema (2.1 implemented the
   nested `PayrollReportAggregates` object per the `PayrollReportPage` contract). The
   document matches the real SDL 1:1 (codegen would fail otherwise under
   `noSilentErrors: true`).
3. **`id` selected on Page / Row / Aggregates / OverrideResult** — the §5.1 snippet
   omitted `id` everywhere; the AGENTS.md `id`-on-every-object-type mandate + the task
   text's explicit id-equivalent requirement outrank the snippet (same precedent the
   2.1–2.2 outcome set for the Pothos objects).
4. **No default values in the variable definitions** (`$limit: Int`, `$offset: Int`, not
   `= 50` / `= 0`) — repo precedent (`users`, `staffDirectory`, `parentsDirectory`
   documents all declare plain nullable variables even where the schema declares
   server-side defaults) and the §5.1 snippet itself agree; omitting the variables lets
   the server-side defaults (limit 50 / offset 0) apply exactly as the 2.3–2.4 resolver
   contract defines (`args.limit ?? 50`). The generated `Variables` type is
   `limit?: number | null | undefined` either way. (The 2.3–2.4 outcome's carry-forward
   had suggested `= 50`/`= 0` defaults; repo convention + plan snippet win.)
5. **Flat generated type names, not `Operations.X`/`Types.Y`** — the dispatch/task text
   used the `TypedDocumentNode<Operations.X, Types.Y>` shape, but this repo's codegen
   emits flat types from the single `graphql.ts` (the old `graphql-types.ts` +
   `operations.ts` files no longer exist — `sharedDocuments/AGENTS.md` explicitly bans
   them). The actual convention (`TypedDocumentNode<XQuery, XQueryVariables>`) is what
   was implemented; the "Types.Args" verification maps to the generated
   `…QueryVariables`/`…MutationVariables` types.
6. **No co-located test file** — the only co-located test in sharedDocuments is the
   top-level `profile.documents.test.ts` exception; no sibling documents file carries
   tests and task 4.1 does not mandate one. The documents are exercised end-to-end by
   the 2.5 backend suites (real schema) and will be by 4.8/5.3 UI tests.

### Nullability contract for Phase-4 consumers

- Repo-wide convention holds: **every output field is `T | null`** (`instanceId: string |
  null`, `calculationStatus: CalculationStatus | null`, `teacherPaidAmount: string | null`,
  …); `rows` itself is `Array<PayrollReportQuery_payrollReport_rows> | null` (list items
  non-null); `aggregates` is `… | null`; the page and the mutation result are nullable
  root fields. View models must treat all of these as nullable — identical to every
  existing page's generated types.
- `rowCountByStatus` is the `JSON` scalar → generated as `unknown` (cast/guard at the
  edge; the service guarantees a zero-filled `Record<CalculationStatus, number>`).
- Apollo cache ids: `PayrollReportRow.id` / `PayrollOverrideResult.id` resolve to the
  instanceId (natural key); `PayrollReportPage`/`PayrollReportAggregates` ids are
  synthetic. The override result's `__typename` differs from the row's, so a mutation
  write-back will NOT auto-patch an existing row object — task 5.2's cache evict/refetch
  remains the planned refresh strategy (per plan); `auditEventId` is the US-9.2
  audit-drawer link.
