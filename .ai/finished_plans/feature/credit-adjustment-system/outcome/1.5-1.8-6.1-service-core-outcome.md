### Why the shared transaction skeleton

The three flows were first written per the plan sketches as three full functions.
Per-file jscpd flagged the `subtractCredit`/`subtractWithCarryover` transaction
bodies as an intra-file clone (11 lines / 79 tokens). They were refactored into
`executeAdjustmentTransaction` (single atomic body parametrized by
`AdjustmentTxParams`: `signedHours`, `reason`, optional `carryover`,
`idempotencyKey`) + `runAdjustment` (try/unique-violation recovery + success
logging) with `addCredit` / `subtractCredit` / `subtractWithCarryover` as thin
wrappers. Behavior is identical to the plan sketches; `signedHours < 0` selects
the `INSUFFICIENT_CLASSES` guard + `StudentRepository.deductClasses`, otherwise
`StudentRepository.addClasses`; `carryover` presence selects `assertTeacherExists`
+ `maybeInsertCarryoverBalanceEntry`.

## Dispatcher & validation (`recordAdjustment`)

1. `await requirePermission(actorUserId, AppPermission.ACCOUNTING_CREDITS_MANAGE, tErrors)` — **first**, throws `ForbiddenError`.
2. `validateAdjustmentInput(input, tErrors)`:
   - `studentId` blank or `hours` not finite / `< 1` → `ValidationError(tErrors.credit.invalidInput)`.
   - Carryover block (teacher + all three dates) required **iff**
     `SUBTRACT_WITH_CARRYOVER` — via `requireCarryoverBlock` (also re-invoked inside
     `subtractWithCarryover` to narrow the optional fields without non-null assertions).
   - `fromDate > toDate` → `ValidationError`.
   - `paymentDate > now + 1 day` (`maxPaymentDate = new Date(); setDate(getDate() + 1)`; dates compared as parsed) → `ValidationError`.
3. Switch on `input.adjustmentType`: `ADD → addCredit`, `SUBTRACT → subtractCredit`,
   `SUBTRACT_WITH_CARRYOVER → subtractWithCarryover`, `default → throw new ValidationError(tErrors.credit.invalidInput)`
   (the default satisfies oxlint `consistent-return`; the enum covers every real path).

## Atomicity & idempotency (inside `db.transaction`, in order)

1. **Advisory lock**: `await acquireAdvisoryLock(tx, \`student_${input.studentId}\`)` —
   `pg_advisory_xact_lock(hashtext('student_<id>'))` via the shared helper
   (`@/backend/db/repo/shared`); no-ops on SQLite. Acquired FIRST, before any read.
2. `assertStudentExists`.
3. Carryover only: `assertTeacherExists` (in-tx read).
4. Subtract variants only: `assertSufficientClasses` — balance read and check
   happen AFTER the lock, so no unlocked read-modify-write.
5. Idempotency pre-check: `CreditRepository.findByIdempotencyKeys([key], tx)`;
   existing row → `mapToAdjustmentReturnType(existingRow)` returned (double-submit collapses).
6. `CreditRepository.createAdjustment(tx, { ... })` with `notes: sanitizeAdjustmentNotes(input.notes)`
   (sanitized via `sanitizeRichText`; blank/fully-stripped reasons persist as `null`).
7. Balance write (`addClasses`/`deductClasses`) + `QuotaService.refreshStudentOndemandInstances`.
8. Carryover only: `maybeInsertCarryoverBalanceEntry` — inside the same tx.

Outside the tx: on a Postgres unique violation (SQLSTATE 23505), `resolveDuplicateAdjustment`
re-reads by key and returns the winning row; the error is rethrown otherwise.
`runAdjustment` logs `Credit adjustment Add | Subtract | Subtract-With-Carryover recorded`.

## 6.1 Carryover stub (`carryover-handoff.ts`)

```ts
export interface CarryoverHandoffPayload {
  creditTransactionId: string;
  teacherId: string;
  studentId: string;
  fromDate: string;     // ISO YYYY-MM-DD
  toDate: string;
  paymentDate: string;
  hours: number;
  approvedByUserId: string;
}
export async function maybeInsertCarryoverBalanceEntry(tx: DBTransaction, payload: CarryoverHandoffPayload): Promise<void>
```

Behavior: no-op when `isSqlite()` or the tx cannot execute raw SQL; otherwise probes
`SELECT to_regclass('teacher_carryover_balances')` (result normalized across
`{ rows }` drivers and plain-array Neon HTTP results via `extractRows`). When the
table exists, inserts the row with the §2.5-documented column set
(`credit_transaction_id, teacher_id, student_id, from_date, to_date, payment_date, hours, status='PENDING', created_at=now()`)
using a parameterized `sql` template (table name via `sql.identifier`), then
`logger.debug`. **Deviation note:** `approvedByUserId` is carried in the payload
(per the §3.7 call contract) but is not inserted — §2.5 defines no audit column;
Plan 5 owns the table and can add one.
