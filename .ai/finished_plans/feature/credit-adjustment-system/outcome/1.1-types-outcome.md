## Exact type definitions added

```ts
/** Operator-facing input for a manual credit adjustment (add / subtract / subtract-with-carryover). */
export interface CreditAdjustmentInput {
  studentId: string;
  adjustmentType: CreditAdjustmentType;
  /** Positive class-credit amount; the sign is derived from adjustmentType. */
  hours: number;
  /** Sanitized rich-text reason for the adjustment. */
  notes?: string | null;
  /** Carryover metadata — required when adjustmentType is SUBTRACT_WITH_CARRYOVER. */
  carryoverTeacherId?: string | null;
  /** ISO date strings (YYYY-MM-DD) — carryover columns are TEXT in the schema. */
  carryoverFromDate?: string | null;
  carryoverToDate?: string | null;
  carryoverPaymentDate?: string | null;
}

/** Adjustment ledger row returned to callers, carrying the carryover metadata columns. */
export interface CreditAdjustmentReturnType extends CreditTransactionReturnType {
  adjustmentType: CreditAdjustmentType;
  carryoverTeacherId: string | null;
  carryoverFromDate: string | null;
  carryoverToDate: string | null;
  carryoverPaymentDate: string | null;
}

/** Repository insert payload for a single adjustment ledger row. */
export interface CreditAdjustmentInsertInput {
  studentId: string;
  /** Signed class-credit delta (positive for ADD, negative for subtract variants). */
  changeAmount: number;
  reason: CreditReason;
  adjustmentType: CreditAdjustmentType;
  /** Sanitized rich-text reason for the adjustment. */
  notes?: string | null;
  creditedByUserId: string;
  carryoverTeacherId?: string | null;
  carryoverFromDate?: string | null;
  carryoverToDate?: string | null;
  carryoverPaymentDate?: string | null;
  idempotencyKey: string;
}
```

## Derivation notes (for later tasks)

- `CreditAdjustmentInput` / `CreditAdjustmentReturnType` are verbatim from
  `implementation.md` §3.1 (comments reworded to clean, plan-tag-free wording per
  the clean-comments rule).
- `CreditAdjustmentInsertInput` has no explicit sketch in `implementation.md`; its
  shape is derived exactly from the `CreditRepository.createAdjustment(tx, {...})`
  call sites in §3.5–3.7 and the column mapping in §3.8 (`changeAmount`,
  `reason`, `adjustmentType`, `notes?`, `creditedByUserId`, four optional
  carryover fields defaulted `?? null` by the repo, `idempotencyKey`).
- `CreditAdjustmentReturnType` restates `adjustmentType` and the four carryover
  fields even though `CreditTransactionSelectType` (post-0.4) already infers them
  — this matches the design and pins the enum type contract
  (`.$type<CreditAdjustmentType>()` on the column makes the extension compatible).
- Schema column types the types must satisfy (from 0.4): `adjustmentType:
  CreditAdjustmentType` (NOT NULL), `carryoverTeacherId: string | null`,
  `carryover*Date: string | null` (TEXT, ISO YYYY-MM-DD).
