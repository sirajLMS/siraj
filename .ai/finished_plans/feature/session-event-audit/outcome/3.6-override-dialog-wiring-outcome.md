## Why the dialog-only render was rejected

`ClassAuditContainer` (Wave F) already sets `useClassDetailsStore.overrideDialogOpen = true`
on `?openOverride=1`. Rendering Plan 3's `OverrideDialog`
(`frontend/common/views/dashboard/accounting/payroll/OverrideDialog.tsx`) bound to that flag
is technically possible today, but with no payroll data source on the audit page the only
option is `row: null`, which yields a **non-functional dialog**: `canSubmit` is
`row?.instanceId != null` (useOverrideDialogViewModel.ts:354), so the primary action is
disabled and every summary value renders "—". That is a broken end state for the deep link
and would fail the task's end-to-end intent (specs AC-9.2: the dialog opens so the operator
can apply the override). Fabricating a `PayrollReportRow` from `audit` data is not viable
either: `groupClassAudit.id` is the *group* id (not the instance id), the type requires 19
fields, and fabricated values violate the no-placeholder/NO-MAPPING rules.

## Facts established during investigation

- `classAuditViewGridShared.tsx:57` renders `ClassAuditDetailsCard` with no `payroll` /
  `statusEvents` / `onOverride` — the payroll card (`ClassAuditDetailsCard.tsx:244`,
  `ClassAuditPayrollCard`) never mounts in the tier views.
- `groupClassAudit` (`backend/services/group-class/group-class.service.ts:96`) returns
  `GroupClassAuditReturnType` with no payroll fields; the resolver gate is
  `authScopes: { permission: AppPermission.SESSION_VIEW_DETAILS }` (widened from
  `superAdmin: true` in the post-implementation review fix wave — super admins
  still pass via the `permission` scope's `isSuperAdmin` short-circuit) and the
  service asserts `SESSION_VIEW_DETAILS`.
- No existing query returns payroll data by instance id: `payrollReport` /
  `sessionAuditReport` filters have teacher/student/date/search but no `instanceId`;
  `groupClassAudit` has no payroll selection; `classInstanceQueryDocument` does not select
  the payroll fields even though `ClassInstanceDetail` exposes them
  (`generated/schema.graphql`, type `ClassInstanceDetail`: `calculationStatus`,
  `calculatedDuration`, `teacherPaidAmount`, `teacherPaidCurrency`, `isPartialPercentage`,
  `payrollNote`, `payrollCalculatedAt`).
- Status events for the override-history section are already available via the existing
  `classStatusEventsQueryDocument` (`sharedDocuments/scheduling/class-session.documents.ts:94`)
  — no codegen needed for that half.
- `frontend/common/graphql/generated/gql/graphql.ts` shows `M` in `git status` (in-flight
  from another wave); running `bun codegen` here would rewrite a file owned by concurrent
  work.

## Store-flag leak to resolve in the follow-up wave

`useClassDetailsStore.overrideDialogOpen` is also consumed by the class **details** page's
rate-override dialog (`useClassDetailsContainerState.tsx:8` →
`buildOverrideRateDialog(... open: store.open ...)`), which is a *different* dialog
(`OverrideRateDialog`, hourly-rate override — not Plan 3's payroll `OverrideDialog`). Because
Zustand state survives in-session navigation, leaving the flag set on the audit page would
auto-open the rate dialog if the user later opens `/classes/[id]` in the same session. The
follow-up wave should either reset the flag when the audit page unmounts / the dialog closes
(prefer a dedicated flag, e.g. on `classAuditStore`, with the container kept as the only
writer), or accept and document the shared-flag semantics.

## Recommended wiring recipe (for the follow-up wave, no re-architecture)

1. Backend: extend `GroupClassAuditReturnType` + `GroupClassAuditRef` pothos type +
   `getGroupClassAudit` with the payroll snapshot fields (the service already fetches
   `classInstance`, which carries all payroll columns), respecting the accounting-permission
   story (decide whether payroll fields are permission-gated or simply null for
   non-authorized viewers).
2. Documents: select the new fields in `groupClassAuditQueryDocument`
   (`sharedDocuments/classes/group-class.documents.ts`); run `bun codegen` **after** the
   in-flight `graphql.ts` modification lands.
3. Narrow `OverrideDialog`'s `row` prop type as described in blocker (b); also give
   `useOverrideDialogViewModel` a success path that refreshes the audit query (today it
   evicts `payrollReport` only), e.g. via an `onApplied` callback or an additional cache
   eviction of the audit root field.
4. ViewModel/props: add `payroll`, `statusEvents`, `onOverride` (store-driven: call
   `useClassDetailsStore.openOverrideDialog` or the dedicated flag) to
   `useClassAuditViewModel` → `ClassAuditViewProps` → tier views → `classAuditViewGridShared`
   → `ClassAuditDetailsCard` (its props and `ClassAuditDetailsCard.test.tsx` harness already
   anticipate exactly this — see the `AuditCardWithOverrideDialog` case).
5. Render `<OverrideDialog open={…store flag…} row={payroll-derived row} onClose={close} />`
   in `ClassAuditView.tsx` next to `AdminNoteEditDialog`, mirroring the
   `PayrollReportsContainer.tsx` ownership pattern.
