## Siraj LMS - Permissions & Permission Groups (Part 3: 00:00 - 01:58)

### 1. Permission Groups (Roles)

The functionalities introduced in this module are assigned to the following roles, separating standard live-class execution from destructive state manipulation:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **Academy Admin** | Ultimate authority over session lifecycles, including bypassing system validation rules and reverting destructive state changes. | `session.activate_override`, `session.reset`, all `session.update_status.*` |
| **Teacher** | Standard execution rights for managing live class states (attendance, starting, cancellations) on an activated session. | `session.update_status.start`, `session.update_status.absent`, `session.update_status.leave` |

---

### 2. Granular Permissions Breakdown

#### Group 1: Advanced Session Overrides (`session.admin`)

Controls high-level actions that bypass standard business logic or destructively mutate historical session data.

* **`session.activate_override`**
* **Description:** Grants the ability to manually activate a scheduled class on behalf of a teacher, explicitly bypassing the `system.enforce_time_window` rule established in Part 2.
* **Expected Outcome:** State updates to render the live action toolbar (Start, Absent, Leave, Reset) regardless of the current server time relative to the scheduled time.


* **`session.reset`**
* **Description:** Grants the ability to destructively clear session-specific data and revert a class to its untouched state.
* **Expected Outcome:** Clears all captured timestamps, remarks, and status mutations. Resets the database record's status back to default `"Regular"`.



#### Group 2: Live Session Controls (`session.status`)

Controls the standard operational workflow for managing a live or pending class instance. These permissions require the class to first be in an "Activated" state.

* **`session.update_status.start`**
* **Description:** Allows the user to officially begin a session upon student arrival.
* **Expected Outcome:** Updates class status to "Running", captures the exact server timestamp, and commits it as the permanent Start time in the database record.


* **`session.update_status.absent`**
* **Description:** Allows the user to mark a student as a no-show after the mandated waiting period.
* **Expected Outcome:** Transitions status to "Absent", automatically injects the string `"I have been waiting for whole class time."` into the remarks/description field, and flags the record for teacher payroll credit.


* **`session.update_status.leave`**
* **Description:** Allows the user to process an excused cancellation for either party.
* **Expected Outcome:** Transitions status to "Leave" and triggers the rescheduling workflow, queuing the record to be moved to `"Re Scheduled"` status in the future.



---

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Override Architecture:** The `session.activate_override` permission specifically acts as a localized kill-switch for the `system.enforce_time_window` rule from Part 2. Without this permission, the time-window check acts as a hard blocker.
> * **Separation of Duties:** While Teachers have access to the `session.update_status.*` workflows to move a class forward through its lifecycle, the `session.reset` permission is strictly isolated to Admins. This prevents teachers from tampering with or erasing payroll-flagged data (like an "Absent" state) once it has been committed.
