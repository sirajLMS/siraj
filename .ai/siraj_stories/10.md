## Siraj LMS - Permissions & Permission Groups (Part 11: 00:00 - 01:57)

### 1. Permission Groups (Roles)

The functionalities in this module extend the administrative lifecycle controls introduced in Part 10, while introducing complex, automated system rules that directly affect teacher workflows and financial quotas:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **Academy Admin** | Authority to execute advanced enrollment state changes that trigger academy-wide consequences. | Leverages existing `student.manage_status` (specifically applying `Suspended` and `On Leave` states). |
| **Teacher** | Restricted by automated system rules; loses the ability to execute session actions on inactive students. | *None applicable* (Read-only observation of downstream system locks). |
| **System Automated** | Internal background logic that alters class interactivity and financial quotas based on student status. | `system.enforce_suspended_lock`, `system.process_student_leave` |

---

### 2. Granular Permissions Breakdown

#### Group 1: Advanced Lifecycle Management (`student` - *Extended Application*)

Controls the execution of specific, highly impactful enrollment states.

* **Application of `student.manage_status` (Suspension & Leave)**
* **Description:** Grants the Admin the authority to transition a student from `"Regular"` to either `"Suspended"` or `"On Leave"` via the profile dropdown.
* **Expected Outcome:** Updates the global database state of the student, serving as the trigger for the system's automated schedule enforcement protocols.



#### Group 2: Automated Schedule Enforcement (`system`)

Controls the cascading background rules that protect business logic, prevent unauthorized teaching, and safeguard parent financial quotas.

* **`system.enforce_suspended_lock`**
* **Description:** An automated validation rule that evaluates a student's status before rendering live-session controls on a Teacher's schedule.
* **Expected Outcome:** When a student is `"Suspended"`, the system retains the class visually on the Teacher's schedule (so the teacher is aware of the cancellation) but forces the Class Status badge to `"Suspended"`. Critically, it **revokes all UI control rendering**—hiding or disabling the `Activate`, `Start`, `Absent`, and `Leave` action buttons to physically prevent the teacher from opening the virtual room or altering the record.


* **`system.process_student_leave`**
* **Description:** An automated workflow that protects a family's paid package quota when a student is formally marked as away.
* **Expected Outcome:** When a student is `"On Leave"`, the system evaluates their upcoming scheduled classes. Instead of locking them destructively (like a suspension), it flags these future classes as formally excused absences. The system automatically queues these missed sessions to be rescheduled once the student returns to `"Regular"` status, ensuring no paid classes are lost to the absence.



---

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Suspension vs. Leave (Business Logic):** The distinct separation between `system.enforce_suspended_lock` and `system.process_student_leave` is crucial. Suspension is punitive or administrative (locking access and stopping the clock), whereas Leave is accommodating (protecting the financial investment by ensuring missed classes are owed back to the student).
> * **Teacher UI Safety:** By utilizing `system.enforce_suspended_lock` to leave the class on the calendar but strip its functionality, the LMS provides passive communication to the teacher. If the class simply disappeared, the teacher might assume there was a system bug; seeing it locked as "Suspended" clearly communicates that they should not teach that time slot.
> * **Automated Integrity:** An Admin simply changes a single text string (the status). The system permissions handle the heavy lifting of locking UI elements across different portals and recalculating owed classes, preventing human error in the rescheduling pipeline.
