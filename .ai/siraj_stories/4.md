## Siraj LMS - Permissions & Permission Groups (Part 5: 00:00 - 02:02)

### 1. Permission Groups (Roles)

The functionalities in this module introduce a new automated system constraint while extending the application of existing roles:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **Admin** | Audits future calendar states and processes reschedule requests up to the defined academy limits. | Leverages existing `session.reschedule`, `schedule.filter_advanced` |
| **Teacher** | Standard capability to view future personal schedules; leave requests are now gated by system limits. | Leverages existing `schedule.filter_advanced`, `session.request_leave` |
| **System Automated** | Internal system rules that validate operational constraints against user actions. | `system.enforce_leave_limit` |

---

### 2. Granular Permissions Breakdown

#### Group 1: Automated System Constraints (`system`)

Controls background logic that prevents policy violations regarding teacher attendance.

* **`system.enforce_leave_limit`**
* **Description:** A system-level validation gate that cross-references any `session.request_leave` action against the teacher's historical data for the designated period.
* **Expected Outcome:** Implements a hard cap (maximum of 2 leave/reschedule requests). If a Teacher attempts to trigger a leave request after exhausting their quota, the system revokes the action, blocks the status mutation, and enforces the attendance policy.



#### Group 2: Schedule Verification & Auditing (`schedule` - *Extended Application*)

Utilizes previously established view permissions to audit visual state changes on future dates.

* **Application of `schedule.filter_advanced` (Future Verification)**
* **Description:** Allows authorized users (Teachers for their own schedule, Admins globally) to navigate to future dates to verify calendar integrity.
* **Expected Outcome:** When filtering by a future date string (e.g., "10/31/2024"), the UI renders the newly moved class, explicitly applying a red `"Re Scheduled"` badge to visually differentiate it from default `"Regular"` classes.



#### Group 3: Quota-Aware Schedule Modification (`session.modification` - *Extended Application*)

Utilizes previously established administrative permissions to process subsequent leaves while respecting the quota tracking system.

* **Application of `session.reschedule` (Subsequent Processing)**
* **Description:** Allows the Admin to process subsequent leave requests, serving as the formal execution of the teacher's remaining quota.
* **Expected Outcome:** When an Admin submits the Reschedule form for a second leave request, the system successfully alters the date/time, logs the changes in the Remarks, updates the state to `"Re Scheduled"`, and internally logs the completion of the teacher's final allowed reschedule for that period.



---

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Hard vs. Soft Limits:** The `system.enforce_leave_limit` permission acts as a hard limit for the Teacher's self-service `session.request_leave` capability. The UI and backend will block the teacher from initiating a third request.
> * **Administrative Authority:** Because Admins use `session.reschedule` rather than `session.request_leave`, the system relies on the Admin to enforce academy policy during the formal rescheduling process. The tracking of the limit (1st vs 2nd reschedule) ensures the administration is aware when a teacher has exhausted their allowance.
> * **Visual Confirmation:** The "Re Scheduled" badge serves as a passive audit tool, allowing both Teachers and Admins to instantly verify that the complex workflow of leaving, overriding, and assigning new temporal data executed successfully.
