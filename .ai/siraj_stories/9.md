## Siraj LMS - Permissions & Permission Groups (Part 10: 00:00 - 02:01)

### 1. Permission Groups (Roles)

The functionalities in this module encompass ad-hoc financial generation, payment ledger manipulation, and direct student lifecycle control. These are highly sensitive operations restricted to administrators:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **Admin** | Authority to generate manual charges, process offline payments, delete financial records, and dynamically reroute/suspend students. | `billing.create_invoice`, `billing.update_status_paid`, `billing.delete_invoice`, `student.reassign_teacher`, `student.manage_status` |
| **Teacher / Parent** | Excluded from manual billing modifications, overriding assigned teachers, or altering system enrollment statuses. | *None applicable* |
| **System Automated** | Internal background processes that synchronize data states across different modules. | `system.sync_notifications` |

### 2. Granular Permissions Breakdown

#### Group 1: Invoice Generation & Processing (`billing`)

Controls the creation, settlement, and destructive erasure of individual financial ledger entries.

* **`billing.create_invoice`**
* **Description:** Grants the ability to generate a manual, custom-billed invoice outside of the automated package renewal cycle.
* **Expected Outcome:** Authorizes access to the manual invoice form (`Fee` amount, `Issue date`). Upon submission, the system writes a new invoice record to the database with a default `"Unpaid"` status and optionally triggers an automated email dispatch to the parent.


* **`billing.update_status_paid`**
* **Description:** Grants the ability to manually verify and log the settlement of an outstanding invoice.
* **Expected Outcome:** Authorizes the "Mark as Paid" action (green checkmark). Triggers a database update that shifts the status to `"Paid"`, injects the current server timestamp into the `Paid Date` column, and revokes further edit actions for that specific row.


* **`billing.delete_invoice`**
* **Description:** Grants the authority to destructively wipe a financial record from the database.
* **Expected Outcome:** Exposes the "Delete" action (red trash can). Upon passing a mandatory confirmation prompt, the system permanently removes the invoice from the parent's billing history.



#### Group 2: Student Metadata & Lifecycle Management (`student`)

Controls the quick-action overrides for student assignment and overarching system access.

* **`student.reassign_teacher`**
* **Description:** Grants the ability to dynamically change a student's assigned instructor without navigating away from the parent's profile view.
* **Expected Outcome:** Authorizes the "Change" link under the Teacher column, mounting a dropdown of active staff. Upon submission, it instantly updates the relational database link between the Student ID and the new Teacher ID.


* **`student.manage_status`**
* **Description:** Grants the authority to alter a student's global enrollment state.
* **Expected Outcome:** Allows the user to click the current status badge (e.g., `"Regular"`) and select a new state (`"On Leave"`, `"Suspended"`). Committing this change cascades throughout the system, affecting the student's ability to be scheduled for classes and included in future automated billing cycles.



#### Group 3: Automated System Synchronization (`system`)

Controls the internal logic linking financial updates to global UI states.

* **`system.sync_notifications`**
* **Description:** An automated background rule that forces the global notification tray to reflect real-time database changes.
* **Expected Outcome:** When an Admin successfully executes `billing.update_status_paid` or `billing.delete_invoice`, this rule automatically evaluates the parent's remaining ledger. If no "Unpaid" invoices remain, it purges the parent's name from the global Unpaid Invoices notification dropdown (introduced in Part 6).

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Financial Ledger Integrity:** Notice that once `billing.update_status_paid` is executed, the UI removes further action icons (edit/pay) for that row. This ensures that paid invoices become immutable records, protected from accidental modification. If a paid invoice is fundamentally flawed, resolving it typically requires explicit administrative action (like generating a credit or using `billing.delete_invoice` if authorized).
> * **Cascading Consequences:** The `student.manage_status` permission is highly impactful. Changing a student to "Suspended" or "On Leave" must be deeply integrated with the `schedule` module to ensure that suspended students do not continue to consume teacher capacity or trigger automated classes.
> * **Cross-Module Efficiency:** The `student.reassign_teacher` capability represents a UI/UX optimization. Rather than forcing the admin to navigate to the student directory, find the student, and open a full edit form, this permission allows targeted, surgical updates directly from the overarching Parent profile.
