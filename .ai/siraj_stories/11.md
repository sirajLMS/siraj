## Siraj LMS - Permissions & Permission Groups (Part 12: 00:00 - 02:00)

### 1. Permission Groups (Roles)

The functionalities introduced in this module span global auditing, top-tier staff management, and curriculum distribution. These are mapped to the following roles:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **System Administrator** | Highest authority; capable of auditing and modifying the profiles of other high-level administrative staff. | `manager.view_directory`, `manager.edit_profile` |
| **Admin** | Authority to view global student populations, audit class histories, and provision learning materials. | `student.view_directory`, `student.view_history`, `resource.view`, `resource.upload` |
| **Teacher** | Standard capability to consume internal curriculum materials. | `resource.view` |
| **Student / Parent** | Strictly excluded from staff directories and internal curriculum files. | *None applicable* |
| **System Automated** | Internal backend rules that protect file storage from unauthorized external access. | `system.restrict_resource_access` |

### 2. Granular Permissions Breakdown

#### Group 1: Global Student Auditing (`student`)

Controls access to overarching student metrics and comprehensive historical tracking, independent of parent associations.

* **`student.view_directory`**
* **Description:** Grants access to the global Students Directory (`/students.php`).
* **Expected Outcome:** Authorizes the rendering of overarching student status metric cards and a flattened data table containing all active and inactive students, exposing cross-relational data (Parent Name, Teacher Name, Country, Hours a Week).


* **`student.view_history`**
* **Description:** Grants the ability to view a student's historical session attendance and schedules across past months.
* **Expected Outcome:** Authorizes routing to the "Class History" calendar view. Grants access to the "View Class History of Other Months" filter, allowing the user to submit Year/Month parameters to execute database queries that fetch and render historical class grids.



#### Group 2: Administrative Staff Management (`manager`)

Controls access to the internal directory of system administrators and backend managers.

* **`manager.view_directory`**
* **Description:** Grants access to the Managers List page (`/managers.php`).
* **Expected Outcome:** Renders the data table listing staff members who possess administrative backend access, exposing their contact details, Skype IDs, and privilege types.


* **`manager.edit_profile`**
* **Description:** Grants the authority to modify the comprehensive profile of a fellow administrative user.
* **Expected Outcome:** Authorizes access to the "Edit Manager Profile" form. Allows read/write actions for sensitive staff information (National ID, Skype, Phones). Upon submission, updates the manager's backend record.



#### Group 3: Learning Resources Repository (`resource`, `system`)

Controls the provisioning, consumption, and security of internal academy curriculum files.

* **`resource.view`**
* **Description:** Grants the ability to access the `/resources.php` directory and download centralized academy files.
* **Expected Outcome:** Renders the table of available documents (PDF books, syllabi, worksheets).


* **`resource.upload`**
* **Description:** Grants the authority to provision new files to the academy's shared repository.
* **Expected Outcome:** Authorizes access to the document upload modal. Processes the submission of the `Doc Name` and file object (e.g., .pdf), writes a new record to the database, and commits the file to server storage.


* **`system.restrict_resource_access`**
* **Description:** A system-level security gate that enforces strict isolation of the learning resources folder.
* **Expected Outcome:** Automatically evaluates the session token of any user attempting to access the resources directory or direct file URLs. If the user lacks the `resource.view` permission (e.g., a Student or Parent attempting to bypass the curriculum), the system blocks the request and prevents the download.

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Hierarchical Privilege Risk:** The `manager.edit_profile` permission is highly sensitive. Standard Admins typically manage Teachers and Parents, but modifying the profiles (and potentially the system privileges) of *other* Admins is an action that should usually be restricted strictly to a System Administrator/Super Admin role to prevent privilege escalation.
> * **Global vs. Relational Access:** While Part 9 introduced `student.view_associated` (allowing an admin to see a student *through* a parent's profile), `student.view_directory` provides a flattened, global perspective. This is crucial for academy-wide operations, allowing an Admin to filter or find a student without needing to know which family they belong to first.
> * **Resource Segregation:** By splitting the resources module into `resource.upload` (Admin only) and `resource.view` (Admin and Teacher), the system establishes a strict one-way distribution channel. Teachers can consume the official syllabus materials, but only Admins can dictate what those official materials are.
