## Siraj LMS - Permissions & Permission Groups (Part 9: 00:00 - 01:57)

### 1. Permission Groups (Roles)

The workflows in this module encompass sensitive user lifecycle management, financial auditing, and quota manipulation. These capabilities are strictly mapped to administrative roles:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **Academy Admin** | Authority to view comprehensive family data, suspend accounts, modify student quotas, and audit billing/legal documents. | `parent.view_profile`, `parent.manage_status`, `student.view_associated`, `student.edit_quota`, `billing.view_history`, `document.manage_parent_docs` |
| **Parent** | Restricted to their own portal. Cannot view other parents' data, modify their own status, or alter their child's system quotas. | *None applicable* |

---

### 2. Granular Permissions Breakdown

#### Group 1: Parent Profile & Account Lifecycle (`parent`)

Controls access to comprehensive family profiles and the ability to terminate system access.

* **`parent.view_profile`**
* **Description:** Grants access to the detailed Parent Profile view.
* **Expected Outcome:** Authorizes the rendering of the parent's core information (`Name`, `Email`, `Country`, `Phone`), `Social Media Links`, and overarching `Fees Details` (`Invoice Type`, `Fee`, `Payment Method`, `Currency`).


* **`parent.manage_status`**
* **Description:** Grants the ability to suspend or revoke a parent's access to the LMS.
* **Expected Outcome:** Exposes the "Deactivate Account" button. Upon clicking and passing the confirmation prompt (`"Are you sure that you want to deactivate this account?"`), the system updates the database status to deactivated, immediately restricting the parent's login capabilities.



#### Group 2: Associated Student Management (`student`)

Controls visibility into child records linked to a parent and the authority to manipulate system quotas.

* **`student.view_associated`**
* **Description:** Grants the ability to view the aggregated list of a parent's children.
* **Expected Outcome:** Renders the "Parent's Students" data table, exposing cross-relational data including the assigned `Teacher`, `Hours a Week`, and the remaining `Classes Left`.


* **`student.edit_quota`**
* **Description:** Grants the authority to manually adjust a student's available class balance.
* **Expected Outcome:** Authorizes routing to the "Edit Student Profile" view. Allows the user to modify the numerical `Classes Left` integer input. Upon saving, the system overwrites the quota in the database, directly impacting when the student's next renewal or invoice is triggered.



#### Group 3: Financial Auditing & Document Storage (`billing`, `document`)

Controls access to historical financial records and secure file attachments.

* **`billing.view_history`**
* **Description:** Grants access to the parent's historical invoicing table.
* **Expected Outcome:** Renders the "Invoices" tab. Fetches the financial ledger containing columns for `Month`, `Issue Date`, `Due Date`, `Paid Date`, `Fee`, and `Status`. Displays `"You don't have invoices."` if the array is empty.


* **`document.manage_parent_docs`**
* **Description:** Grants the ability to attach and view external files linked to the parent's record.
* **Expected Outcome:** Renders the "Upload Docs" tab, authorizing the system to accept file uploads (e.g., contracts, identity verification) and securely link them to the specific Parent ID in the database.

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Quota Manipulation Risks:** The `student.edit_quota` permission is highly sensitive. Because changing the `"Classes Left"` value directly impacts billing cycles (e.g., granting a student extra free classes or prematurely forcing an invoice), it must be strictly audited and limited to trusted administrators.
> * **Separation of Billing Scope:** While Part 6 introduced `billing.view_unpaid_invoices` for a global view of *all* academy debt, `billing.view_history` in this module allows for a localized, deep-dive audit of a *single* parent's entire financial lifecycle, including already paid invoices.
> * **Destructive Account Actions:** The `parent.manage_status` permission acts as a hard kill-switch for a family's access. The required confirmation modal acts as a UI safeguard against accidental clicks, but the backend must instantly invalidate any active session tokens for that parent upon successful deactivation.
