## Siraj LMS - Permissions & Permission Groups (Part 14: 00:00 - 02:01)

### 1. Permission Groups (Roles)

The functionalities in this module govern the onboarding of new users across all system tiers, enforcing strict boundaries around who can provision which type of account:

| Permission Group | Description | Assigned Permissions |
| --- | --- | --- |
| **System Administrator** | Highest authority; exclusively permitted to create and assign privilege tiers to new backend administrative staff. | `manager.create_account` |
| **Admin** | Authority to provision operational users (educators and clients) and configure their baseline financial and technical profiles. | `staff.create_teacher`, `parent.create_account` |
| **Unauthenticated User** | Users attempting to access the system without a valid session. | Leverages existing `auth.login`, introduces `auth.login_validation` |

---

### 2. Granular Permissions Breakdown

#### Group 1: Educator & Staff Provisioning (`staff`)

Controls the onboarding of new teaching staff and the establishment of their operational profiles.

* **`staff.create_teacher`**
* **Description:** Grants access to the "Add Teacher" workflow (`/add-teacher.php`) and the authority to write new educator records to the database.
* **Expected Outcome:** Mounts a comprehensive, multi-section form. Requires the user to input and submit data spanning `Personal Info` (Demographics, Qualifications), `Official Details` (Zoom credentials, Timezone, Skype), and highly sensitive `Salary Details` (Amount, Currency, SWIFT, IBAN). Submitting this form activates the teacher's portal access.



#### Group 2: Family & Client Provisioning (`parent`, `billing`)

Controls the onboarding of new family accounts and the initial configuration of the automated billing engine.

* **`parent.create_account`**
* **Description:** Grants access to the "Add Parent" workflow (`/add-parent.php`) to register new clients.
* **Expected Outcome:** Mounts the parent registration form. Crucially, it authorizes the configuration of the `Fees Details` section. By establishing the `Invoice Type`, `Payment Method`, and `Currency` during account creation, this permission sets the foundational rules for how the system's automated billing engine will handle this parent in the future.



#### Group 3: Administrative Provisioning (`manager`, `system`)

Controls the expansion of the backend management team and the delegation of system privileges.

* **`manager.create_account`**
* **Description:** Grants the authority to provision new backend staff and explicitly assign their RBAC privilege tier.
* **Expected Outcome:** Authorizes access to the "Add Manager" workflow (`/add-manager.php`). Processes standard personal credentials and requires a selection from the `Account Type` radio toggles (`Admin` vs. `Manager`). Upon submission, the system generates a backend user scoped precisely to the selected privilege tier.



#### Group 4: Identity & Access Management (`auth`)

Controls the security logic that rejects unauthorized access attempts and provides UI feedback.

* **`auth.login_validation`**
* **Description:** A system-level security rule that scopes credential validation to specific database tables based on the selected UI role tab.
* **Expected Outcome:** When an unauthenticated user submits credentials, the system checks *only* the database table corresponding to the selected role tab (e.g., Parent, Teacher). If the credentials do not exist in that specific scope (e.g., trying to use an Admin username on the Parent tab), the system blocks the session creation and returns an explicit, localized error: `"PLEASE CHECK THE ERRORS: The user doesn't exist."`

### 3. Traceability Mapping

> **Note on Security & Workflow Boundaries:**
> * **Delegation of Authority:** The `manager.create_account` permission is the gatekeeper of the RBAC system itself. By restricting this permission strictly to System Administrators, standard Admins are prevented from creating rogue administrative accounts or escalating their own colleagues' privileges.
> * **Role-Scoped Authentication:** The `auth.login_validation` rule ensures that a Teacher cannot log into the Parent portal, even if they have valid system credentials. By scoping the database query to the selected role tab, the LMS maintains strict separation of environments and data visibility.
> * **Financial Pre-configuration:** The `parent.create_account` workflow demonstrates that billing automation is deeply integrated into user onboarding. By forcing the Admin to define the currency and payment method at the moment of creation, the system eliminates the risk of a parent being successfully onboarded but "falling through the cracks" of the invoicing cycle.
